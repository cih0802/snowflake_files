## 11. [순서9-L 2026-07-29 Agent 기간 기본창 · 배포 경로 규명] 진단 결론 · 신규 교훈

> 트리거 = CoWork 실사용 질의 **"예산구분별 편성·집행·집행율을 보여줘"**(기간 미지정) → **전체 기간 집계**로 응답. 사용자 기대는 "최근 1년 월별".
> 결과 = 두 Agent instruction 개정 + **`cortex_agent_deploy` 로 발행 완료**(VERSION$2 = default, VERSION$1 보존).

### 11-A. 🔴 원인 — 순서9-G 발동조건의 사각지대

순서9-G(§7-A)에서 기간 스코프를 Agent 프롬프트 → SV `AI_SQL_GENERATION` 으로 이전할 때, ROLLUP 발동 조건을 **"기간·그룹이 *모두* 없을 때"** 로 한정했다. 이번 질문은 **그룹(예산구분)이 지정**되어 조건을 벗어났고, 그 경로에 기간 기본값을 줄 규칙이 **SV·Agent 어디에도 없었다**.

| 질문 유형 | 기간 | 그룹 | 9-G 커버 | 결과 |
|---|---|---|---|---|
| "집행율 알려줘" | ✗ | ✗ | 🟢 ROLLUP 발동 | 총계+최근12개월 |
| "예산구분별 집행율" | ✗ | **✓** | 🔴 **미커버** | **전기간 스캔(무증상)** |
| "2024년 예산구분별" | ✓ | ✓ | 해당없음 | 정상 |

**진단 원리**: 발동 조건을 AND로 좁히면 **좁힌 만큼 사각이 생기는데, 사각은 에러가 아니라 "그럴듯한 답"으로 나타난다.** 전기간 집계는 문법·값 모두 정상이므로 컴파일·fan-out·행수 검증을 전부 통과한다. §9-B(비율 metric 커버리지)·§9-C(코드 comment 불일치)와 **동일 계열의 무증상 결함**이다.

### 11-B. 🟢 조치 — instruction "추가"가 아니라 "제자리 교체"

`orchestration` 에 이미 **"기간·집계 SQL 스코프는 SV 의 AI_SQL_GENERATION 이 담당하므로 여기서 반복하지 않음"** 이라는 **위임 선언**이 있었다. 여기에 기간 규칙 블록을 *덧붙이면* 위임 선언과 정면 충돌한다.

- ❌ 초안: 별도 "기간 기본값 규칙" 블록 신설 → 위임 선언과 병렬 모순 → LLM이 둘 중 하나를 비결정적으로 무시
- ✅ 채택: **위임 선언 자체를 개정** — "…반복하지 않**되, 기간 미지정 시 기본 창을 질의에 명시해 전달**한다"

| Agent | 기본 창 지정 방식 | 근거 |
|---|---|---|
| AGENT_OVERALL | **SV 그레인 기준**(월=최근 12개월 월별, 일=최근 7일 일별) | 도구 4종의 그레인이 비교적 명확 |
| AGENT_MEMBER | **도구명 직접 명시**(`analyst_member_monthly`=12개월 월별, 그 외 3종=7일 일별) | **월 그레인 1종 + 일 그레인 3종 혼재** → 그레인 추론 오류 위험이 커 결정론 고정 |

공통: `"전체·전기간"` 명시 시 미적용. `response` 는 "총계 먼저+**월별** 추이" → "**기본 창** 총계 먼저+**기간별** 추이", 되묻기에 **'전체 기간'** 추가.

**폐기한 초안 3건**(자기검토):
1. "적용 기간을 응답에 명시" — `response` 1행 "조회 기간·필터를 명시"와 **완전 중복** → 삭제(토큰 순증 ≈ 0)
2. **"결과 행 수 7~12개 목표"** — 예산구분(2)×12개월=**24행**. 행 수를 목표로 주면 LLM이 기간을 임의 절단한다. 기준은 **시간 버킷 수**여야 한다
3. "연도별 최근 3개년" — 근거 없이 생성한 값

**수용한 트레이드오프**: 기본 창은 **암묵적 필터링**이라 "왜 2022년이 없지?" 혼란이 가능 → ① 적용 기간 응답 명시(기존 규칙 재사용) ② 되묻기에 '전체 기간' 노출 ③ `"전체"` 키워드로 무시 — 3중 완화.

### 11-C. 🔴 Agent 배포 3경로의 버전 의미 차이 (실측 규명 · 중대)

`SHOW VERSIONS IN AGENT` 에서 **`is_default=true` 행이 실사용자에게 서비스되는 버전**이고, `live` 는 편집 중 버전으로 default가 아니다. 이 구분을 놓치면 "배포 성공" 메시지를 받고도 실제로는 구 spec이 서비스된다.

| 경로 | default 승격 | 버전 이력 | 부수 파괴 | 판정 |
|---|---|---|---|---|
| ① `CREATE OR REPLACE AGENT` | 🟢 즉시(COMMIT 불요) | 🔴 **VERSION$1 하나로 초기화 → 전 버전 소멸** | 🔴 USAGE grant 3건 · CoWork SI 등록(§9-J §2) | 최초 생성 전용 |
| ② `cortex_agent_save` 단독 | 🔴 **안 됨**(live만 갱신) | 보존 | 없음 | 🔴 **함정** |
| ③ `cortex_agent_deploy`(save+publish) | 🟢 VERSION$N+1 생성·승격 | 🟢 보존(롤백 가능) | 없음 | ★**권장** |
| ③′ **순수 SQL**(`09` [4-B]) | 🟢 ③과 동일 | 🟢 보존 | 없음 | ★**CoCo 불요** |

**실측 근거**
- ①: 임시 agent `ZZ_TMP_VERTEST` 생성(v1) → `CREATE OR REPLACE`(v2) → `SHOW VERSIONS` 결과 **VERSION$2가 생기지 않고 VERSION$1의 내용만 v2로 교체**. 즉 롤백 대상이 사라진다.
- ②: 본 세션 초반 `cortex_agent_save` 성공 후 `SHOW VERSIONS` → live=신 spec / **VERSION$1 `is_default=true`(구 spec)**. 이 상태를 "배포 완료"로 오인 보고했다가 자기검토에서 발견.
- ③: 두 Agent 배포 후 **VERSION$2 `is_default=true`**(`agent_spec` 에 "기본 창" 포함) · VERSION$1 `is_default=false` 보존 확인.
- ③′: 임시 agent `ZZ_TMP_SQLPUB` 로 v1 생성 → `MODIFY LIVE VERSION SET SPECIFICATION`(v2) → `COMMIT` 시 **`Version VERSION$2 successfully committed`** + `is_default=true`, **VERSION$1 보존** → `ADD LIVE VERSION FROM LAST` 로 live 복구(3행). **③과 결과 동일**.

**③′ 순수 SQL 등가 경로 — CoCo/semantic_studio 없이 SQL만으로 가능**
```sql
-- 0) ★ live 선복구 — 없으면 1)이 실패 (구버전 계정 필수)
ALTER AGENT <fqn> ADD LIVE VERSION FROM LAST;    -- 이미 있으면 에러 → 09 [4-B-0] 멱등 블록
ALTER AGENT <fqn> MODIFY LIVE VERSION SET SPECIFICATION = $$ <YAML 전문> $$;  -- ⚠ 전체 교체 · = 필수
ALTER AGENT <fqn> COMMIT COMMENT = '...';        -- = 발행. VERSION$N+1 생성 + default 자동 승격
ALTER AGENT <fqn> ADD LIVE VERSION FROM LAST;    -- ⚠ COMMIT이 live를 소진 → 생략 시 이후 편집 불가
-- 4) ★ COMMENT·PROFILE 은 spec 이 아니라 DDL 속성 → 위 단계로는 안 바뀜 (⚠ 콤마 구분 필수)
ALTER AGENT <fqn> SET COMMENT = '...', PROFILE = '{"display_name":"...","color":"#..."}';
```
grant·CoWork SI 등록은 건드리지 않으므로 `09` [2]·[3]·[4] 재실행이 불필요하다. 구현체 = `09` **[4-B]** — 종전 전체 주석 템플릿이었으나 **양 Agent YAML 전문을 담은 실행 가능한 완전 SQL로 교체**(2026-07-29). 운영 계정 업데이트의 기본 경로다.

⚠ **최초 3단계안은 불완전했다 — 후속 자기검토에서 2단계 누락 발견**(`ZZ_TMP_GAP` 추가 검증):

| 누락 단계 | 증상 | 실측 |
|---|---|---|
| **0) live 선복구** | 🔴 1)이 즉시 실패 | COMMIT 후 `SHOW VERSIONS` 에 live 행 소멸 → `MODIFY LIVE VERSION` → **`Live version is not found.`** → `ADD LIVE VERSION FROM LAST` 후 3행 복구. **`COMMIT`·CoWork UI 발행 이력이 있는 계정은 live 가 없다** → 구버전 계정 시나리오에 직결 |
| **4) COMMENT·PROFILE** | 🔴 CoWork **표시명·색상·설명이 구버전으로 잔존** | spec 을 v3 로 커밋한 뒤에도 `comment='old-comment'`·`display_name='구버전표시명'` 유지. `SET COMMENT='…' PROFILE='…'`(콤마 없음) → `unexpected 'PROFILE'`, 콤마 추가 후 성공 |

부수 확인: **`COMMIT` 은 멱등이 아니다** — spec 이 동일해도 새 버전을 만든다(무변경 COMMIT → `VERSION$2` 생성). 재실행형 스크립트에서 버전이 무한 증식하므로 **변경이 있을 때만 COMMIT** 해야 한다.

↔ 4단계의 성질은 **양날**이다: ①(`CREATE OR REPLACE`)은 COMMENT·PROFILE 을 매번 재지정해야 하고 누락 시 **소실**되지만, ③′은 건드리지 않으므로 **기존 표시설정이 보존**된다. "바뀌지 않는다"는 사실을 알고 있어야 양방향으로 안전하다.

⚠ **주의**: `MODIFY LIVE VERSION` 은 전체 교체이므로 반드시 정본 `cortex_project/*.agent.yaml` **전문**을 붙여넣어야 한다. 부분 수정은 불가하며, 빠뜨린 필드는 조용히 삭제된다.

### 11-D. 🟢 CoWork `ADD AGENT` 멱등화 — 가드의 전제를 실측해야 한다

`ALTER SNOWFLAKE INTELLIGENCE … ADD AGENT` 는 **이미 등록된 agent에 재실행하면 에러**다. 재실행 가능한 배포 스크립트를 만드는 과정에서:

| 시도 | 결과 |
|---|---|
| `ADD AGENT IF NOT EXISTS` | 🔴 syntax error (미지원) |
| `REMOVE AGENT` | 🔴 syntax error — **그러나 "제거 미지원"이 아니다** |
| **`DROP AGENT`** | 🟢 **정답** (docs *Configure the visibility of agents in Snowflake CoWork*) |

⚠ **본 세션 자체 결함**: `REMOVE AGENT` 실패만 보고 "제거 구문 미지원"으로 문서에 기록했다. 문서를 확인하니 올바른 동사는 `DROP AGENT` 였다 → **실패한 추측을 사실로 기록한 사례**(P14 계열). 정정 완료.

🔴 **가드 전제의 함정(핵심)**: 해법으로 `SHOW AGENTS IN SNOWFLAKE INTELLIGENCE <si>` 사전 확인을 채택했는데, 이 결과가 `SHOW AGENTS IN ACCOUNT` 와 **정확히 동일했다**(본 계정 2건). 그러면 이 SHOW가 "계정 전체 목록"인지 "SI 멤버십"인지 **구분되지 않는다** — 전자라면 가드는 **항상 skip 하는 무력 상태**이고, 신규 환경에서 agent가 **영구히 등록되지 않는다**. 그런데 겉보기 동작은 정상(`skipped` 반환)이다.

→ **변화를 일으켜 검증**: `DROP AGENT` 직후 해당 행 **소멸(0)** → 재-`ADD` 후 **복귀(1)** 확인(자기복원 블록). **멤버십 반영 확정**.

부수 발견: Snowflake Scripting `FOR rec IN (…) DO` 의 커서 변수(`rec.col`)는 **스크립팅 표현식에서 참조 불가**(`invalid identifier 'REC.AGENT_NAME'`) → agent 목록 루프 대신 **명시 분기**로 작성.

### 11-E. 🔴 YAML gotcha — plain scalar 안의 "콜론+공백"

agent spec 의 `description` 을 plain scalar 로 두면 본문의 `활성 지표: `·`차원: ` 등 **콜론+공백**을 YAML 파서가 매핑 구분자로 해석해 `agent spec is invalid` 로 실패한다. **에러 메시지에 원인·위치가 나오지 않는다.**

```yaml
# ❌ 실패
description: 예산 팩트(FBD). 활성 지표: 편성예산·집행예산. 차원: 연/월.
# ✅ 블록 스칼라
description: |-
  예산 팩트(FBD). 활성 지표: 편성예산·집행예산. 차원: 연/월.
# ✅ 인용 (본 프로젝트 09 [1-ALT] 방식)
description: "예산 팩트(FBD). 활성 지표: 편성예산·집행예산. 차원: 연/월."
```

본 세션 첫 `cortex_agent_save` 실패의 실제 원인이었다. 한국어 설명문은 `지표: `·`차원: `·`원천: ` 패턴이 잦아 **재발 확률이 높다**.

### 11-F. ⚠ 정본↔사본 drift 4회째 재발 — P23의 실효성 부족

정본 `cortex_project/*.agent.yaml` 2종은 갱신·배포했으나, 자기검토 중 **`08 §3.1`(AGENT_MEMBER 사본)이 순서9-F/9-G 이전 구버전**임을 발견했다(라벨화·원천·기본창 모두 미반영, 장문 서술형 판본). `08 §3.2`(OVERALL)는 동기화 상태였다.

- **이번 세션 변경분이 아닌 누적 부채**이며, 사본을 근거로 재배포하면 **라벨화·원천 규칙이 소실**된다 → 전면 교체는 별도 작업으로 분리하고 `08 §3.1` 에 🔴 경고 블록 + "정본 yaml 직독" 지시 명시.
- P23(정본 위상 준수) 기록 **직후에 또 발견**됐다는 점이 중요하다. **원칙 문서화만으로는 drift가 멈추지 않는다** → 기계적 대조(정본 yaml ↔ 08 사본 diff)를 DoD에 넣지 않으면 재발한다.

### 11-G. 신규 교훈 (P-시리즈)
- **P24 (instruction 개정은 *추가*보다 *제자리 교체*)**: 프롬프트에 **위임 선언**("이건 다른 계층이 담당하므로 여기서 다루지 않음")이 있으면, 그 주제의 규칙을 **덧붙이는 순간 자기모순**이 되고 LLM은 둘 중 하나를 **비결정적으로 무시**한다. 기존 줄을 찾아 개정하라. 또 신규 규칙을 넣기 전 **기존 instruction 전문을 읽어 중복을 제거**한다(중복은 토큰 낭비 + 우선순위 혼란). **정량 목표를 줄 때는 단위를 검증**하라 — "결과 행 수"는 그룹 카디널리티에 곱해지므로 시간 버킷 수와 다르다.
- **P25 (배포 ≠ 발행 · 그리고 spec ≠ 객체속성)**: Agent 는 `live`(편집)와 `is_default`(서비스) 버전이 분리된다. **저장 성공 메시지는 발행을 보장하지 않는다.** 변경 후 반드시 `SHOW VERSIONS` 로 `is_default=true` 행의 spec을 확인한다. 경로 선택: **최초 생성만 `CREATE OR REPLACE`(이력·GRANT·SI등록 파괴), 기존 agent 갱신은 `cortex_agent_deploy` 또는 순수 SQL**(결과 동일, 툴 의존 없음). `save` 단독으로 끝내지 말 것. 순수 SQL 경로는 **3단계가 아니라 5단계**다 — ① `ADD LIVE VERSION FROM LAST`(**선복구**: COMMIT·UI 발행이 live 를 소진하므로 기존 계정은 live 가 없을 수 있고, 없으면 `MODIFY LIVE VERSION` 이 `Live version is not found.` 로 실패) ② `MODIFY LIVE VERSION SET SPECIFICATION =` ③ `COMMIT`(**멱등 아님** — 무변경이어도 새 버전 생성) ④ `ADD LIVE VERSION FROM LAST`(재개용) ⑤ `SET COMMENT, PROFILE`. **⑤가 핵심 함정**: `COMMENT`·`PROFILE`(CoWork 표시명·색상)은 **spec 이 아니라 DDL 속성**이라 spec 을 갱신해도 바뀌지 않는다 → 구버전 표시명이 조용히 잔존한다. 역으로 `CREATE OR REPLACE` 에서는 매번 재지정해야 하며 누락 시 소실된다. **"어떤 속성이 spec 안에 있고 어떤 것이 객체에 있는지"를 먼저 구분**하라.
- **P26 (가드의 관측 대상을 변화로 검증)**: 멱등 가드는 "관측값이 실제 대상 상태를 반영한다"는 **전제 위에서만** 동작한다. 두 개의 서로 다른 관측(예: `SHOW … IN SNOWFLAKE INTELLIGENCE` vs `IN ACCOUNT`)이 **우연히 같은 결과**를 내면, 잘못된 대상을 보는 가드가 **정상처럼 보인다**(항상 skip = 무력). → **상태를 변화시켜(등록 해제 → 재등록) 관측값이 따라 움직이는지 확인**한다. 조회만으로 가드를 신뢰하지 말 것. P16(감사 오탐이 미탐보다 위험)의 가드 버전.
