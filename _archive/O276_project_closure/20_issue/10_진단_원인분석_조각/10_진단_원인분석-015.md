### 22-G. 신규 교훈 P67~P75 (P76 = §22-I)

- **P67 (합계 일치는 grain 정확성의 근거가 아니다)**: 축을 하나 접어버리면 **합계는 정확히 보존되면서
  grain 만 파괴된다**. O38 의 `SUM(GOAL_CNT)` 는 원천과 완전히 일치했고 그것이 오히려 정상 신호로
  읽혔다. → 원천 대조는 **합계 + grain 카디널리티(distinct 조합수)를 함께** 본다. 합계만 맞추는
  검증은 축 소실을 **구조적으로 발견할 수 없다**.
- **P68 (키 컬럼에는 값 테스트가 아니라 규약 테스트가 필요하다)**: `MONTH_KEY` 는 `not_null`·
  `relationships` 를 다 통과하면서 1~12 였다. YYYYMM 같은 **형식 규약은 별도 단정문**이 없으면
  검사되지 않는다. → 규약을 COMMENT 로 선언한 키 컬럼은 **그 규약을 실행 가능한 테스트로도** 둔다
  (`dbt_utils` 없으면 singular test). 신설 시 **현 데이터에 돌려 위반이 검출되는지 먼저 확인**한다
  (O38 은 12키·7,272행 검출을 확인했다 — 이것이 P26 의 적용이다).
- **P69 (센티넬 제외 `where` 가 걸린 FK 가드는 그 축이 전건 센티넬이면 무력이다)**: `where SK != 0`
  는 미매핑을 관용하려는 장치인데, 축이 **아직 배선되지 않아 전건 0** 이면 검사 대상이 0행이 되어
  **PASS 가 무의미**해진다. 배선 완료 여부와 가드 유효성이 결합돼 있다는 뜻이다.
  → 센티넬 비율을 함께 관측하고(예: `count_if(SK=0)/count(*)`), **100% 센티넬인 축의 FK 가드는
  「가드 있음」으로 집계하지 않는다**. 이슈원장 §18 의 「100% 센티넬 FK 13건/7팩트」(P52) 목록이
  곧 무력 가드 목록이기도 하다.
- **P70 (`dbt compile` 은 「돌리는 것」이 아니라 「산출물을 읽는 것」이다)**: P64 는 *compile 이 SQL
  유효성을 묻지 않는다*를 말했는데, O38 은 그 다음 단계를 놓쳐서 터졌다 — compile 을 **돌렸고 정상
  종료했는데** 여러 노드 중 관심 있는 하나의 출력만 읽고 넘어갔다. Jinja 가 유효해도 **렌더 결과가
  유효한 SQL 이 아닐 수 있다**(공백제거 마커가 `select` 를 `--` 주석에 붙였다).
  → 신규·수정 노드는 **전건의 컴파일 산출물을 눈으로 확인**하거나, 렌더된 SQL 을 DB 에 `EXPLAIN`
  으로 물어본다. *"compile 이 통과했다"* 는 문장은 검증 근거가 아니다.
- **P71 (Jinja 는 SQL 주석을 주석으로 보지 않는다 · 공백제거 마커는 개행을 지운다)**: 두 가지가 결합해
  같은 파일에서 연속 2회 컴파일을 깼다. ① `set` 태그에 양방향 공백제거 마커를 쓰면 **앞뒤 개행이 함께
  삭제**되어 뒤 구문이 앞 줄(특히 `--` 주석 줄)에 흡수된다 → 태그 뒤에 SQL 이 오면 마커를 쓰지 않는다.
  ② `--` 주석 안에 Jinja 문법을 **예시로 적으면 그것도 파싱된다**(`tag name expected`) → 재발방지
  주석에 문법을 인용하지 말고 **말로 서술**한다. 교훈을 적는 행위가 새 결함을 만들 수 있다.
- **P72 (테스트 ERROR 는 산출물을 막는다 — 실패 원인이 데이터라고 가정하지 않는다)**: singular test
  자신의 SQL 결함이 ERROR 가 되면 dbt 가 **하위 노드를 SKIP** 한다. O38 에서 `WIDE_TARGET_DEV`·
  **`WIDE_DEV_ACHIEVEMENT`(세션 주 산출물, 신설)** 2건이 미생성됐다. 데이터·모델은 전부 정상이었다.
  → build 리포트에서 **ERROR 와 SKIP 을 함께** 읽고, **SKIP 목록에 신설 객체가 있는지** 확인한다.
  신설 객체는 직전 build 산물이 없으므로 SKIP = **아예 없음**이다(기존 객체의 SKIP 과 위험도가 다르다).
