Avoid that, unless specifically requested by user.\n\n**Fix — aggregate transform** (preferred):\n```json\n{\n  \"transform\": [\n    {\"aggregate\": [{\"op\": \"sum\", \"field\": \"SALES\", \"as\": \"SALES\"}], \"groupby\": [\"REGION\", \"CATEGORY\"]}\n  ],\n  \"mark\": \"bar\",\n  \"encoding\": {\n    \"x\": {\"field\": \"SALES\", \"type\": \"quantitative\"},\n    \"y\": {\"field\": \"REGION\", \"type\": \"nominal\"},\n    \"color\": {\"field\": \"CATEGORY\", \"type\": \"nominal\"}\n  }\n}\n```\n\n**Fix — grouped bar chart** (when you want to show per-item bars side by side instead of stacking):\nUse `xOffset` (vertical bars) or `yOffset` (horizontal bars) to place bars next to each other. This is the **default** for multi-color bar charts.\n```json\n{\n  \"title\": \"Revenue by Region and Category\",\n  \"mark\": \"bar\",\n  \"encoding\": {\n    \"x\": {\"field\": \"SALES\", \"type\": \"quantitative\"},\n    \"y\": {\"field\": \"REGION\", \"type\": \"nominal\"},\n    \"yOffset\": {\"field\": \"CATEGORY\", \"type\": \"nominal\"},\n    \"color\": {\"field\": \"CATEGORY\", \"type\": \"nominal\", \"title\": \"Category\"}\n  }\n}\n```\n\n**Fix — stacked bar chart** (ONLY when the user explicitly asks for a \"stacked bar chart\"):\nAdd `\"stack\": \"zero\"` to the **quantitative** axis encoding and do NOT include `xOffset`/`yOffset`. Use `\"stack\": \"normalize\"` only when the user explicitly asks for normalized/percentage stacked bars.\nNEVER use `\"stack\": false`, `\"stack\": null`, or `\"stack\": \"center\"` — these cause broken or overlapping bars.\n```json\n{\n  \"title\": \"Sales by Region and Category (Stacked)\",\n  \"mark\": \"bar\",\n  \"encoding\": {\n    \"x\": {\"field\": \"SALES\", \"type\": \"quantitative\", \"stack\": \"zero\"},\n    \"y\": {\"field\": \"REGION\", \"type\": \"nominal\"},\n    \"color\": {\"field\": \"CATEGORY\", \"type\": \"nominal\", \"title\": \"Category\"}\n  }\n}\n```\nWhen combining with fold (wide-format data with multiple metric columns):\n```json\n{\n  \"transform\": [\n    {\"fold\": [\"CAPACITY\", \"UTILIZATION\"]},\n    {\"calculate\": \"({'CAPACITY': 'Capacity', 'UTILIZATION': 'Utilization'})[datum.key]\", \"as\": \"key\"}\n  ],\n  \"mark\": \"bar\",\n  \"encoding\": {\n    \"x\": {\"field\": \"value\", \"type\": \"quantitative\"},\n    \"y\": {\"field\": \"ACCOUNT\", \"type\": \"nominal\"},\n    \"yOffset\": {\"field\": \"key\", \"type\": \"nominal\"},\n    \"color\": {\"field\": \"key\", \"type\": \"nominal\", \"title\": \"Metric\"}\n  }\n}\n```\n**Rule**: The `xOffset`/`yOffset` field MUST be different from `x` and `y` fields. Never use the same field in multiple encodings.\n\n## 2. Line charts: unique x-values per series\n\nEach color series in a line chart must have unique x-values. Duplicate x-values within the same series create ambiguous zigzag lines.\n\n**Fix — wide-format data** (multiple value columns → fold):\n```json\n{\n  \"transform\": [{\"fold\": [\"REVENUE\", \"ORDERS\"]}],\n  \"mark\": \"line\",\n  \"encoding\": {\n    \"x\": {\"field\": \"MONTH\", \"type\": \"temporal\"},\n    \"y\": {\"field\": \"value\", \"type\": \"quantitative\"},\n    \"color\": {\"field\": \"key\", \"type\": \"nominal\"}\n  }\n}\n```\n\n**Fix — duplicate rows** (aggregate transform):\n```json\n{\n  \"transform\": [\n    {\"aggregate\": [{\"op\": \"sum\", \"field\": \"SALES\", \"as\": \"SALES\"}], \"groupby\": [\"DATE\", \"REGION\"]}\n  ],\n  \"mark\": \"line\",\n  \"encoding\": {\n    \"x\": {\"field\": \"DATE\", \"type\": \"temporal\"},\n    \"y\": {\"field\": \"SALES\", \"type\": \"quantitative\"},\n    \"color\": {\"field\": \"REGION\", \"type\": \"nominal\"}\n  }\n}\n```\n\n**Fix — missing color encoding**: If data has a category column causing duplicates, add `color` encoding so each series gets its own line with unique x-values.\n\n## 3. Bar charts: custom x-axis domains cause bars extending off-screen\n\nBar marks always start from 0 on the quantitative axis. If you set a custom `scale.domain` that excludes 0 (e.g., `[0.95, 1.1]` for values near 1.0), bars will stretch from 0 (off-screen) to their value, appearing as extremely long bars extending to the left (horizontal) or bottom (vertical).\n\n**Fix — use `x2`/`y2` to anchor the bar baseline at the domain start:**\n```json\n{\n  \"mark\": \"bar\",\n  \"encoding\": {\n    \"x\": {\"field\": \"METRIC\", \"type\": \"quantitative\", \"scale\": {\"domain\": [0.95, 1.1]}},\n    \"x2\": {\"datum\": 0.95},\n    \"y\": {\"field\": \"CATEGORY\", \"type\": \"nominal\"}\n  }\n}\n```\n\n**Alternative — use tick or point marks** which don't have a baseline:\n```json\n{\n  \"mark\": {\"type\": \"tick\", \"thickness\": 3},\n  \"encoding\": {\n    \"x\": {\"field\": \"METRIC\", \"type\": \"quantitative\", \"scale\": {\"domain\": [0.95, 1.1]}},\n    \"y\": {\"field\": \"CATEGORY\", \"type\": \"nominal\"}\n  }\n}\n```\n\n**Rule**: Whenever you use a bar chart with a custom `scale.domain` that does not include 0, you MUST either set `x2`/`y2` to the domain start value, or use a non-bar mark type (tick, point, circle).\n\n## 4. Temporal line charts: regular spacing\n\nFor temporal line charts, avoid data with very irregular time gaps (e.g., daily data with multi-month gaps). Vega-Lite draws straight lines between points, making large gaps misleading.\n\n**Fix options**:\n- If the user explicitly asks for a line chart with irregular data, use `\"point\": true` to show where real observations exist: `\"mark\": {\"type\": \"line\", \"point\": true}`\n- Otherwise, prefer a Vega-Lite `filter`/`aggregate` transform to produce data with regular time intervals (e.g., fill gaps with zeros or nulls, or aggregate to a coarser granularity like monthly/quarterly). Only run a new SQL query when absolutely necessary — i.e., the required transformation cannot be expressed as a vega-lite transform\n- Provide separate charts for each interval\n\n\n## 5. Field name casing must match SQL column names exactly — and must match across layers\n\nVega-Lite field matching is **case-sensitive**. Snowflake SQL returns column names in UPPERCASE by default. Always use the exact casing from the SQL result set.\n\n**Correct:** `{\"field\": \"REVENUE\", ...}` (matches Snowflake column `REVENUE`)\n**Wrong:** `{\"field\": \"revenue\", ...}` or `{\"field\": \"Revenue\", ...}`\n\nThis applies everywhere: encoding fields, `calculate` expressions (`datum.REVENUE`), `fold` field lists, `sort` field references, and `aggregate` groupby fields.\n\n**Cross-layer rule (layered specs):** Once a `field` name is used on a shared scale (e.g. `x` is `field: \"MONTH\"` in the bar layer), every other layer that draws on that same scale **and** every key in those layers' inline `data.values` must use the *exact* same string. Do NOT rename a column to make it look \"internal\" by adding/removing an underscore (`MONTH` → `_MONTH`) or changing case (`_month_name` → `_MONTH_NAME`) in an annotation layer — the rename silently breaks shared-scale features (sort fall-through, color-scale fall-through, axis-domain mismatch).
