### 16-F. 신규 교훈

- **P47 (커버리지 분모를 잘못 고르면 실재하는 축을 삭제 후보로 만든다 — 과소평가도 결손 창작만큼 위험하다)**: DEC-28 §18-C 는 발송구분 커버리지를 **0.106%(요청 grain)** 로 적어 저가치로 판단했으나, 소비 grain(발송×회원)에서는 **21.58%** 다 — 발송구분이 붙는 요청은 평균 4,862.5명 발송이고 없는 요청은 18.7명이라 **260배** 차이가 난다. P39 는 *"분모를 개념 존재 모집단으로 하라"* 였는데 여기서는 한 걸음 더 필요하다: **분모는 소비 grain 이어야 한다.** 마스터 grain 으로 재면 fan-out 이 큰 축은 조직적으로 과소평가된다. → 차원·컬럼의 폐기/보류를 판단할 때는 **팩트 조인 후 행 기준으로 다시 센다.**
- **P48 (안전해 보이는 내장 함수가 무성 오답을 재도입할 수 있다 — 파싱은 표기를 먼저 가른다)**: O29 를 고치려고 `TRY_TO_TIME` 을 쓰면 `TRY_TO_TIME('30000000')` 이 **실패하지 않고 `05:20:00`(19,200초)** 를 반환한다. 즉 단위 미확정 숫자가 **그럴듯한 초수로 조용히 바뀌어** 고치려던 결함과 같은 종류의 오답이 다시 생긴다. `TRY_TO_*` 계열은 *"실패하면 NULL"* 이지 *"의미가 맞으면 값"* 이 아니다. → 혼재 표기를 다룰 때는 **표기 판별(`LIKE '%:%'` 등)을 먼저** 하고 분기별로 파싱한다. 그리고 **수정안도 원본과 같은 방식으로 실측 검증**한다(본 건은 distinct 9종 전량을 두 방식으로 비교해 잡았다).

### 17-C. 🔴 내 작업 사고 — 테스트가 추가되지 않았는데 "완료"로 보고했다

**§15-E·DEC-30 에 *"테스트 추가 완료"* 라고 적었으나 실제로는 파일에 아무것도 쓰이지 않았다.**

경위:
1. `cat >> _gold_ready_schema.yml <<EOF` 로 테스트를 추가하려 했다 → stderr 에 **`cat: write error: Operation not supported`** 가 나왔다. `/workspace` 마운트는 **append 모드를 지원하지 않는다.**
2. 직후 `yaml.safe_load` 로 파싱해 *"models: 26"* 을 확인하고 **성공으로 오판**했다 — 26 은 **원래 개수**였다. 즉 **변화를 확인하는 검증이 아니라 파일이 여전히 유효한지만 확인**했다.
3. 빌드는 `ERROR=0` 으로 통과했다. **없는 테스트는 실패하지 않는다** → 거짓 안심.
4. 이후 python 으로 다시 쓰고 재확인했을 때는 *"EVENT_BK 포함: True"* 가 나왔는데 **나중에 다시 읽으면 사라져 있었다**(마운트 되돌림).
5. 복구하려고 `cp /tmp/... /workspace/...` 를 실행했더니 **`File exists` 로 실패하면서 대상 파일이 삭제**됐다. `ls` 는 *"No such file"*, `cp` 는 *"File exists"* 로 **모순 상태**가 됐고 스테이지에서도 파일이 사라졌다.

🔴 **왜 이것이 O29·O28 과 같은 부류인가**: *"실패하지 않았으므로 성공했다"* 고 판단한 것이다. `TRY_TO_NUMBER` 가 에러 없이 NULL 을 만들듯, `ERROR=0` 은 *"테스트가 통과했다"* 가 아니라 *"실패한 테스트가 없다"* 는 뜻이고 **테스트가 0개여도 만족된다**(P27 의 도구 버전).

### 17-D. 신규 교훈

- **P49 (쓰기 성공은 "다시 읽어 변화를 확인"으로만 판정한다 — 파일 유효성 확인은 검증이 아니다)**: `cat >>` 가 `Operation not supported` 로 실패했는데 나는 직후 YAML 파싱이 성공하는 것을 보고 완료로 판단했다. **파싱 성공은 "파일이 망가지지 않았다"만 증명하고 "내 변경이 들어갔다"는 증명하지 않는다.** → 파일 변경 후 검증은 반드시 **추가한 식별 문자열을 grep** 하고, 나아가 **소비자에게 물어본다**(dbt 라면 `dbt list --resource-type test --select <model>` 로 테스트가 실제 등재됐는지). `/workspace` 는 append(`>>`)를 지원하지 않으므로 **전체 내용을 `/tmp` 에 만들고 `cortex ws cp` 로 올린다.**
- **P50 (`ERROR=0` 은 "검증이 통과했다"가 아니라 "실패한 검증이 없다"다 — 테스트 개수를 함께 본다)**: 내 테스트가 하나도 등록되지 않은 상태에서 빌드는 `ERROR=0` 으로 성공했다. 테스트가 없으면 아무것도 실패하지 않는다. → 가드를 추가한 뒤에는 **총 테스트 수(TOTAL) 증가분**을 확인한다(본 건 337→344 는 다른 테스트 증가였고 FEP 는 0건이었다). 이상적으로는 **가드가 실제로 잡는지 일부러 깨서 확인**한다(본 건은 사전검증 쿼리로 대체: 3키 distinct = 행수 → 통과 예측 · 오염값 2건 → warn 예측).
- **P51 (센티넬 라우팅은 업무키를 함께 보존해야 한다 — 0 은 조인을 살리려는 것이고 식별자를 버리려는 것이 아니다)**: 미매칭을 `SK=0` 으로 라우팅하는 규약은 조인 유실을 막지만, **업무키(BK)를 팩트에 함께 남기지 않으면 미매칭 대상들이 서로 구별되지 않는다.** `FEP` 는 고아 **53개 행사·263,611행(23.2%)** 이 하나로 뭉개져 있었다. → 센티넬을 쓰는 팩트 FK 에는 **원천 업무키를 degenerate key 로 병설**한다. 특히 고아 비율이 높은 축은 필수다. 기존 센티넬 축 전수 점검 대상: `SERVICE_SK`·`CAMPAIGN_SK`·`AD_CREATIVE_SK`·`REASON_SK`·`ORG_SK`.
