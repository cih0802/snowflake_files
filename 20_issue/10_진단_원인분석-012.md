## §19. 전체 환경 재구축이 「정본 DDL 미동기화」 구조 변경을 되돌렸다 (O30 · 2026-08-04)

> 본 절의 모든 수치는 **본 세션 직접 실측**이다(`INFORMATION_SCHEMA` · `QUERY_HISTORY` · `run_results.json`).
> 트리거 = 사용자가 3차 `dbt build` 를 실행했고 **ERROR 3 · SKIP 68** 이 났다. 직전 세션은 `ERROR=0` 로 끝났다.

### §19-C. 왜 에러가 3건뿐이었나 — 드리프트 방향이 증상을 결정한다

dbt `incremental` 은 **대상 테이블의 컬럼 목록**으로 `INSERT … SELECT` 를 만든다(`target/run/**.sql` 실측).

| 방향 | dbt 동작 | 증상 |
|---|---|---|
| **물리에만 있는 컬럼**(모델이 안 만듦) | `SELECT` 목록에 넣고 모델에서 찾음 | 🔴 `invalid identifier` = **에러** |
| **모델에만 있는 컬럼**(물리에 없음) | 목록에 아예 안 넣음 | 🔴 **에러 없이 조용히 폐기** |

→ O27 의 ADD 4컬럼은 **후자**였다. 즉 `DIM_MEMBER` 가 에러로 멈추지 않았다면 **`AREA_CD`·`AGE`·`PREV_*` 는 무증상으로 버려졌을 것**이다. 실제로 그런 컬럼이 하나 더 있었다:

🔴 **`GOLD.DIM_AD_CREATIVE.DURATION_SEC` — 2회 빌드 동안 무증상 폐기**. DEC-30 이 이 컬럼을 *"오배치 중복축"* 으로 DROP 판정하고 `06_DDL.sql` 에서 제거했는데, **모델은 계속 `CAST(NULL) as DURATION_SEC` 를 산출**하고 있었다. 에러도 경고도 없었고 어떤 테스트에도 걸리지 않았다. → **P57**.

### §19-F. 신규 교훈 P57

- **P57 (정본 DDL 은 재구축의 유일한 진실이다 — 물리 `ALTER` 는 정본에 접히지 않으면 「다음 재구축까지의 임시 패치」다)**: 이 프로젝트는 `CREATE OR REPLACE TABLE` 금지(FK·GRANT 보존) 규칙 때문에 구조 변경을 `ALTER` 로만 해 왔고, 정본 DDL 동기화는 **문서에 적힌 권고**였다. 그런데 전체 재구축은 **정본 DDL 을 실행**하므로, 접히지 않은 변경은 **경고 없이 통째로 사라진다**(O26 2컬럼·O27 7컬럼이 실제로 사라졌다). 더 고약한 것은 **드리프트 방향에 따라 증상이 갈린다**는 점이다 — 물리에만 있으면 `invalid identifier` 로 **시끄럽게** 죽지만, **모델에만 있으면 dbt 가 조용히 버린다**(`DIM_AD_CREATIVE.DURATION_SEC` 2회 빌드 무증상 폐기). → ① 구조 변경 DoD 에 **「정본 DDL 동기화」를 물리 `ALTER` 와 동일 세션 필수 항목**으로 못 박는다 ② 완료 판정은 문서가 아니라 **정본 DDL 로 임시 테이블을 만들어 물리와 컬럼 집합 양방향 차집합 0 을 확인**한다(본 세션 적용: DDL 30 == 물리 30) ③ **모델 산출 컬럼 vs 물리 컬럼 전수 대조를 정례 점검에 넣는다** — 이것만이 「조용히 버려지는 컬럼」을 잡는다.


### §19-G. 신규 교훈 P58 — COMMENT 의 실측 수치는 자동으로 지울 수 없다

**배경**: 사용자 규칙 확정 — *"COMMENT 에서 실측 수치는 코드값 외엔 삭제한다. 데이터는 계속 들어온다."*
COMMENT 는 SV `description` 으로 소비되므로 낡은 수치는 **무증상 오답 경로**가 된다(AD-4·P19 계열).

**규모 실측**: COMMENT **1,686개**(06_DDL 495 · 08_SILVER 734 · dbt models 457) 중
**132개**가 실측 수치 보유(06_DDL 67 · 08_SILVER 30 · models 35).

**자동화 2회 시도 → 전부 폐기**

| 시도 | 방식 | 실패 사례 |
|---|---|---|
| 1차 | 절 내부 수치 토큰 제거 + 잔해 정리 | `MM018 1개인·2기업·3단체` → **`인·2기업·3단체`**(코드값 파괴 — `1개` 패턴이 `1개인`을 먹었다) · `정본 5종을 3종으로 축약` → `정본 을 으로 축약` · `조회 시 항상 0행` → `조회 시 항상` |
| 2차 | 수치 토큰·수치만 든 괄호만 제거(주변 낱말 불가침) | `(2종 69부서/23,130명 · 3종 131부서/…)` → **`(69부서/·131부서/=)`** · `적중 96.91%(…)` → **`값..`** · `와 441건 상이·573건 동일` → `와 상이· 동일` |

**분류 결과**: 자동 처리 가능 **5건** · **수동 재작성 96건**.

- **P58 (COMMENT 의 실측 수치는 자동으로 지울 수 없다 — 애초에 넣지 마라)**: 한국어 COMMENT 에서 수치만 정규식으로 제거하면 **코드값과 문장 구조가 함께 깨진다**. 숫자는 코드값(`1개인`·`110=Success`·`1~6`)과 형태가 겹치고, 측정치는 서술 절과 엉켜 있어 **절 단위 삭제는 가드 문구를 함께 날린다**. 즉 "안전한 자동 제거"는 존재하지 않는다. → ① COMMENT 에는 **코드값·가드·정소재지·라벨 관계**만 쓰고 실측치는 **문서(문서10)에만** 둔다 ② 이미 들어간 것은 **수동 재작성만이 안전**하다(기계 처리 결과를 그대로 배포하면 코드값 파괴가 물리에 박힌다) ③ 🔴 **`ALTER … COMMENT` 문을 정본에서 verbatim 재사용할 때 수치 포함 여부를 먼저 확인**한다 — 본 세션에서 내가 O27 §4 를 그대로 적용해 10컬럼에 수치를 주입했다(§19-E ⑤).

(`grep -r 'SERVING.DIM_MONTH'`)이 필요하고, 나는 **문서가 가리킨 한 곳만** 봤다.
§19-E ① (탐지 패턴이 틀려 「손실」을 창작)과 **같은 계열의 실수를 같은 세션에서 반복**했다.

#### 실제 결함 — `08` §G.2 가 O27 을 반영하지 않았다

| 항목 | 내용 |
|---|---|
| 증상 | `SERVING.DIM_MEMBER_CURRENT` 생성문이 `NEW_EXISTING_FLAG`·`LAST_CAMPAIGN`·`CURRENT_SPONSORSHIP` 을 SELECT — **O27 이 `GOLD.DIM_MEMBER` 에서 DROP 한 컬럼** |
| 실증 | 동일 SELECT 를 현재 물리에 컴파일 → `invalid identifier 'NEW_EXISTING_FLAG'` |
| 파급 | 이 문장이 실패하면 helper 뷰가 안 생기고, `05_SV_DDL.sql` 이 그 뷰를 논리테이블로 참조하므로(4곳) **SV 배포 전체가 연쇄 실패** |
| 🔴 은폐 조건 | 이 파일은 **dbt 밖**이다 → `dbt build` 를 몇 번 돌려도 절대 드러나지 않는다. SV 배포 단계에서야 터진다 |
| 조치 | ✅ 3컬럼 제거 · 컴파일 검증 통과. SV 는 3컬럼 미참조(실측 0건)라 소비 영향 0 |

#### O27 이 번진 산출물은 4개였다

| # | 산출물 | 2026-08-04 이전 |
|---|---|---|

- **P59 (구조 변경은 소비 계층까지 역추적해야 완결된다)**: O27 은 「정본 DDL · 물리 · dbt 모델」 3곳을 맞추고 완료로 판정했는데, **소비측 뷰**가 DROP 된 컬럼을 계속 SELECT 하고 있었다. 이 결함은 **`dbt build` 로 드러나지 않는다** — 해당 파일이 dbt 관리 밖이기 때문이다. 즉 *"build 가 통과했으니 정합"* 은 **dbt 가 아는 범위 안에서만** 참이다(P50 계열). → 컬럼 `DROP`·개명 시 **워크스페이스 전역 `grep -r <컬럼명>`** 을 돌려 dbt 밖 산출물(환경 setup SQL · SV DDL · Agent spec · 런북 예제)까지 회수 목록에 넣고, 회수 여부를 **컴파일로 실증**한다.

### §19-J. 신규 교훈 P60 — 시점 스냅샷을 「현재 속성」으로 노출하면 값이 맞아도 답이 틀린다 (O34)

> ⚠️ **문서 공백 보정(2026-08-04)**: 이슈원장 §2-F 별계열 주의가 *"P60 은 §19-J"* 라고 지목하는데
> 본 문서에 그 절이 **없었다**(O33·O34·O35 진단이 이슈원장에만 기록돼 있었다). 아래는 그 회수분이다.

`DIM_MEMBER.AGE`·`AREA_CD` 는 **약정(개발) 시점에 굳는 값**인데 `DIM_MEMBER_CURRENT` 를 거쳐 SV 에
올라가면서 **현재 속성처럼** 보였다. 값·매핑·채움률은 전부 정상이라 **어떤 품질 테스트로도 잡히지 않는다**
— 의미(semantics) 결함이다.

| 검증 축 | 결과 |
|---|---|
| 라벨 매핑 | 코드사전 CM014 와 완전 일치(우리 결함 아님) |
| 독립 원천 대조 | `SND_MEMBER_LIST.AGE` 와 회원 단위 대조 — 불일치가 압도적으로 **노화 방향**(동일+늙음) |
| 약정연도 상관 | 최근 연도는 평균차 0 에 수렴하고 과거로 갈수록 단조 증가 |
| ''10대 미만'' 최다 | **실제다** — 편지쓰기대회 계열(학교·부모 DB 기반 아동 명의 약정) 캠페인 편중 |
| 현재 연령 산출 | 🔴 **불가** — BRONZE 전체에 생년월일 컬럼이 없다(전수 스캔) |

🔴 내 최초 진단은 *"원천 기본값이 첫 코드(1)로 유입된 오염"* 이었고 **틀렸다**. 분포만 보고 **시점 축을
의심하지 않았기** 때문이다.

- **P60**: ① 시점 종속 속성은 **차원·컬럼명에 시점을 박는다**(`_AT_PLEDGE`·`_AT_EVENT`) ② 배선 시
  *"이 값은 언제 굳는가"* 를 반드시 묻는다 ③ 분포가 이상하면 **값 오류를 먼저 의심하지 말고 시점 정의를
  먼저 확인**한다 ④ 검증은 **독립 원천과의 방향성 대조**(노화처럼 단조성이 있는 축은 이것으로 확정된다).
