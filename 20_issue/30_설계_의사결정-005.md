## 17. ✅ 결정 — DEC-27: 분석가 직접조회(GOLD-only) 대응 — 안전 진입점 신설 + '미상' 정상화 [2026-08-03]

> 진단 정본 = 문서10 §13-F-4(개념 부재 오라벨) · §13-F-5(팬아웃).

### 17-A. 🔴 최우선 위험 — `DIM_MEMBER` SCD2 팬아웃 (실증)

회원 관련 FACT 4개(`FACT_MEMBER_MONTHLY`·`FACT_MEMBER_EVENT`·`FACT_EVENT_PARTICIPATION`·`FACT_SERVICE_EVENT`)가 **전부 `MEMBER_DK` 로 조인**하는데 `DIM_MEMBER` 는 SCD2다 — 회원 1명 = **평균 4.50행**(최대 218 · 56.5%가 다버전).

| 실측(202606 단월) | 값 |
|---|---:|
| `FACT_MEMBER_MONTHLY` 원 행수 | 734,521 |
| `join DIM_MEMBER using (MEMBER_DK)` | **2,645,714 (3.60배)** |
| `+ where IS_CURRENT` | 734,521 (일치 ✅) |
| 납입회비 실제 | 17,132,725,212 |
| 순진한 조인 후 | **50,747,852,886 (2.96배 과대)** |

🔴 그런데 **GOLD 에는 비-WIDE 뷰가 0개**였고 안전한 현재본은 `SERVING` 스키마에만 있었다 — GOLD-only 분석가에게는 **안전한 기본값이 아예 없었다.** 에러도 경고도 없이 3배 과대계상되는 경로다.

**결정**: **`GN_DW.GOLD.DIM_MEMBER_CURRENT` 뷰 신설**(가산 — `DIM_MEMBER` 무변경). 1,763,065행 = 회원수 1:1 검증 완료. GRANT 3롤 부여. `DIM_MEMBER` 테이블·`MEMBER_DK`·`IS_CURRENT` COMMENT 에 실측 수치와 함께 경고 명시.

### 17-B. '미상' 정상화 — 개념 부재와 결측을 분리한다

**원인**: `COALESCE(라벨, '미상')` 이 **개념 부재를 결측으로 뭉갰다.** 일시회원(ONCE)은 원천에 회원상태·가입경로가 **없다**.

| 컬럼 | 종전 '미상' | 교정 후 |
|---|---:|---|
| `MEMBER_STATUS_NAME` | 175,723 | `(해당없음)` 175,722(ONCE) + NULL 1(FDRM 결측) |
| `MEMBER_STATUS_GROUP` | 175,723 | 동일 |
| `ENROLL_PATH_NAME` | 175,726 | `(해당없음)` 175,722 + NULL 4 |
| `GENDER_NAME` | 421 | **NULL**(진짜 결측 — 법인·단체는 O26 에서 이미 정규 범주로 분리됨) |

🟢 **표기는 프로젝트 기존 선례를 따랐다** — `DIM_DEVICE.sql` 5~6행이 이미 *"`(해당없음)`은 값이 확정된 정상 멤버, `0`/`(unknown)`은 진짜 미상 전용"* 으로 두 개념을 분리해 쓰고 있었다. 신규 관례 도입이 아니다.
🟢 **DEC-17-B 준수 회복** — "라벨을 강제 채우지 않는다(창작 금지)" 를 `COALESCE('미상')` 이 위반하고 있었다.

**일시회원 식별**: `MEMBER_DK` 의 `'S'` 접두로 판별한다(모델 헤더 6행의 기존 규약). 실측으로 SILVER `MEMBER_TYPE` 과 **완전 일치** 검증 — ONCE 175,722 = 상태 NULL 175,722 = 경로 NULL 175,722. → **SILVER 조인 없이 GOLD 계층 내부에서 파생 가능**하므로 뷰에 `IS_ONETIME_MEMBER` BOOLEAN 을 노출한다.

⚠️ **`MEMBER_TYPE` 이라는 이름을 쓰지 않은 이유**: GOLD 에 이미 `MEMBER_TYPE_NAME`(MM018 개인/기업/단체)이 있어 **`MEMBER_TYPE` 을 추가하면 서로의 코드/라벨 쌍으로 오인되는 새 동명이의 함정**을 만든다(P32·P17). 자기서술적 boolean 이 안전하다.

### 17-D. ⚠️ 자기검토 — 본 결정 초판의 오류 3건 (2026-08-03 당일 정정)

**초판 조치가 내가 세운 규칙 3개를 스스로 위반했다.** 전부 당일 정정했으나 유형을 남긴다.

| # | 초판 오류 | 위반 규칙 | 정정 |
|---|---|---|---|
| 1 | 정기/일시 구분을 **`MEMBER_DK LIKE 'S%'` 문자열 접두로 파생** | — | 🔴 **근본원인 오진이었다.** SILVER `CRM_MEMBER.MEMBER_TYPE` 이 **이미 존재하고 모델이 `select * from CRM_MEMBER` 로 읽고 있었는데 CTE 컬럼열거(70·83행)에서 탈락**했을 뿐이다. 즉 **G3 결손("모델O·SELECT 탈락 44") 유형 그대로**. 파생 해킹이 아니라 **컬럼 복원**이 정답 → `MEMBER_TYPE` 을 CTE·최종 SELECT·`ALTER TABLE ADD COLUMN`·06_DDL 에 반영 |

> 🔴 **[2026-08-03 DEC-28 정정] 이 단락의 결론 범위가 과했다.** `AGE` 는 연속형 나이가 아니라 **CM014 12종 코드**여서 `AGE_BAND` 는 생년월일 없이 채울 수 있다(§18-B). 생년월일이 실제로 막는 것은 **시점정확 연령**(SCD2 과거 버전의 당시 나이·LTV 연령 코호트)뿐이다. 입고 요청은 유지하되 사유를 그 선으로 좁힌다.

### 17-E. ✅ 뷰 소유권 확정 — `06_DDL.sql` 이 아니라 **dbt 모델** [2026-08-03 사용자 제기로 재검토]

사용자 지적: *"WIDE 뷰는 dbt에서 만들기로 했는데, 원본 일치를 위해 DDL 문서에 두는 게 좋을까?"* → **dbt 가 맞다.** 근거 3개 전부 실측·문서 확인.

| 근거 | 내용 |
|---|---|
| **확립 원칙** | `dbt_project.yml` §67~72: *"ref() 로 GOLD 모델 참조 → 거버넌스·리니지·build 게이트 확보(**BLOCKING-4 해소, 미거버넌스 객체 재발방지**)"* — WIDE 뷰를 dbt 로 옮긴 이유가 정확히 이것이다. 내가 만든 것이 바로 그 **미거버넌스 객체**였고, 06_DDL 이관은 **절반만 해결**이었다 |
| **범주** | `06_DDL.sql` 은 **테이블 24개 구조 소유주**다. 뷰를 여기 두는 것은 범주 오류이며, 뷰만 재생성하려 해도 `CREATE OR REPLACE TABLE` 블록이 섞인 파일을 다뤄야 한다 |
| **GRANT** | 🟢 **GOLD 스키마에 VIEW future grant 가 이미 있다**(실측: `SELECT ON FUTURE VIEWS` → `GN_DW_ANALYST`·`GN_DW_VIEWER`·`GN_DW_SERVICE`, 2026-07-30 설정). 따라서 **dbt 가 만들어도 GRANT 가 자동 부여**되고, 내가 06_DDL 에 넣은 **GRANT 3줄은 애초에 불필요**했다. 이것이 WIDE 뷰가 별도 GRANT 스크립트 없이 매 build 마다 권한을 갖는 이유다 |

**조치**: `10_dbt_pipeline/models/gold/dim/DIM_MEMBER_CURRENT.sql` 신설(`materialized='view'` · `ref('DIM_MEMBER')` · COMMENT 는 post_hook — WIDE 패턴 동일) · `06_DDL.sql` 의 CREATE VIEW/GRANT 블록은 **소유권 포인터 주석으로 대체**. `dbt compile` 로 `ref()` 해석·모델 인식(78) 확인.

📌 **일반 규칙으로 승격**: **GOLD 계층의 뷰는 dbt 모델이 소유한다**(테이블 구조는 `06_DDL.sql`, SERVING 헬퍼뷰는 `02_SERVING_setup`/`08_After_Deploy_DBT`). 계층별 소유주를 헷갈리면 미거버넌스 객체가 재발한다.

### 18-C. 🔴 B군 — `DIM_SERVICE.SEND_TYPE_L/M/S`: DROP 판정 철회 · 차원 재설계 결정 대기

⚠️ **본 절은 당일 자기검토로 초판을 철회한 것이다.** 초판은 *"grain 함수종속 불성립 → 3컬럼 DROP"* 으로 결정했다. **DROP 은 오답이다** — 이 3컬럼은 **정본 지표 #133·#134·#135(발송구분 대/중/소)** 이고 `WIDE_SERVICE_EVENT` 가 이미 그 지표번호로 노출한다. DROP 하면 정본 지표 3개가 소멸한다. 진단 정본 = 문서10 **§14-B**.

**결정 대기 선택지** (🔴 둘 다 파괴적 변경이므로 사용자 결정 전 착수 금지):

| 안 | 내용 | 위험 |
|---|---|---|
| ① grain 확장 | `DIM_SERVICE` grain 에 대/중/소 3컬럼 추가 | `SERVICE_SK` 산식 변경 → **이미 99.97% 적재된 `FACT_SERVICE_EVENT.SERVICE_SK`(A3 배선) 파괴** · 10행→74행 |

### 18-D. 판정 순서 규칙 (P37 — §17-C 규칙의 선행 단계 신설)

§17-C 의 사용자 확정 규칙(①같은 역할 컬럼 有→DROP ②BRONZE 근거 有→채움 ③둘 다 아니면 DROP)에 **grain 판정을 ② 앞에 삽입**한다.

```
① 같은 테이블에 같은 역할 컬럼이 있는가        → 있으면 DROP
②-NEW 대상 grain 에 함수종속하는가             → 아니면 DROP (원천이 있어도)
③ BRONZE/SILVER 근거가 있는가                  → 있으면 채움 (커버리지 병기)
④ 대표값 규칙이 필요한가 · 그 규칙이 확정됐는가 → 미확정이면 보류(게이트 우회 금지)
⑤ 위 어디에도 안 걸리면 DROP
```

**근거**: 본 세션 B군이 ②에서 걸렸다. ②가 없으면 "원천이 실재하므로 채움"(P14 논리)으로 잘못 진행된다. 반대로 `AGE_BAND` 는 ②를 통과하고 ④도 **불요**(원천이 이미 구간화)여서 즉시 ③ 이다.

### 18-E. 실행 순서 (DEC-27 §17-C 와 통합 — `dbt build` 는 사용자 실행)

🔴 **`CREATE OR REPLACE TABLE` 금지**(FK·GRANT 파괴). GOLD 테이블 = `ALTER TABLE ADD/DROP COLUMN`.

1. `ALTER TABLE` — GOLD 테이블 컬럼 추가/삭제 (`DIM_MEMBER`·`DIM_SERVICE`·`DIM_AD_CREATIVE`·`DIM_ORG`·FACT 4종)
2. dbt 모델 수정 — CTE 컬럼열거 **누락 방지**가 핵심(본 결손의 근본원인)
3. **WIDE 소비처 동시 수정** — `REGION`·`AGE_BAND` 각 4개 · `NEW_EXISTING_FLAG` 2개 · `FIRST/CURRENT_SPONSORSHIP` `WIDE_MEMBER_MONTHLY` · `LAST_CAMPAIGN` 0개
4. `06_DDL.sql`·`08_SILVER_테이블DDL` 정본 동기화
5. **COMMENT DoD 3종(P33)** — 물리 `ALTER … COMMENT` · 소유 산출물(뷰=`post_hook`) · **거짓이 된 주석 회수**(`DIM_AD_CREATIVE` "원천 부재" · `DIM_MEMBER` "개발·증감 대기"). ⚠️`DIM_SERVICE` 주석은 §18-C 재설계 결정과 함께 처리(단독 수정 금지)
6. `accepted_values` 가드 — `AGE_BAND`(CM014 12종)·`REGION`(CM018 18종 + sentinel `'0'`)
7. `dbt build` → `INFORMATION_SCHEMA` 스캔으로 완료 판정

⚠️ **`AGE_BAND`·`REGION` 은 `CRM_CODE` 조인으로 라벨을 만든다**(하드코딩 `CASE` 금지 — P31/DEC-25). 코드 컬럼(`AGE`·`AREA_CD`)도 **병설**한다(DEC-25 "코드+라벨 병기").
⚠️ **다중값 대표 규칙** — `REGION` 다중 지역 3.2%(최대 7) · `AGE_BAND` 는 회원이 여러 개발건을 가지면 여러 값을 가진다. `LAST_STOP_DATE`(max)·`FIRST_SPONSORSHIP`(최소 발생일)처럼 **규칙 불요한 것과 구별**해야 하며, 대표 규칙이 필요한 축은 §18-D ④ 로 되돌아간다.
⚠️ **sentinel `'0'`**(`AREA_CD` 20,624행)은 `USE_YN` 필터가 아니라 **`(미매핑)` 라우팅**으로 처리한다(DEC-26 §16-C).

### 19-B. 🔴 선행 지목의 오류가 결정으로 이어진 경로

`99_NEXT_SESSION.md` §3 과 문서10 §14-H·§14-I 는 **결론(두 체계 혼입 · 96.6% 소실 · 단위 오류)은 전부 옳았다.** 틀린 것은 **조치안의 세부 지정**이었고, 그대로 실행하면 다음이 발생했다:

- 조치안 ②를 문면대로 하면 → 고아 23.2% 에서 **판별 실패**(결정 3으로 교체)
- 조치안 ③을 문면대로 하면 → **정상 코드를 고치고 진짜 원인(원천 입력)을 방치**(결정 4로 교체)
- §3 대상 지정대로 하면 → **소비 계층(WIDE)에 경고가 안 닿음**(결정 1·2로 확장)

📌 **일반 규칙으로 승격**: 인수인계 문서의 조치안은 **결론과 별개로 재검증한다.** 결론은 실측에 근거하지만 **조치안은 그 시점의 추론**이며, 특히 *"어느 컬럼을 쓰라"* 는 지정은 §18-D ①(같은 역할 컬럼 확인)·`INFORMATION_SCHEMA` 실재 확인을 통과해야 한다. 미이행 시 P38(결손 창작)의 변형인 **"조치 창작"** 이 된다.

### 19-C. 구현 시 준수 사항

- 🟢 **GOLD 팩트 테이블 COMMENT 는 영구적이다** — `gold.fact` 는 `incremental + append + pre-hook TRUNCATE` 이고 **COMMENT 를 세팅하는 `post_hook` 이 없다**. `TRUNCATE` 는 COMMENT 를 지우지 않는다(본 세션 검증). 따라서 `ALTER … COMMENT` 만으로 충분하며 재빌드 불요.
- 🔴 **WIDE 뷰는 반대다** — `post_hook` 이 소유주이므로 **모델 파일 수정이 필수**다. 물리 ALTER 는 보조 수단.
- ⚠️ **`post_hook` 문자열에 이중인용부호를 넣지 말 것** — Jinja 문자열 이스케이프가 얽힌다. 본 세션은 `\"…\"` 를 **`「…」`** 로 교체해 회피했고 `dbt compile` 로 검증했다.
- 🔴 **완료 판정은 `INFORMATION_SCHEMA` 스캔**(P33) — 본 세션 결과 FEP 17/17 · WIDE_EP 16/16 · `DURATION_SEC` 3/3. 거짓 경고문 스캔(`온라인`) 잔존 1건은 **교정문이 구 문구를 인용해 설명하는 의도적 이력 서술**이다(§13-F-2 ④ 선례).
- 🔴 **정본 DDL 동기화 필수**(P33 ②) — GOLD 테이블 COMMENT 의 소유 산출물은 `06_DDL.sql` 이다. 물리만 고치면 다음 `CREATE OR REPLACE TABLE` 실행 시 되돌아간다.
