### 22-I. `AGENT_OVERALL` 목표 라우팅 — 「사실인 부정형 서술」도 오답을 만든다 [2026-08-05]

> 사용자 지적: *"`AGENT_OVERALL` 미적재 목록의 「사업목표 대비」는 `FACT_TARGET_BIZ` 기준이라 문자
> 그대로는 사실이지만, 「목표 달성율 보여줘」라고 물으면 「목표는 아직 없습니다」로 답할 수 있다 —
> 회원개발 목표는 이제 산출 가능한데도."*

#### 이 지적이 P61 을 한 단계 일반화한다

O38 작업 중 나는 `AGENT_OVERALL` 을 점검하고 **회수 불요**로 판정했다. 판정 근거는 실측이었고 그 실측은
지금도 맞다 — `FACT_TARGET_BIZ` **0행** · `CRM_BIZ_TARGET` **0행**(E-6 미입고)이므로
*"사업목표 대비"* 가 미적재라는 서술은 **문자 그대로 사실**이다.

🔴 **그런데 판정 기준이 틀렸다.** 내가 물은 것은 *"이 문장이 사실인가"* 였고,
물어야 했던 것은 *"이 문장으로 답하면 사용자가 옳은 답을 얻는가"* 였다.

오답 경로가 성립하는 조건이 실제로 갖춰져 있었다:
- `AGENT_OVERALL` 은 `analyst_member_monthly` 를 보유한다 → **개발 실적**은 답할 수 있다
- 그러나 그 SV 에 **목표가 없다** → 달성율의 **분모가 없다**
- 미적재 목록에는 *"사업목표 대비"* 가 있다 → 사용자가 대상을 안 밝히고 "목표 달성율"을 물으면
  이 항목에 매칭돼 **"없습니다"** 로 답할 수 있다
- 실제로는 `FACT_TARGET_DEV` **25,344행** · `WIDE_DEV_ACHIEVEMENT` **37,522행**으로 **산출 가능**하다

→ **부정형 서술이 개별적으로 사실이어도, 다른 축의 활성화로 인해 질문 단위에서는 거짓이 된다.**
「사업목표」와 「회원개발 목표」가 사용자 어휘에서는 둘 다 그냥 **"목표"** 이기 때문이다.

#### 조치 — 도구를 붙이지 않고 라우팅만 고쳤다

`AGENT_OVERALL` 은 예산·광고 도메인이므로 개발목표 도구를 붙일 대상이 아니다(도메인 경계를 흐리면
`AGENT_MEMBER` 와 소관이 겹쳐 라우팅이 더 나빠진다). **경계를 지키고 안내만 정확히 했다.**

| 위치 | 조치 |
|---|---|
| `system` | **"목표는 두 가지"** 절 신설 — 사업목표(미입고 → 산출 불가) vs 회원개발 목표(산출 가능 · `AGENT_MEMBER` 소관). *"뭉뚱그려 없다고 답하지 말 것"* · 두 목표 **합산·비교 금지** |
| `orchestration` | 목표·달성율은 이 Agent 도구로 답 불가 → `AGENT_MEMBER` 안내. 🔴 `analyst_member_monthly` 로 달성율을 만들지 말 것(**분모가 없다**) |
| `analyst_member_monthly` description | 「이 도구에는 목표가 없다」 명시 |
| `sample_questions` | **`"개발 목표 달성율을 보여줘"` 추가** |

🟢 **sample_question 을 회귀 감시로 썼다.** 오답을 유발했던 그 질문을 스펙에 박아 두면
다음 NL 스모크에서 **반드시 밟게 된다**(#12). 부정형 서술 회수는 지금까지 4회 재발했는데
(P61 · O33 · O35 · O37), 재발 감지가 사람의 기억에 의존했던 것이 원인이다.

#### 배포·검증

`09_2` 정본 경로: `ALTER WORKSPACE … COMMIT` → `ADD VERSION FROM <디렉터리>` → `SHOW VERSIONS`.
**`VERSION$4` is_default** · GRANT **4종 보존**(OWNERSHIP `GN_DW_ADMIN` + USAGE 3역할, `created_on` 불변) ·

⚠️ **관찰 1건 — 원인 미확정**: 이번엔 `ADD VERSION` 만으로 `is_default` 가 **자동 승격**됐다.

→ **결론은 바뀌지 않는다: 발행 후 `is_default` 를 실측하고, 아니면 명시 지정한다(P66).**

> *"조직·부서별 회원개발 목표 대비 달성률은?"* | `WIDE_TARGET_DEV` | **✅ 사용가능** | 목표관리 표준화

**O38 이전부터 3중으로 거짓이었다.**

반대로 「불가한 것을 가능하다」고 말하고 있었다.** 후자가 더 위험하다 — 현업이 그 객체를 조회하면
**빈 결과나 15년 합산치를 받고도 그것이 답이라고 믿는다.**

✅ 조치: 대상 객체를 `WIDE_DEV_ACHIEVEMENT` 로 교체 · 상태를 **✅ → ◐ 부분**으로 하향(상위 조직 불가 ·
증액·재후원 목표 미편성 명시) · **정정 사유를 표 아래에 명시**(사람이 읽는 문서를 조용히 바꾸지 않는다) ·

⚠️ **P76 의 적용 범위를 넓혀야 한다**: 부정형·긍정형 **양방향**으로, 그리고 **Agent 스펙뿐 아니라
현업 배포 문서까지** 점검 대상이다. 「✅ 사용가능」 표기는 **그 객체로 실제 질문에 답해 본 뒤**에만 쓴다.

#### 신규 교훈 P76

- **P76 (부정형 서술의 회수 판정은 「사실 여부」가 아니라 「그 답으로 사용자가 옳은 답을 얻는가」다)**:
  P61 은 *축이 활성인데 부정형 서술이 남으면 Agent 가 "불가"로 답한다*를 말했고, 그 회수 대상은
  **거짓이 된 문장**이었다. O38 은 한 단계 더 나아간 경우다 — 문장은 **여전히 사실**인데
  사용자 어휘가 두 대상을 같은 말(**"목표"**)로 부르기 때문에 **질문 단위에서 오답을 만든다.**
  → ① 부정형 서술을 점검할 때 *"이 문장이 사실인가"* 가 아니라 *"사용자가 이 단어로 물으면
  무엇에 매칭되는가"* 를 본다. ② **사용자 어휘가 겹치는 두 대상**(사업목표/개발목표, 실적부서/등록부서,
  사건시점/스냅샷 …)이 있으면 **둘을 명시적으로 대조**해 서술한다 — 한쪽만 적으면 다른 쪽이 그 문장에
  흡수된다. ③ 오답을 유발한 질문은 **`sample_questions` 에 넣어 회귀 감시**로 만든다
  (재발 감지를 사람의 기억에 맡기지 않는다). ④ **양방향으로 점검한다** — 「불가하다고 잘못 말하는 것」만
  아니라 **「가능하다고 잘못 말하는 것」** 도 같은 결함이며 후자가 더 위험하다(현업이 빈 결과·틀린 합계를
  답으로 믿는다). ⑤ **Agent 스펙에 그치지 말고 현업 배포 문서까지** 같은 기준으로 본다 —
  「✅ 사용가능」 표기는 **그 객체로 실제 질문에 답해 본 뒤**에만 쓴다(O38 에서 이 표기가
  3중으로 거짓이었다).

## §23. O39 — `*_MEMBERS` 컬럼이 「명」이 아니다 · grain 별로 답이 갈렸다 [2026-08-05]

### 23-A. 발단 — 내가 두 번 틀렸고, 둘 다 실측이 잡아냈다

현업 인벤토리 대조 중 「개발(명)」 서빙 경로를 보다가 `FACT_MEMBER_EVENT.DEV_MEMBERS` 의 COMMENT 가
`'개발(명) (#148)'` 인데 값이 `DEV_CNT` 와 전 행 동일한 것을 발견했다.

🔴 **1차 오판**: 「SV 에 `SUM(DEV_MEMBERS)` 가산 metric 이 없다 = 공백」이라 보고 추가를 제안했다.
→ 실측하니 `DEV_MEMBERS` 는 **0/1 플래그**이고 `SUM` 은 개발(건)이었다. 그 metric 을 「개발(명)」으로
추가했다면 **2,291,878 을 명수로 답**했을 것이다(실제 1,585,923 · **44.5% 과대**). 제안 자체가 결함이었다.

🔴 **2차 오판**: 「동일 패턴 전수 스캔 후 **일괄** 교정」을 제안했다.
→ `%MEMBERS%` 43컬럼을 전수 시험하니 **패턴이 균일하지 않았다.** `FACT_MEMBER_MONTHLY.DEV_MEMBERS`
는 **옳았고**, 이름만 보고 일괄 교정했다면 **옳은 것을 틀리게** 만들었다.

> 두 오판의 원인은 같다 — **컬럼 이름과 COMMENT 를 근거로 삼았다.** P24-B(주석은 검증이 아니다)를
> 내가 그대로 반복했다. 사용자가 "추론이 아닌 실제 데이터로 비판적 검토" 를 요구해 둘 다 잡혔다.

### 23-B. 실측 — grain 이 답을 가른다 (2026-08-05)

| 객체 | 컬럼 | grain | `SUM` | 실제 고유회원 | 판정 |
|---|---|---|---|---|---|
| `FACT_MEMBER_EVENT` | `DEV_MEMBERS` | 1행=1사건 | 2,291,878 | **1,585,923** | 🔴 **44.5% 과대** |
| `FACT_MEMBER_EVENT` | `STOP_MEMBERS` | 1행=1사건 | 1,038,262 | **903,064** | 🔴 **15.0% 과대** |
| `FACT_SERVICE_EVENT` | `SEND_MEMBERS` | 1행=1발송 | 38,470,780 | **1,031,971** | 🔴 **37.3배 과대** |
| `FACT_MEMBER_MONTHLY` | `DEV_MEMBERS` | 월×회원 | 1,996,977 | 1,996,977 | 🟢 **옳다** |
| `FACT_MEMBER_COHORT` | `ACQ_MEMBERS` | 1행=1회원 | 1,585,949 | 1,585,949 | 🟢 **옳다** |

직접 증거: FME 개발행 2,291,878 중 **같은 회원·같은 날 2건 이상이 218,948건**(회원-일 distinct
2,072,930) → 이 grain 에는 회원 dedup 이 없다. 반면 FMM 은 **466개월 전부** `SUM == COUNT(DISTINCT)`
(불일치 0개월 · 최대편차 0), COHORT 는 행수 1,585,949 = distinct 1,585,949 로 1행=1회원이다.

### 23-C. 🔴 라이브 Agent 오답 경로가 실재했다 — `SV_SERVICE`

8개 SV 를 전수 스캔해 `SUM(*_MEMBERS)` 를 쓰는 metric 을 찾았다. **한 건 나왔다**:

```
SV_SERVICE.TOTAL_SEND_MEMBERS = SUM(fse.SEND_MEMBERS)
  SYNONYMS ('발송수','발송 건수','발송 회원수')   <- 🔴 '발송 회원수'
  COMMENT '발송수 합계. F(가산).'
```

같은 SV 에 **옳은 `DISTINCT_SEND_MEMBERS = COUNT(DISTINCT MEMBER_DK)` 가 이미 있었는데**
「발송 회원수」 synonym 이 **틀린 쪽에** 붙어 있었다. 결함은 metric 부재가 아니라 **라우팅**이었다 —
「발송 회원수」를 물으면 38,470,780(실제 1,031,971 · **37.3배**)이 나올 수 있었다.

✅ **조치(배포·검증 완료)**: synonym `'발송 회원수'` 를 `TOTAL_SEND_MEMBERS` 에서 **제거**하고
`DISTINCT_SEND_MEMBERS` 로 이전(+`'발송(명)'`·`'수신자수'`·`'몇 명에게 발송'` 보강). 양쪽 COMMENT 에
건/명 구분·금지사항 명시. 값 불변(38,470,780 / 1,031,971) · owner `GN_DW_ADMIN` · GRANT 7건 보존.

> 🟢 `SV_MEMBER_EVENT` 는 애초에 `COUNT(DISTINCT)` 만 노출해 **결함이 없었다** — GOLD 컬럼 오표기의
> 실피해는 직접 SQL 소비자에 한정됐고, Agent 경로는 `SV_SERVICE` 한 곳만 뚫려 있었다.

### 23-D. 조치 — COMMENT 가드 (`03_top-down_gold/O39_COMMENT_GUARD.sql`)

### 23-F. 신규 교훈

🆕 **P78 (같은 이름의 컬럼이 grain 에 따라 옳기도 하다 · 「일괄 교정」은 그 자체로 결함이다)**:
`*_CNT`/`*_MEMBERS` 처럼 **의미가 이름에 실린 컬럼**은 이름이 아니라 **grain 으로 판정**한다.
판정식은 하나다 — `SUM(컬럼) == COUNT(DISTINCT 개체키)` 가 **모든 구간에서** 성립하는가. 성립하면
옳고(FMM·COHORT), 아니면 플래그다(FME·FSE). → ① 이름 기반 일괄 교정 금지 ② 오표기를 찾으면
**반대 방향(옳은 것을 틀리게 만들 위험)도 같은 강도로 시험** ③ 교정 스크립트의 검증에는
「대상에 반영됐는가」와 **「제외 대상이 훼손되지 않았는가」를 둘 다** 넣는다.

🆕 **P79 (metric 이 옳아도 synonym 이 틀리면 오답이다 · 라우팅도 검증 대상)**:
`SV_SERVICE` 는 옳은 `COUNT(DISTINCT)` metric 을 **갖고 있었는데도** 「발송 회원수」에 37배 값을 답할
수 있었다 — synonym 이 틀린 metric 에 붙어 있었기 때문이다. → SV 점검은 metric **정의**만 보지 말고
**어느 자연어 표현이 어느 metric 으로 가는지**를 본다. 특히 한 SV 안에 **건/명·총계/고유처럼 쌍을
이루는 metric** 이 있으면 **synonym 교차오염을 반드시 확인**한다(정의는 맞고 라우팅만 틀린 결함은
값이 그럴싸해 무증상이다).
