## §24. O40 — 납부율·미납금액의 분자·분모 모집단 불일치 · 이미 발생한 사고 [2026-08-05]

### 24-A. 발단 — Agent 답변 검증 요청에서 드러났다

사용자가 Agent 답변(2025 청구 204,757,262,930 · 납입 192,421,682,840 · 납부율 93.98% ·
총미납 12,335,580,090 · *"이미 마감된 실측치"*)의 BRONZE 대조를 요청했다. 내부 산술은 맞았고
**GOLD 가 그 값을 정확히 재현**했다 — 즉 Agent 는 시키는 대로 계산했고 **정의 자체가 틀려 있었다.**

### 24-B. 원인 — 구조로 증명했다 (근사 일치가 아니라 컬럼 존재로)

| 계층 | 사실 |
|---|---|
| SILVER | `CRM_PAYMENT_BILLING` = 회비 46,391,620 ∪ 기부금 1,130,252 = 47,521,872 |
| SILVER | **`PAYMENT_TYPE='기부금'` 1,130,252행은 `RQEST_AMT` 가 전건 NULL**(`MBRFEE_MT` 도 전건 NULL) |
| 모델 | `PAID_FEE = SUM(PAY_AMT)`(47행 line 47) · `BILLED_AMT = SUM(RQEST_AMT)`(line 48) — **필터 없음** |

→ 분자 = **회비 ∪ 기부금**, 분모 = **회비뿐**. 기부금은 원천에 청구 컬럼이 **아예 없어** 분모에
구조적으로 들어갈 수 없다. 이것이 P63 모집단 불일치의 교과서적 사례다.

> ⚠️ **1차 분석의 자기교정**: 처음엔 「`ONETIME_ONETIME_FEE` 가 기부금」이라고 40,000원 근사 일치로
> 판단했다. 모델을 열어보니 그 컬럼은 **`MT_MEMBER_TYPE='ONCE'`(일시회원) 기준**이고 기부금 테이블
> 기준이 아니었다. 축이 달라 마스터부재 314행이 어디에도 안 들어간다. → 정확한 판별자는
> **`PAYMENT_TYPE`** 이고, 실측이 이를 확정한다: 회비 46,391,620행 = `MBRFEE_DIV_CD` 비NULL
> 46,391,620행 **정확 일치** / 기부금 1,130,252행 = 비NULL **0행**.

### 24-C. 🔴 무증상이 아니라 이미 사고가 났다 — 전 기간 실측

```
SV_MEMBER_MONTHLY.PAYMENT_RATE     = 100.3608 %        <- 비율이 100% 초과
SV_MEMBER_MONTHLY.TOTAL_UNPAID_AMT = -3,218,518,220    <- 미납금액이 음수
```

**이 SV 에는 `>100%` 상한 스모크가 없었다.** O37·O38 에서 두 번 겪고 P73 으로 못박은 그 검사가
정작 금액 계열 SV 에는 걸려 있지 않았다. 2025 만 보면 93.98% / 123억으로 **그럴싸해서** 더 위험했다.

| 지표 | 현행(결함) | 정본 | 오차 |
|---|---|---|---|
| 2025 납부율 | 93.98% | **85.65%** | **+8.32%p 과대** |
| 2025 미납금액 | 12,335,580,090 | **29,251,314,636** | **2.37배 과소**(169억 누락) |
| 2025 미납비중 | 6.02% | **14.29%** | +8.27%p 과소 |

두 오차 모두 **경영 판단을 낙관 쪽으로** 왜곡한다(납부율은 좋게, 미납은 작게).

### 24-D. 세 번째 결함 — `HAS_BILLING` 이 「회비 스코프」가 아니다

Agent 답변이 `HAS_BILLING=TRUE` 를 근거로 「회비 기준」이라 서술했는데, 모델은
`HAS_BILLING = IFF(bl.MEMBER_DK IS NOT NULL, TRUE, FALSE)` 이고 `bl` 이 **회비∪기부금 CTE** 다.
COMMENT 는 `'TRUE=회비(billing) 원천 존재 행'` 이라 **회비 스코프로 믿게 만든다.**
실측: 2025 `HAS_BILLING=TRUE` 8,514,780행 중 **청구가 0/NULL 인 행 28,521건**(기부금 전용 월)이고,
2025 기부금 17,039,752,344 원이 **전액 TRUE 안에** 들어 있다. → 이 필터로는 분자가 정화되지 않는다.

### 24-E. 「마감된 실측치」도 사실이 아니다

BRONZE 최종 납입일 **2026-07-01** · 2025년분 회비 중 **2,454건 46,485,890원이 2025-12-31 이후 납입**.
회비월 데이터는 **202911** 까지 존재(미래월 편성분). → 연도 실적은 **적재 시점 스냅샷**이며
확정치가 아니다. 금액 비중은 작지만(미납의 0.16%) **성격의 오류**다.

### 24-H. 🔴 build 는 "에러 없음"으로 끝났지만 신규 컬럼이 조용히 버려졌다 [2026-08-05]

사용자가 build 를 실행했고 **`ERROR=0` · 워닝도 예정대로**였다. 그런데 신규 2컬럼이 **생기지 않았다.**

**증거 체인(전부 실측)**
| 확인 | 결과 |
|---|---|
| 모델 파일 업로드 시각 | **07:15:29 GMT** |
| build 의 FMM `INSERT` 시각 | **07:29:56 GMT** (=14분 후) → build 는 **수정된 모델을 썼다** |
| 그 `INSERT` 의 컬럼 목록 | **56개** · `PAID_FEE_BILLABLE`·`UNPAID_BILLED_AMT` **미포함** |
| ALTER 전 대상 테이블 컬럼 수 | **56개** → `INSERT` 는 **대상 테이블 컬럼만** 썼다 |
| `on_schema_change` 설정 | `dbt_project.yml`·모델 **둘 다 없음** → dbt 기본값 **`ignore`** |

→ **원인 확정**: `gold.fact` = `incremental` + `incremental_strategy: append` 이고 `on_schema_change` 가
기본값 `ignore` 다. 대상 테이블에 없는 컬럼은 dbt 가 **에러도 워닝도 없이 SELECT 에서 떨어뜨린다.**
모델은 올바르게 산출했지만 적재 경로에서 소실됐다.

🔴 **그래서 "ERROR=0" 은 성공 신호가 아니었다.** 이 프로젝트가 P75 로 못박은 「배포했다로 끝내지 않는다」가
build 에도 그대로 적용된다 — **build 성공 ≠ 의도한 컬럼이 적재됨**.

⚠️ **내 실행 순서 판단의 결함**: `O40_PAYMENT_SCOPE_FIX.sql` 은 **§1 ALTER → §2 build** 순서를 명시했는데,

### 24-G. 신규 교훈

🆕 **P80 (금액 계열 비율에도 상한·부호 스모크를 걸어라 · 「그럴싸한 구간」이 검출을 늦춘다)**:
`PAYMENT_RATE` 는 **전 기간 100.36%**, `TOTAL_UNPAID_AMT` 는 **음수**였는데 아무도 몰랐다 — P73 의
`>100%` 0행 스모크가 **개발 달성율에만** 걸려 있고 금액 계열에는 없었기 때문이다. → 비율·차액 metric
전량에 **①상한(>100%) ②부호(음수)** 스모크를 배치한다. 그리고 **최근 연도만 보고 넘기지 않는다**:
2025 는 93.98% 로 그럴싸했고 전 기간을 봤을 때만 100% 초과가 드러났다.

🆕 **P81 (「A ∪ B」 원천을 한 컬럼에 합산했으면 판별 축을 반드시 함께 노출한다)**:
`PAID_FEE` 는 회비∪기부금을 합산했는데 FMM 에 **회비/기부금 판별 축이 없었다** — 그래서 소비 계층에서
분자를 정화할 방법이 아예 없었고, `HAS_BILLING` 이 그 역할을 하는 것처럼 **이름만** 보였다.
→ 서로 다른 원천을 한 measure 에 합산할 때는 **판별 컬럼(또는 스코프된 measure)을 같은 grain 에 함께
싣는다.** 판별 축 없는 합산 measure 는 **하류에서 되돌릴 수 없는 손실**이다.
그리고 **차액식(A−B)으로 정의된 measure 는 A·B 의 모집단이 같은지 먼저 증명**한다 — 이번 미납금액이
음수가 된 것이 그 증명을 건너뛴 대가다.


🆕 **P82 (dbt `incremental+append` 에서 `on_schema_change` 기본값은 신규 컬럼을 무증상 폐기한다)**:
모델에 컬럼을 추가하고 build 가 `ERROR=0` 으로 끝나도 **대상 테이블에 그 컬럼이 없으면 조용히 사라진다**
(dbt 기본 `on_schema_change='ignore'`). → ① 팩트에 컬럼을 추가할 때는 **ALTER 를 먼저 실행하고
`INFORMATION_SCHEMA` 로 컬럼 존재를 확인한 뒤** build 한다 ② build 후 검증에 **「신규 컬럼 비NULL 건수」**
를 반드시 넣는다(행수·기존 값 불변만 보면 통과해 버린다) ③ 🔴 **실행 순서를 문서에 적는 것과 선행 단계를
실제로 완료해 두는 것은 다르다** — 사용자에게 넘길 때는 「무엇을 먼저 해야 하는지」가 아니라
**「지금 무엇만 하면 되는지」** 상태로 만들어 넘긴다.
