### 22-H. `HAS_GOAL` 개명 + `HAS_POSITIVE_GOAL` 병설 — 주석이 아니라 이름으로 고쳤다 [2026-08-05]

> 사용자 지시: *"`HAS_GOAL` COMMENT 교정 — 「목표 편성 여부」가 오해를 부른다. 「목표 행 존재(값 0 포함)」로
> 바꾸고 `HAS_POSITIVE_GOAL` 컬럼 병설 검토."*

#### 왜 COMMENT 교정만으로는 부족한가

§22-F-2 ④ 의 결함(증액 537.1% · 재후원 1700.9%)은 **COMMENT 를 잘못 읽어서 생긴 게 아니다.**
당시 COMMENT 는 *"목표 편성 여부"* 라고 적혀 있었고 **그 서술이 컬럼명과 함께 오해를 확정**시켰다.
같은 이름을 남겨두고 설명만 바꾸면 다음 사람(또는 다음 세션의 나)이 같은 실수를 반복한다 —
이 프로젝트가 P61·P75 로 이미 배운 패턴이다: **서술은 구조를 이기지 못한다.**

→ 그래서 이번엔 **개명**했다. 오해를 부르는 식별자는 이름 자체가 결함이다.

| 종전 | 교정 | 의미 |
|---|---|---|
| `HAS_GOAL` | **`HAS_GOAL_ROW`** | 목표 **행**의 존재. 값이 0·NULL 이어도 TRUE. 용도 = 「목표 행 자체가 없는 조합」 탐색 |
| — | **`HAS_POSITIVE_GOAL`** | `GOAL_CNT > 0`. **달성율 스코프의 정본** |

#### BRONZE 재스캔 — 「0 이 많다」의 원인은 결측이 아니었다

작업조건 3(원본 스캔)에 따라 `BRONZE_CRM.TM_CM_MBER_DVLP_GOAL` 25,344행을 직접 봤다.
**COMMENT·기존 기재를 근거로 삼지 않았고, 그 결과 종전 O38-D 기재가 틀렸음이 드러났다.**

| 실측 | 값 |
|---|---|
| `GOAL_CNT > 0` | **10,677행** |
| `GOAL_CNT = 0` | **14,660행** |
| `GOAL_CNT IS NULL` | **7행** (2015년 4 · 2017년 3) |
| 연도별 행수 | 2012~2019 **672~1,008** → **2020년 2,844** → 2021년 1,116 → 2022~2026 **2,484~3,384** |

🔴 **원인 = 원천의 행 생성 방식 변경.** **2020년부터** CRM 이 `부서 × 월 × 개발구분 3코드` 조합을
**전량 행으로 생성하고 미편성분을 0 으로 채운다**(2019년까지는 신규 코드만 sparse). 2021년만 축소됐다.

🔴 **종전 O38-D 기재 정정**: *"증액·재후원 목표가 2023년부터 전건 0(2022년까지는 편성)"* 이라고 적었는데
이는 **2022년만 보고 일반화한 오류**다. 실제로는 **거의 편성된 적이 없다** —

| 개발구분 | 목표가 실제 편성된 연도 |
|---|---|
| 신규(1) | **전 연도** (2025년 350,000 · 2026년 352,702) |
| 증액(2) | 2014 · 2019 · 2021(15,120) · 2022(24,612) — **4개 연도** |
| 재후원(4) | **2022(4,898) 단 1개 연도** |

→ **개발목표는 사실상 「신규」에만 편성된다.** 이 사실은 달성율을 개발구분별로 비교할 때
반드시 함께 밝혀야 한다(SV COMMENT·Agent 도구 description 에 이미 반영돼 있다).

#### `COALESCE(...,0)` 가 두 가지를 합치는 문제 — 컬럼을 만들지 않은 이유

소비뷰의 `COALESCE(g.GOAL_CNT, 0)` 는 ① FULL OUTER 미매칭(목표 행 없음) ② 원천 `GOAL_CNT` NULL
(목표 미입력) 을 모두 0 으로 만든다. ①은 `HAS_GOAL_ROW=FALSE` 로 구분되지만 ②는 「명시적 0」과 섞인다.

**세 번째 컬럼을 만들지 않았다.** 근거:
- 규모가 **7행**(0.028%)이다.
- **달성율 산술 결과가 동일**하다 — 0 과 NULL 모두 분모 기여가 0 이다.
- 구분이 필요한 경로가 이미 있다: **`FACT_TARGET_DEV.GOAL_CNT IS NULL`**(팩트는 NULL 을 보존한다).

→ 창작하지 않고(P21) **경로를 COMMENT 에 남겼다**. 컬럼 신설은 규모가 커지거나 O38-D 회신이
「0 = 명시적 0건 목표」로 확정될 때 재검토한다(그때는 NULL 과 0 의 의미가 실제로 갈린다).

#### 신설 가드 — `assert_wide_dev_achv_goal_rows_preserved`

플래그를 분리하자 **행 보존을 기계적으로 검사할 수 있게 됐다**:
`FACT_TARGET_DEV` 행수·목표합계 == 소비뷰의 `HAS_GOAL_ROW=TRUE` 행수·목표합계.

이 뷰는 FULL OUTER 조인이라 키 타입·널 처리·grain 이 어긋나면 **목표 행이 조용히 유실**된다.
유실되면 **분모가 작아져 달성율이 과대**해지는데 행수는 오히려 줄어 "정상"처럼 보인다 —
총계 대조만으로는 잡히지 않는다. 사전 실행으로 PASS 확인(25,344 · 4,622,103 양쪽 일치).
⚠️ P64/P70 준수: 파일에 넣기 전에 **live 데이터로 직접 실행**하고 `dbt compile` **렌더 산출물까지 확인**했다.

### 22-J. 비율 상한 불변식은 grain 에 의존한다 — 부서 축의 100% 초과는 정상이다 [2026-08-05]

D-4(부서별 달성율)를 재실행하니 **목표가 월 5건뿐인 소규모 센터가 171.7% 로 1위**로 올라왔다.
D-3b(개발구분×연)가 0행인데 부서 축에서는 초과가 나온 것이다.

🔴 **먼저 P73 재발을 의심하고 base 를 직접 열어 검증했다** — 결과는 **스코프 정상**이다:
해당 부서 36행 전체에서 목표는 `신규` 12개월 × 5건 = 60 뿐이고, 분자 103 은 **전부 그 `GOAL_CNT>0` 행**에서
나왔다(`증액`·`재후원` 은 목표 0 이라 분자에서 정확히 제외됐다). 즉 **진짜 초과 달성**이다.

| 실측 (2026-08-05) | 값 |
|---|---|
| 목표 보유 부서 | **203** |
| 달성율 100% 초과 부서 | **1** |
| 최대 부서 달성율 | **171.7%** |
| 그 부서의 목표가 전체 목표에서 차지하는 비중 | 60 / 4,622,103 = **0.0013%** |
| 월×부서×구분 행 중 실적 > 목표 | **1,198 / 10,677 (11.2%)** |

→ **집계 grain 에서의 100% 초과는 결함 신호지만, 세부 grain 에서는 정상적인 초과 달성이다.**
D-3b 의 판정 기준(0행)은 **그 grain 에 한정해서만** 유효하다.

🔴 **그런데 값이 맞다는 것으로 끝나지 않았다** — 이것은 NL 스모크 **#4**(*"중단률이 가장 높은 캠페인"* →
소표본이 1위면 실패)와 **정확히 같은 유형**이다. 「달성율이 가장 높은 부서」를 물으면 Agent 가
목표 5건짜리 센터를 **최우수 부서로 제시**할 수 있고, 그 답은 사실이지만 사용자는 틀린 결론을 얻는다(P76).
SV_DEV_ACHIEVEMENT 에는 규모 하한 관련 서술이 **하나도 없었다**.
