| ID | 패턴 | 내용 |
|---|---|---|
| **P18** | **비율 metric 은 분모 커버리지를 먼저 측정하고, 분자를 분모에 정합시킨다** | ①신규 SUM/SUM metric 은 배포 전 `COUNT(분모)/COUNT(*)` 를 측정한다. ②분자는 항상 `SUM(CASE WHEN <분모> IS NOT NULL THEN <분자> END)` 로 제한한다. ③분모 커버리지 **90% 미만이면 정합해도 노출 여부를 재검토**하고, 노출 시 커버리지를 comment·instruction 에 명시한다. 컴파일·fan-out·행수 검증은 이 결함을 **전부 통과**시키므로 **DoD 에 커버리지 항목을 신설**해야 한다 |

| **P20** | **시간축 NULL 의 사유는 3분류하고 실측으로 판정한다** | "지연"(곧 채워짐) / "원천 포맷 변경"(영구) / "해당 없음"(정상) 은 조치가 완전히 다르다. **월별 × 관련 컬럼쌍 교차 COUNT** 로 대체 컬럼이 그 자리를 채웠는지 확인하기 전에는 "적재 지연"으로 단정하지 않는다. 상호배타 컬럼쌍은 **검증 관계가 아니라 기간 보완 관계**다 |

> **교훈 연결**: P15("설계 완료 ≠ 값 존재")의 심화판이 P18("값 존재 ≠ 값 완비")이다.
> P19 는 P15/P18 과 달리 **결함이 데이터가 아니라 메타데이터(comment)에 있고**, 증상이 예외가 아니라 **빈 결과**라는 점에서 탐지가 가장 어렵다.
> 본 세션의 자체 결함 3건(9-B 2건 + 9-C 1건)은 모두 **최초 배포를 통과했고 재검토에서만 잡혔다** → **배포 후 비판적 재검토를 절차로 고정**할 근거(P17 과 동일한 뿌리).

## 10. [순서9-K 2026-07-29 BRONZE 원천노출 · 공8 오진 철회] 진단 결론 · 신규 교훈

> 세션 트리거: (1) "Agent가 여러 SV 결과를 스스로 조합할 수 있나 / 왜 표를 분리하나" 질의 → SV에 BRONZE 원천 기입으로 확장. (2) 사용자가 `13_SV_AD_배포_추가작업.sql` 진단쿼리를 직접 실행 → **순서9-J의 AD-1 판정이 오진임이 드러남**.

### 10-A. 🔴 뒤집힌 판정 — AD-1 "방송 개발단가 커버리지 5.2%" 는 **범주 오류**였다
순서9-J 는 공8을 "분모 커버리지 5.2% → 41% 과대계상"으로 **제거**했다. 실측 재검증 결과 **판정 근거 자체가 틀렸다**.

**원인: 분모의 유효 모집단(scope)을 확정하지 않고 커버리지를 계산했다.**

| BRONZE 원천 | 개발 컬럼 | 의미 |
|---|---|---|
| `BRONZE_AGENCY.REBRDC_AD_CMPGN_DTLS` | `DVLP_CNT`·`DVLP_MBER_CNT` **존재** | 재방송 리포트는 개발실적을 보고한다 |
| `BRONZE_AGENCY.VIDEO_AD_CMPGN_DTLS` | **없음** (`AD_CNT`·`CONV_CALL_CNT`·`INBOUND_CALL_CNT` 뿐) | 비디오 리포트는 개발 대신 **전환콜**을 보고한다 |

즉 VIDEO 의 개발 공백은 **미적재 결손이 아니라 구조적 부재**다. 그런데 종전 계산은 VIDEO(35,822행)까지 분모 모집단에 넣었다.

| 산정 범위 | 커버리지 | 미정합 | 정합 | 왜곡 |
|---|---:|---:|---:|---:|
| 방송 합계(VIDEO+REBROADCAST) = **종전 근거** | 1,982/37,886 = **5.23%** | 223,466원 | 157,969원 | **+41.5%** |
| **REBROADCAST 단독** = 올바른 모집단 | 1,982/2,064 = **96.03%** | 158,933원 | **157,969원** | **+0.61%** |

- **결론**: 공8은 자기 스코프에서 **96% 적재된 정상 지표**다. 5.2%·41.5%는 VIDEO 를 섞었을 때만 나오는 수치다.
- **추가 오기 발견**: 종전 주석 "정합해도 방송 광고비의 **29%만** 반영"은 **수치가 뒤집혔다**. 정합 분자 ₩15,215,758,016 / 방송합계 ₩21,524,449,226 = **70.7% 포함**이며, 29%는 오히려 *제외되는* VIDEO 의 몫이다.
- **조치**: `REBRDC_DEV_UNIT_PRICE` 로 **복원·노출**(공8 P2→**P1**). 명명은 `BRDC_`(방송)가 아니라 **`REBRDC_`(재방송)** — VIDEO(방송 광고비 29%)에 개발 개념이 없으므로 "방송 개발단가"는 여전히 스코프를 오인시킨다.
  > 종전의 *문제의식*("이름이 실제 커버리지를 오인시킨다")은 **타당했다**. 틀린 것은 해법이었다 — **제거가 아니라 정확한 스코프 명명**이 답이었다.
- **왜 최초에 못 잡았나**: 순서9-J 는 커버리지 결함을 *발견*하는 데 성공했지만(P18 수립), 그 결함의 **분모 모집단이 타당한지는 검증하지 않았다**. `AVG_RETENTION_MONTHS`(전건 NULL = 진짜 산출 불가) 선례에 성급히 유비한 것이 확증편향으로 작용했다.

### 10-B. BRONZE 원천(provenance)을 SV 메타데이터로 노출 — 신규 설계 규약
사용자 질의("Agent가 어느 원천에서 끌어온 건지 답할 수 있나")에서 출발. **실측으로 기술 전제를 먼저 확인**했다.

- `semantic_view_read`(SV_BUDGET 배포본) 역직렬화 결과: SV DDL 의 COMMENT 는 semantic model YAML 의 **`description` 필드로 1:1 매핑**된다(테이블 COMMENT→`tables[].description`, SV COMMENT→최상위 `description`). `description` 은 **Cortex Analyst 가 프롬프트 context 로 소비**하는 필드다.
- → 원천을 COMMENT 에 적으면 **별도 tool·Cortex Search 없이** Agent 가 provenance 질문에 창작 없이 답한다.
- **입도 결정 = 테이블 수준만**. 컬럼 단위 매핑은 넣지 않는다:

| 방식 | 비용 | 유지보수 | 채택 |
|---|---|---|---|
| (A) 테이블 수준 | COMMENT 1~3줄 | SV 재배포 1회 | ✅ |
| (B) 컬럼 수준 전량 | **매 질의 context 토큰 상시 소모** | **정본 이중화(drift)** — `04_컬럼계보매핑.md`(자동생성)와 수기 COMMENT 가 갈라짐 | ❌ |
| (C) `04_컬럼계보매핑.md` → Cortex Search 색인 → Agent tool | 검색 호출분만 | 정본 1벌 | 🔜 에스컬레이션 대기 |

- **(C) 트리거**: 현업이 컬럼 단위 출처를 반복 질문하면(CoWork 피드백·오답 로그로 확인) 색인해 `cortex_search` tool 추가. ⚠️ **P11/원칙11과 구분** — 원칙11 의 Cortex Search 는 **SV dimension 에 붙여 리터럴 필터를 해소**하는 것이고, (C)는 **Agent 에 붙는 문서 검색 tool**이다. 부착 지점·목적이 다르다.
- **부수 효과(설계 가치)**: 원천이 다른 SV 를 한 답변에 낼 때 Agent 가 **왜 표를 분리하는지 근거를 갖는다**(예산=ERP ↔ 광고=AGENCY). 종전에는 tool 결과가 물리적으로 분리돼 있어 분리 제시했을 뿐, **이유를 설명하지 못했다**.
- **가드레일 신설**: SV COMMENT 는 `REFERENCES,SELECT` 보유 role(ANALYST/VIEWER/SERVICE) 전원이 읽는다 → **PII 컬럼명 기입 금지**(`RRN_*_ENC`·`CARD_PWDNO_ENC`·연락처·주소·아동정보 = `11_BRONZE적재 컬럼대조.md §2` 목록). 원천 **시스템명을 항상 앞세운다**(VIEWER 는 BRONZE SELECT 권한이 없을 수 있어 테이블명만으로는 실행 불가).

### 10-C. 정본 위상(canonical tier) 위배 — 실행 로그에 스펙을 쓰면 정본이 뒤처진다
본 세션 최초 시도에서 Agent instruction 변경을 `09_AGENT_spec_구현.sql`에만 반영했다. 그런데 `08_AGENT_spec.md §3` 은 정본을 명시하고 있다:

```
정본 = cortex_project/{AGENT_MEMBER,AGENT_OVERALL}.agent.yaml
08_AGENT_spec.md = 동기화 사본
09_AGENT_spec_구현.sql = 대행배포 실행 로그(성공 쿼리 기록)
```

- **로그에 스펙을 쓰는 것은 카테고리 오류**다. 정본(yaml)과 사본(08)이 그대로 뒤처진다.
- 자기검토에서 **기존 부채도 함께 발견**: `AGENT_OVERALL.agent.yaml` 에 **`analyst_ad`/SV_AD 가 아예 없었다**(순서9-J 산출물이 yaml 로 전파되지 않음). 08 §3 말미에 이미 "2026-07-28 실측 시 배포된 Agent 가 문서보다 구버전" 기록이 있었다 — **동일 유형의 3회째 재발**.
- 조치: yaml 2종을 정본으로 갱신(원천 규칙 + SV_AD + 공8) · `09` 헤더에 정본 위상 경고와 4단계 반영 순서 기재.

### 10-D. SV 정본 이중화 제거 — `cortex_project/*.sv.yaml` 삭제
`cortex-project.yaml` 에 SV yaml 4종이 등록돼 있었다(`SV_BUDGET`·`SV_AD` 누락, `[원천]` 절 없음).

### 10-E. 평가셋 공백 — provenance 질문은 gold-SQL 로 채점할 수 없다 (**PRV-1**)
원천 질문을 `sample_questions` 에 추가했으나 **`07_평가셋_eval.md` 의 채점 체계와 맞지 않는다**.

- 또한 `06_검증쿼리_VQR.md` 에 등록하는 것도 **부적합**하다 — VQR 은 SQL 정본이다.
- 조치 필요(미착수): `07` 에 **가드레일(ⓖ) 신규 클래스** 신설 — "텍스트 답변 기대 · 도구 미호출 기대" 유형. 기존 ⓖ 는 "SQL 생성 거부" 케이스라 판정 축이 다르다.

### 10-F. 신규 교훈 (P-시리즈)
- **P21 (결함 판정의 모집단 검증)**: 커버리지·결손을 근거로 지표를 제거하기 전에 **분모의 유효 모집단을 먼저 확정**한다. *해당 개념이 애초에 존재하지 않는 세그먼트*를 분모에 포함시키면 정상 지표가 결함으로 오판된다. 판정문에 **모집단 정의를 명시**하고(예: "REBROADCAST 2,064행 중"), 원천 스키마에 컬럼이 **존재하는지**(구조적 부재 vs 미적재)를 `INFORMATION_SCHEMA` 로 확인한다. **P18(분모 커버리지 선측정)의 전제 조건**이다 — P18 만 적용하면 이번과 같은 오진이 난다.
- **P22 (provenance 는 소비 계층 신뢰의 일부)**: 출처를 못 대는 숫자는 현업이 채택하지 않는다. SV COMMENT 가 Cortex Analyst context 로 소비되므로 원천을 **테이블 수준**으로 기입하면 별도 도구 없이 답할 수 있다. 단 **컬럼 단위는 정본 문서로 위임**한다 — 상시 토큰 소모 + 자동생성물 이중화(drift) 때문. 메타데이터 노출 시 **읽는 주체의 권한 범위**(SV COMMENT = 소비 3역할 전원)를 전제로 PII 를 배제한다.
- **P23 (정본 위상 준수)**: 산출물은 *정본 / 동기화 사본 / 실행 로그* 위상이 다르다. **실행 로그에 스펙을 쓰면 정본이 조용히 뒤처진다.** 변경 시 정본을 먼저 고치고, 문서 헤더에 위상과 반영 순서를 명시한다. 동일 유형 재발 3회(순서9-J 배포본 구버전 · yaml 에 SV_AD 미전파 · 본 세션 최초 시도) — **자동 전파가 없는 구조에서는 순서를 문서화하는 것이 유일한 방어**다.
