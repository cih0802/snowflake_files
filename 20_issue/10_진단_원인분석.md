## 2. 핵심 교훈 (근본원인 예방)
- 사전의 **"추정"·"(LLM생성)"은 실측 전 사실 아님** → 단정 금지(P5).
- `_NO`/`_ID` 유사 키는 grain부터 의심 → distinct 비교(P2).
- PK 있어도 measure는 실물 중복 별도 확인(P4).
- **정의서 타입 ≠ 실측 타입**: UNION/캐스팅 전 `INFORMATION_SCHEMA.COLUMNS` 실타입 확인.
  - 예: `SNDNG_STDR_DE`·`SEND_DATE` 문서상 TEXT였으나 실측 DATE → `::TIMESTAMP_NTZ` 필요.
- **다계열 UNION 키는 판별자를 PK에 포함**(예 `SEND_CHANNEL`) → 미래 키 충돌 방지.

## 3. 설계 노트 (개선 후보·비긴급)
- **월 팩트 conform 갭**: `FACT_MEMBER_MONTHLY`·`ERP_BUDGET`는 `MONTH_KEY`(YYYYMM) grain인데 **DIM_MONTH 부재**, `DIM_DATE`는 일 grain → 월 팩트가 날짜차원에 단일키 조인 불가. **월 차원 신설 또는 degenerate 명시** 검토.
- **`DW_BATCH_ID` 전 SILVER NULL**: `NULL AS DW_BATCH_ID` 하드코딩(dbt `invocation_id` 미주입). 감사메타 보완 필요(GOLD는 `gold_meta` 매크로로 정상 주입). *내부 처리·현업 판정 대상 아님.*
 - **🔴 FROZEN(삭제 금지) — D1 후속**: 스캐폴드 팩트 6종(FGA·FSE·FMM·FME·FEP·FTD)은 `incremental + append + pre-hook TRUNCATE + full_refresh:false`(순서9 G-1/G-2 개정 — `table`은 CTAS가 06_DDL FK/타입 드롭해 폐기). 매 run TRUNCATE 후 전량 재적재 → 잔존행 0·멱등이나 **대량시 재적재 비용 발생**. **마감 전 볼륨·비용 재평가 후 진성 `incremental`(+merge, unique_key에 활성 SK) 재전환 여부 결정 필수.** (의사결정 상세: 문서30 D1)

- **[2026-07-23 개정2 = AI/DB 전문가 검토 반영]** §7-F 참조. "무조건 월별"의 경직성·CURRENT_DATE 오류를 교정한 **최종 설계**(VERSION$7):
  · **적용 조건 명확화**: "기간·그룹이 **모두** 없을 때만" 기본스코프 발동(그룹 지정 질문=예: 세세목별·특정 프로젝트는 대상 아님).
  · **총계+월별 동시 제공**: `GROUP BY ROLLUP((연,월))`로 12개 월별 행 + 총계 행을 한 쿼리로 반환 → 비율(집행율·납부율)도 총계 레벨에서 SUM기반 정확. Agent는 상단 총계요약→월별표→되묻기.
  · **단일값 우선**: 사용자가 "합계/총액만" 요청 시 단일값 답변.
  · **기준월 = 데이터 MAX(연월)**(CURRENT_DATE 아님): 실측 데이터 최신월이 FMM 2029-11·FBD 2026-12로 오늘(2026-07)보다 미래 → CURRENT_DATE 윈도우는 최신데이터 누락. 검증: FMM `MAX(month_key)` 기준, 발송 `MAX(cal_year*100+cal_month)` 기준으로 직전 12개월 ROLLUP 생성 확인.
- **검증**(Cortex Analyst 생성SQL): 예산 → `WHERE cal_year=(SELECT MAX(cal_year))` · 회원월 "납부율은?" → `ORDER BY month_key DESC LIMIT 1`. ✅ 트라이얼에서도 `cortex analyst query` CLI로 **생성SQL 검증 가능**(6-C DATA_AGENT_RUN 차단과 무관 — Analyst text-to-SQL은 열려 있음).
- **교훈(P11)**: **기본 필터·데이터포맷 등 "생성 SQL 제어"는 Agent instruction이 아니라 SV의 `AI_SQL_GENERATION`에 넣어야 반영된다.** Agent orchestration은 라우팅·답변톤 담당. → 6-B(P10 기간스코프 강제)의 **실행 수단이 이 계층**임을 확정.

### 7-B. 🛠️ SV 부분재배포: `CREATE OR ALTER` = GRANT 보존 (`CREATE OR REPLACE`는 소실)
- `CREATE OR REPLACE SEMANTIC VIEW`는 GRANT 전부 삭제(OWNERSHIP만 잔존) → 재부여 필요(05_SV_DDL.sql §6 경고, SV_MEMBER_MONTHLY 재배포 시 실측).
- **`CREATE OR ALTER SEMANTIC VIEW`는 기존 GRANT 보존**(SHOW GRANTS `created_on` 원본 timestamp 유지 실측). AI_SQL_GENERATION 추가처럼 **정의만 바꿀 땐 CREATE OR ALTER 권장** → 재grant 불필요. (`ALTER SEMANTIC VIEW … SET`은 COMMENT만 변경 가능.)

### 7-C. 🛠️ Agent COMMIT 후 재편집: `ADD LIVE VERSION FROM LAST` 필요
- `ALTER AGENT … COMMIT` 후 live 버전이 소진돼 다음 `MODIFY LIVE VERSION`이 **'Live version is not found'** 실패.
- **해소**: 재편집 전 `ALTER AGENT … ADD LIVE VERSION FROM LAST` → `MODIFY LIVE VERSION SET SPECIFICATION` → `COMMIT`. COMMIT이 새 VERSION을 default로 자동승격(`SET DEFAULT_VERSION=LAST`는 **미지원 — 문법오류**).

### 7-D. PoC 비즈니스로직 이식 (미납비중·총미납금액·평균납입회비)

### 7-F. AI/DB 전문가 검토 대응 (2026-07-23) · Data Mart는 Phase-2 백로그
- **AI 설계 검토(수용)**: "무조건 월별"은 문맥추론 저하·UX 경직 → 7-A 개정2로 **총계요약 우선 + 월별 추이 + 되묻기 + 단일값 우선**으로 유연화. "특정 프로젝트 예산"은 그룹 지정 질문이라 애초 기본스코프 대상 아님(적용조건 명확화로 해소).
- **DB 아키텍처 검토**:
  · (부분수용) "단일 SUM에 12개월 GROUP BY 강제 = 낭비" → 이미 12개월로 범위 제한 후의 월그룹은 풀스캔 대비 미미하고, ROLLUP 총계행으로 단일값도 동시 확보하므로 낭비 아님. "합계만" 요청 시 단일값 경로도 확보.

(설계결정 원장: 문서30에 후속 반영 대상.)
- **미해결 관찰**: `AI_SQL_GENERATION`은 자연어 지침이라 Analyst가 항상 동일 SQL을 생성하진 않음(예: budget=서브쿼리 MAX, service=산술 MAX). 결과 동치이나 결정론 아님 → VQR(ai_verified_queries)로 대표 패턴 고정이 더 강한 통제(Phase-2 후보).

#### (2) 🔴 신규 결함군 — "GOLD 설계O·값 미주입"

#### (3) 🔴→🟢 감사 도구 자체의 오탐 결함 — 전역 이름매칭의 함정

초기 구현(전역 컬럼명 매칭)은 **노출됨 153건**을 보고했으나, 검증 결과 **대부분 오탐**이었다.

| 오탐 사례 | 초기 판정 | 실제 | 원인 |
|---|---|---|---|
| `AGENCY.DEVICE` | 노출됨 | **하드코딩(전건 unknown)** | GOLD SQL 토큰에 `DEVICE` 출현 |
| `AGENCY.YEAR`·`MONTH`·`DAY` | 노출됨 | **대체노출**(DATE 파생) | `DIM_DATE.YEAR/MONTH/DAY` 와 동명이의 |

- **핵심 위험**: 미탐(false negative)은 "더 확인해야 함"으로 끝나지만, **오탐(false positive)은 실제 결손을 '정상'으로 은폐**한다.
  즉 감사 도구의 오탐은 감사를 **하지 않은 것보다 나쁘다**.
- **교정 설계 3종**:
  1. 계보 매핑 키에 **BRONZE 테이블 포함** → 원천 간 컬럼명 충돌 제거 (`AGENCY.DEVICE` ≠ `GA4.device`)
  2. 계보 매핑 값에 **GOLD 모델 포함** → 동명 컬럼의 모델별 하드코딩/실적재 구분 (`AD_COST`)
  3. 일반명(`YEAR`·`DATE`·`TEAM` 등)은 **`판정보류(동명이의)`** 로 격리 → 근거 불충분을 '노출됨'으로 반올림하지 않음
- 교정 후: 노출됨 153 → **18**, 신규 판정 `대체노출(파생)` 14 · `판정보류` 9 분리.

| **metric 식의 cross-table 참조 불가** | `RELATIONSHIPS` 가 선언돼 있어도 metric 식은 **자기 logical table 컬럼만** 참조 가능. `SUM(fap.AD_COST)/SUM(dig.CRM_DEV_CNT)` → 컴파일 실패 `invalid identifier 'DIG.CRM_DEV_CNT'` | 1:1 결합 팩트는 **SERVING helper 뷰로 pre-join** 후 단일 base (`FACT_AD_COMBINED`) |
| `CREATE OR REPLACE` 의 GRANT 소멸 | SEMANTIC VIEW·AGENT 공통. AGENT 는 추가로 **CoWork SI 등록도 소실** | SV=GRANT 3줄 재실행(또는 `CREATE OR ALTER`) · AGENT=`ALTER AGENT ... MODIFY LIVE VERSION SET SPECIFICATION`(비파괴) 우선 |
| `SEMANTIC_VIEW()` 내부 `FILTER` 구문 | 내부에서 `ad.컬럼` 별칭 참조 시 문법 오류 | 차원을 `DIMENSIONS` 에 넣고 **바깥 `WHERE` 에서 별칭 없는 컬럼명**으로 필터 |
| SERVING 스키마 FUTURE grant 부재 | GOLD 는 FUTURE TABLES/VIEWS grant 로 신규 `FACT_AD_*`·`DIM_DEVICE` 자동 커버 / **SERVING 은 미적용** | helper 뷰는 **명시 GRANT 필수** |

### 9-F. 신규 교훈 (P-시리즈)
| ID | 패턴 | 내용 |
|---|---|---|
| **P18** | **비율 metric 은 분모 커버리지를 먼저 측정하고, 분자를 분모에 정합시킨다** | ①신규 SUM/SUM metric 은 배포 전 `COUNT(분모)/COUNT(*)` 를 측정한다. ②분자는 항상 `SUM(CASE WHEN <분모> IS NOT NULL THEN <분자> END)` 로 제한한다. ③분모 커버리지 **90% 미만이면 정합해도 노출 여부를 재검토**하고, 노출 시 커버리지를 comment·instruction 에 명시한다. 컴파일·fan-out·행수 검증은 이 결함을 **전부 통과**시키므로 **DoD 에 커버리지 항목을 신설**해야 한다 |
| **P19** | **코드 차원 comment 는 실제 코드값을 전수 열거한다(관행적 예시 금지)** | Cortex Analyst 는 comment 를 필터 생성 근거로 삼는다. `'PC/MOBILE/TABLET 등'` 처럼 **추정·관행 표기**를 넣으면 존재하지 않는 값으로 필터가 생성되어 **0행 = 무증상 오답**이 된다. 저카디널리티 차원은 `SELECT DISTINCT` 실측값을 comment 에 열거하고, `AI_SQL_GENERATION` 으로 이중 가드한다 |
| **P20** | **시간축 NULL 의 사유는 3분류하고 실측으로 판정한다** | "지연"(곧 채워짐) / "원천 포맷 변경"(영구) / "해당 없음"(정상) 은 조치가 완전히 다르다. **월별 × 관련 컬럼쌍 교차 COUNT** 로 대체 컬럼이 그 자리를 채웠는지 확인하기 전에는 "적재 지연"으로 단정하지 않는다. 상호배타 컬럼쌍은 **검증 관계가 아니라 기간 보완 관계**다 |

> **교훈 연결**: P15("설계 완료 ≠ 값 존재")의 심화판이 P18("값 존재 ≠ 값 완비")이다.
> P19 는 P15/P18 과 달리 **결함이 데이터가 아니라 메타데이터(comment)에 있고**, 증상이 예외가 아니라 **빈 결과**라는 점에서 탐지가 가장 어렵다.
> 본 세션의 자체 결함 3건(9-B 2건 + 9-C 1건)은 모두 **최초 배포를 통과했고 재검토에서만 잡혔다** → **배포 후 비판적 재검토를 절차로 고정**할 근거(P17 과 동일한 뿌리).

### 9-G. 빈 틀(스캐폴드) 선제 생성에 대한 판정 — **하지 않는다**
질문: "데이터가 더 들어오면 해소될 이슈는 주석 달고 빈 틀만 만들어두면 되지 않나?"
**계층별로 답이 갈린다.**

| 계층 | 스캐폴드 | 판정 | 근거 |
|---|---|---|---|
| BRONZE/SILVER/GOLD 테이블·컬럼 | 컬럼 정의 + `0`/`CAST(NULL)` | ⚠️ **위험 — 이미 실현된 사고** | 순서9-I 의 **"설계O·값 미주입" 76건**(P15)이 정확히 이 방식의 결과다. 커버리지 점검을 통과하면서 전건 NULL |
| **SV metric / Agent 도구** | 정의만 넣고 비활성 주석 | 🔴 **금지** | 소비 계층은 **노출 자체가 계약**이다. Cortex Analyst 는 존재하는 metric 을 사용 가능하다고 간주하므로, 빈 metric 은 오답 또는 0/NULL 을 사실처럼 반환한다. `AVG_RETENTION_MONTHS`(순9-E)·`BRDC_DEV_UNIT_PRICE`(본 세션)가 실사례 |

**결론**: "구조는 미리 설계하고 문서에 적되, **소비 계층(SV/Agent)에는 검증된 것만 노출**한다."
스캐폴드의 진짜 위험은 잊혀지는 것이 아니라 — **정적 점검을 통과해서 '완료'로 집계되는 것**이다(P15).
빈 metric 을 두는 대신 문서에 활성 트리거를 적으면, 구조 재사용 이점은 유지하면서 오답 위험은 0 이 된다.
> ⚠️ **[순서9-K 보정]** 위 표의 `BRDC_DEV_UNIT_PRICE` 실사례 인용은 **부적절**했다 — 그것은 "빈 metric"이 아니라 **정상 적재된 metric을 오진으로 제거한 사례**다(§10-A). 이 칸의 유효 실사례는 `AVG_RETENTION_MONTHS`(전건 NULL) 뿐이다. 원칙(🔴 금지) 자체는 유지.

### 10-A. 🔴 뒤집힌 판정 — AD-1 "방송 개발단가 커버리지 5.2%" 는 **범주 오류**였다
순서9-J 는 공8을 "분모 커버리지 5.2% → 41% 과대계상"으로 **제거**했다. 실측 재검증 결과 **판정 근거 자체가 틀렸다**.

**원인: 분모의 유효 모집단(scope)을 확정하지 않고 커버리지를 계산했다.**

즉 VIDEO 의 개발 공백은 **미적재 결손이 아니라 구조적 부재**다. 그런데 종전 계산은 VIDEO(35,822행)까지 분모 모집단에 넣었다.

| 산정 범위 | 커버리지 | 미정합 | 정합 | 왜곡 |
|---|---:|---:|---:|---:|
| 방송 합계(VIDEO+REBROADCAST) = **종전 근거** | 1,982/37,886 = **5.23%** | 223,466원 | 157,969원 | **+41.5%** |

- **추가 오기 발견**: 종전 주석 "정합해도 방송 광고비의 **29%만** 반영"은 **수치가 뒤집혔다**. 정합 분자 ₩15,215,758,016 / 방송합계 ₩21,524,449,226 = **70.7% 포함**이며, 29%는 오히려 *제외되는* VIDEO 의 몫이다.

### 10-F. 신규 교훈 (P-시리즈)
- **P21 (결함 판정의 모집단 검증)**: 커버리지·결손을 근거로 지표를 제거하기 전에 **분모의 유효 모집단을 먼저 확정**한다. *해당 개념이 애초에 존재하지 않는 세그먼트*를 분모에 포함시키면 정상 지표가 결함으로 오판된다. 판정문에 **모집단 정의를 명시**하고(예: "REBROADCAST 2,064행 중"), 원천 스키마에 컬럼이 **존재하는지**(구조적 부재 vs 미적재)를 `INFORMATION_SCHEMA` 로 확인한다. **P18(분모 커버리지 선측정)의 전제 조건**이다 — P18 만 적용하면 이번과 같은 오진이 난다.
- **P22 (provenance 는 소비 계층 신뢰의 일부)**: 출처를 못 대는 숫자는 현업이 채택하지 않는다. SV COMMENT 가 Cortex Analyst context 로 소비되므로 원천을 **테이블 수준**으로 기입하면 별도 도구 없이 답할 수 있다. 단 **컬럼 단위는 정본 문서로 위임**한다 — 상시 토큰 소모 + 자동생성물 이중화(drift) 때문. 메타데이터 노출 시 **읽는 주체의 권한 범위**(SV COMMENT = 소비 3역할 전원)를 전제로 PII 를 배제한다.
- **P23 (정본 위상 준수)**: 산출물은 *정본 / 동기화 사본 / 실행 로그* 위상이 다르다. **실행 로그에 스펙을 쓰면 정본이 조용히 뒤처진다.** 변경 시 정본을 먼저 고치고, 문서 헤더에 위상과 반영 순서를 명시한다. 동일 유형 재발 3회(순서9-J 배포본 구버전 · yaml 에 SV_AD 미전파 · 본 세션 최초 시도) — **자동 전파가 없는 구조에서는 순서를 문서화하는 것이 유일한 방어**다.

### 11-C. 🔴 Agent 배포 3경로의 버전 의미 차이 (실측 규명 · 중대)

`SHOW VERSIONS IN AGENT` 에서 **`is_default=true` 행이 실사용자에게 서비스되는 버전**이고, `live` 는 편집 중 버전으로 default가 아니다. 이 구분을 놓치면 "배포 성공" 메시지를 받고도 실제로는 구 spec이 서비스된다.

| 경로 | default 승격 | 버전 이력 | 부수 파괴 | 판정 |
|---|---|---|---|---|
| ① `CREATE OR REPLACE AGENT` | 🟢 즉시(COMMIT 불요) | 🔴 **VERSION$1 하나로 초기화 → 전 버전 소멸** | 🔴 USAGE grant 3건 · CoWork SI 등록(§9-J §2) | 최초 생성 전용 |
| ② `cortex_agent_save` 단독 | 🔴 **안 됨**(live만 갱신) | 보존 | 없음 | 🔴 **함정** |
| ③ `cortex_agent_deploy`(save+publish) | 🟢 VERSION$N+1 생성·승격 | 🟢 보존(롤백 가능) | 없음 | ★**권장** |
| ③′ **순수 SQL**(`09` [4-B]) | 🟢 ③과 동일 | 🟢 보존 | 없음 | ★**CoCo 불요** |

**실측 근거**
- ①: 임시 agent `ZZ_TMP_VERTEST` 생성(v1) → `CREATE OR REPLACE`(v2) → `SHOW VERSIONS` 결과 **VERSION$2가 생기지 않고 VERSION$1의 내용만 v2로 교체**. 즉 롤백 대상이 사라진다.
- ②: 본 세션 초반 `cortex_agent_save` 성공 후 `SHOW VERSIONS` → live=신 spec / **VERSION$1 `is_default=true`(구 spec)**. 이 상태를 "배포 완료"로 오인 보고했다가 자기검토에서 발견.
- ③: 두 Agent 배포 후 **VERSION$2 `is_default=true`**(`agent_spec` 에 "기본 창" 포함) · VERSION$1 `is_default=false` 보존 확인.
- ③′: 임시 agent `ZZ_TMP_SQLPUB` 로 v1 생성 → `MODIFY LIVE VERSION SET SPECIFICATION`(v2) → `COMMIT` 시 **`Version VERSION$2 successfully committed`** + `is_default=true`, **VERSION$1 보존** → `ADD LIVE VERSION FROM LAST` 로 live 복구(3행). **③과 결과 동일**.

**③′ 순수 SQL 등가 경로 — CoCo/semantic_studio 없이 SQL만으로 가능**
```sql
-- 0) ★ live 선복구 — 없으면 1)이 실패 (구버전 계정 필수)
ALTER AGENT <fqn> ADD LIVE VERSION FROM LAST;    -- 이미 있으면 에러 → 09 [4-B-0] 멱등 블록
ALTER AGENT <fqn> MODIFY LIVE VERSION SET SPECIFICATION = $$ <YAML 전문> $$;  -- ⚠ 전체 교체 · = 필수
ALTER AGENT <fqn> COMMIT COMMENT = '...';        -- = 발행. VERSION$N+1 생성 + default 자동 승격
ALTER AGENT <fqn> ADD LIVE VERSION FROM LAST;    -- ⚠ COMMIT이 live를 소진 → 생략 시 이후 편집 불가
-- 4) ★ COMMENT·PROFILE 은 spec 이 아니라 DDL 속성 → 위 단계로는 안 바뀜 (⚠ 콤마 구분 필수)
ALTER AGENT <fqn> SET COMMENT = '...', PROFILE = '{"display_name":"...","color":"#..."}';
```
grant·CoWork SI 등록은 건드리지 않으므로 `09` [2]·[3]·[4] 재실행이 불필요하다. 구현체 = `09` **[4-B]** — 종전 전체 주석 템플릿이었으나 **양 Agent YAML 전문을 담은 실행 가능한 완전 SQL로 교체**(2026-07-29). 운영 계정 업데이트의 기본 경로다.

⚠ **최초 3단계안은 불완전했다 — 후속 자기검토에서 2단계 누락 발견**(`ZZ_TMP_GAP` 추가 검증):

| 누락 단계 | 증상 | 실측 |
|---|---|---|
| **0) live 선복구** | 🔴 1)이 즉시 실패 | COMMIT 후 `SHOW VERSIONS` 에 live 행 소멸 → `MODIFY LIVE VERSION` → **`Live version is not found.`** → `ADD LIVE VERSION FROM LAST` 후 3행 복구. **`COMMIT`·CoWork UI 발행 이력이 있는 계정은 live 가 없다** → 구버전 계정 시나리오에 직결 |
| **4) COMMENT·PROFILE** | 🔴 CoWork **표시명·색상·설명이 구버전으로 잔존** | spec 을 v3 로 커밋한 뒤에도 `comment='old-comment'`·`display_name='구버전표시명'` 유지. `SET COMMENT='…' PROFILE='…'`(콤마 없음) → `unexpected 'PROFILE'`, 콤마 추가 후 성공 |

부수 확인: **`COMMIT` 은 멱등이 아니다** — spec 이 동일해도 새 버전을 만든다(무변경 COMMIT → `VERSION$2` 생성). 재실행형 스크립트에서 버전이 무한 증식하므로 **변경이 있을 때만 COMMIT** 해야 한다.

↔ 4단계의 성질은 **양날**이다: ①(`CREATE OR REPLACE`)은 COMMENT·PROFILE 을 매번 재지정해야 하고 누락 시 **소실**되지만, ③′은 건드리지 않으므로 **기존 표시설정이 보존**된다. "바뀌지 않는다"는 사실을 알고 있어야 양방향으로 안전하다.

⚠ **주의**: `MODIFY LIVE VERSION` 은 전체 교체이므로 반드시 정본 `cortex_project/*.agent.yaml` **전문**을 붙여넣어야 한다. 부분 수정은 불가하며, 빠뜨린 필드는 조용히 삭제된다.

### 11-D. 🟢 CoWork `ADD AGENT` 멱등화 — 가드의 전제를 실측해야 한다

`ALTER SNOWFLAKE INTELLIGENCE … ADD AGENT` 는 **이미 등록된 agent에 재실행하면 에러**다. 재실행 가능한 배포 스크립트를 만드는 과정에서:

| 시도 | 결과 |
|---|---|
| `ADD AGENT IF NOT EXISTS` | 🔴 syntax error (미지원) |
| `REMOVE AGENT` | 🔴 syntax error — **그러나 "제거 미지원"이 아니다** |
| **`DROP AGENT`** | 🟢 **정답** (docs *Configure the visibility of agents in Snowflake CoWork*) |

⚠ **본 세션 자체 결함**: `REMOVE AGENT` 실패만 보고 "제거 구문 미지원"으로 문서에 기록했다. 문서를 확인하니 올바른 동사는 `DROP AGENT` 였다 → **실패한 추측을 사실로 기록한 사례**(P14 계열). 정정 완료.

🔴 **가드 전제의 함정(핵심)**: 해법으로 `SHOW AGENTS IN SNOWFLAKE INTELLIGENCE <si>` 사전 확인을 채택했는데, 이 결과가 `SHOW AGENTS IN ACCOUNT` 와 **정확히 동일했다**(본 계정 2건). 그러면 이 SHOW가 "계정 전체 목록"인지 "SI 멤버십"인지 **구분되지 않는다** — 전자라면 가드는 **항상 skip 하는 무력 상태**이고, 신규 환경에서 agent가 **영구히 등록되지 않는다**. 그런데 겉보기 동작은 정상(`skipped` 반환)이다.

→ **변화를 일으켜 검증**: `DROP AGENT` 직후 해당 행 **소멸(0)** → 재-`ADD` 후 **복귀(1)** 확인(자기복원 블록). **멤버십 반영 확정**.

부수 발견: Snowflake Scripting `FOR rec IN (…) DO` 의 커서 변수(`rec.col`)는 **스크립팅 표현식에서 참조 불가**(`invalid identifier 'REC.AGENT_NAME'`) → agent 목록 루프 대신 **명시 분기**로 작성.

### 11-E. 🔴 YAML gotcha — plain scalar 안의 "콜론+공백"

agent spec 의 `description` 을 plain scalar 로 두면 본문의 `활성 지표: `·`차원: ` 등 **콜론+공백**을 YAML 파서가 매핑 구분자로 해석해 `agent spec is invalid` 로 실패한다. **에러 메시지에 원인·위치가 나오지 않는다.**

```yaml
# ❌ 실패
description: 예산 팩트(FBD). 활성 지표: 편성예산·집행예산. 차원: 연/월.
# ✅ 블록 스칼라
description: |-
  예산 팩트(FBD). 활성 지표: 편성예산·집행예산. 차원: 연/월.
# ✅ 인용 (본 프로젝트 09 [1-ALT] 방식)
description: "예산 팩트(FBD). 활성 지표: 편성예산·집행예산. 차원: 연/월."
```

본 세션 첫 `cortex_agent_save` 실패의 실제 원인이었다. 한국어 설명문은 `지표: `·`차원: `·`원천: ` 패턴이 잦아 **재발 확률이 높다**.

### 11-F. ⚠ 정본↔사본 drift 4회째 재발 — P23의 실효성 부족

정본 `cortex_project/*.agent.yaml` 2종은 갱신·배포했으나, 자기검토 중 **`08 §3.1`(AGENT_MEMBER 사본)이 순서9-F/9-G 이전 구버전**임을 발견했다(라벨화·원천·기본창 모두 미반영, 장문 서술형 판본). `08 §3.2`(OVERALL)는 동기화 상태였다.

- **이번 세션 변경분이 아닌 누적 부채**이며, 사본을 근거로 재배포하면 **라벨화·원천 규칙이 소실**된다 → 전면 교체는 별도 작업으로 분리하고 `08 §3.1` 에 🔴 경고 블록 + "정본 yaml 직독" 지시 명시.
- P23(정본 위상 준수) 기록 **직후에 또 발견**됐다는 점이 중요하다. **원칙 문서화만으로는 drift가 멈추지 않는다** → 기계적 대조(정본 yaml ↔ 08 사본 diff)를 DoD에 넣지 않으면 재발한다.

### 11-G. 신규 교훈 (P-시리즈)
- **P24 (instruction 개정은 *추가*보다 *제자리 교체*)**: 프롬프트에 **위임 선언**("이건 다른 계층이 담당하므로 여기서 다루지 않음")이 있으면, 그 주제의 규칙을 **덧붙이는 순간 자기모순**이 되고 LLM은 둘 중 하나를 **비결정적으로 무시**한다. 기존 줄을 찾아 개정하라. 또 신규 규칙을 넣기 전 **기존 instruction 전문을 읽어 중복을 제거**한다(중복은 토큰 낭비 + 우선순위 혼란). **정량 목표를 줄 때는 단위를 검증**하라 — "결과 행 수"는 그룹 카디널리티에 곱해지므로 시간 버킷 수와 다르다.
- **P25 (배포 ≠ 발행 · 그리고 spec ≠ 객체속성)**: Agent 는 `live`(편집)와 `is_default`(서비스) 버전이 분리된다. **저장 성공 메시지는 발행을 보장하지 않는다.** 변경 후 반드시 `SHOW VERSIONS` 로 `is_default=true` 행의 spec을 확인한다. 경로 선택: **최초 생성만 `CREATE OR REPLACE`(이력·GRANT·SI등록 파괴), 기존 agent 갱신은 `cortex_agent_deploy` 또는 순수 SQL**(결과 동일, 툴 의존 없음). `save` 단독으로 끝내지 말 것. 순수 SQL 경로는 **3단계가 아니라 5단계**다 — ① `ADD LIVE VERSION FROM LAST`(**선복구**: COMMIT·UI 발행이 live 를 소진하므로 기존 계정은 live 가 없을 수 있고, 없으면 `MODIFY LIVE VERSION` 이 `Live version is not found.` 로 실패) ② `MODIFY LIVE VERSION SET SPECIFICATION =` ③ `COMMIT`(**멱등 아님** — 무변경이어도 새 버전 생성) ④ `ADD LIVE VERSION FROM LAST`(재개용) ⑤ `SET COMMENT, PROFILE`. **⑤가 핵심 함정**: `COMMENT`·`PROFILE`(CoWork 표시명·색상)은 **spec 이 아니라 DDL 속성**이라 spec 을 갱신해도 바뀌지 않는다 → 구버전 표시명이 조용히 잔존한다. 역으로 `CREATE OR REPLACE` 에서는 매번 재지정해야 하며 누락 시 소실된다. **"어떤 속성이 spec 안에 있고 어떤 것이 객체에 있는지"를 먼저 구분**하라.
- **P26 (가드의 관측 대상을 변화로 검증)**: 멱등 가드는 "관측값이 실제 대상 상태를 반영한다"는 **전제 위에서만** 동작한다. 두 개의 서로 다른 관측(예: `SHOW … IN SNOWFLAKE INTELLIGENCE` vs `IN ACCOUNT`)이 **우연히 같은 결과**를 내면, 잘못된 대상을 보는 가드가 **정상처럼 보인다**(항상 skip = 무력). → **상태를 변화시켜(등록 해제 → 재등록) 관측값이 따라 움직이는지 확인**한다. 조회만으로 가드를 신뢰하지 말 것. P16(감사 오탐이 미탐보다 위험)의 가드 버전.
