## 23. ✅ 결정 — DEC-35: 코드→라벨 계층화를 **다원천 UNION 도메인**까지 확장 [2026-08-11 O58-D 초안 → O59 확정]

> 트리거 = 사용자 설계 요청 *"BRONZE의 코드 데이터를 SILVER, GOLD까지 가져오고, GOLD에서 코드 정의에 따른 라벨을 붙인 후, SV에서는 라벨 기준으로 구성해서 AGENT가 현업이 라벨로 쉽게 이해할 수 있도록"*.
> 🟢 **검토 결론 = 설계 방향은 옳다. 단 신규 설계가 아니라 `DEC-17`·`DEC-25` 의 미적용 도메인 확장이다.**
> 그러므로 **새 규약을 만들지 않는다** — 기존 결정을 그대로 적용하고, 기존 결정이 다루지 않은 **1개 공백(SV 층 노출 규약)** 만 신설한다.

### 23-A. 기존 결정이 이미 규정한 것 (재확인 — 재발명 금지)

|---|---|---|

### 23-C. 🆕 신설 결정 — 기존 결정이 다루지 않은 유일한 공백 = **SV 층 노출 규약**

DEC-25 15-D 는 **WIDE 층**에 「코드+라벨 병기」를 규정했으나 **SV 층 규약이 없다.** 그 공백 때문에 실제로 사고가 났다(§O58-C: `EVENT_KIND` 코드축만 노출하고 옆에 있던 `EVENT_KIND_NAME` 라벨축을 안 썼다 → COMMENT 에 *"업무 의미 미특정"* 이라 적는 **거짓 서술** 생산).

**DEC-35 = SV 층은 라벨축을 정본으로 노출하고 코드축을 보조로 병기한다.**

| 규칙 | 내용 |
|---|---|
| **R1 라벨축 우선** | 라벨 컬럼이 존재하면 **SV 는 라벨축을 노출하고 현업 동의어(`'회원상태'`·`'행사종류'`)를 라벨축에 붙인다.** 코드축에는 `'…코드'` 동의어만 준다 |
| **R2 코드축 병기 유지** | 코드축을 제거하지 않는다 — 필터 재현성·원천 대조·VQR 안정성에 필요하다(DEC-25 15-D 의 WIDE 논리를 SV 로 승계) |
| **R3 라벨 부재 시 명시** | 라벨이 없으면 COMMENT 에 **「라벨 미배선」을 명시**하고 의미 창작을 금지한다. 「미특정」이라 쓰기 전에 **옆 컬럼에 라벨이 있는지 먼저 확인**한다(O58-C 재발 방지) |
| **R4 다체계 축은 판별자 동반 필수** | 헛점 1 해소 전까지는 COMMENT 에 판별자 동반을 요구하는 **잠정 방어**를 두되, 이것을 해결로 적지 않는다(DEC-25 가 불충분하다고 판정했다) |
| **R5 COMMENT 에 폐기 리터럴 금지** | SV COMMENT 는 **LLM 입력**이다. 교정 문안에 폐기값을 인용하지 않는다(P174) |

### 23-E. 범위 실측 (규모)

- 🟢 라벨이 **이미 있는** 축: `DIM_MEMBER`/`DIM_MEMBER_CURRENT`(상태·구분·성별·지역·연령대·가입경로) · `DIM_PAYMENT`(`SETTLE_METHOD`·`PAYMENT_METHOD`·`FEE_TYPE`) · `DIM_CAMPAIGN`(DEC-17 4축) · `DIM_EVENT.EVENT_KIND_NAME` · `DIM_BUDGET_ITEM.BUDGET_CATEGORY`
- 🔴 라벨이 **아예 없는** 축(실측): `DIM_SERVICE` = `SERVICE_SK`·`CHANNEL`·`SUBTYPE` **3컬럼뿐 · 라벨 0** · `DIM_EVENT.EVENT_CATEGORY` · `FSE.SEND_STATUS` · `FEP.PART_STATUS`·`PART_PATH`·`PART_CHANNEL`
- ⇒ **결손이 무작위가 아니다** — 전부 **발송·행사 도메인**이고 그 두 도메인이 정확히 **다원천 UNION 으로 만들어진 도메인**이다. 원인이 하나이므로 처방도 하나로 묶인다.

### 23-G. 🆕 결정 — 결과코드는 **2축**이다 (O59 신규 발견 반영)

초안 §23-B 는 발송 결과를 **1축**으로 전제했다. **틀렸다.**

| 축 | 원천 컬럼 | 성격 | 종전 상태 |
|---|---|---|---|
| **A 채널 상태** | EMAIL `SNDNG_RST_CD` · MSG_AT `TRNSMS_STAT_CD` · SND `SND_YN` · PSTMTR 부재 | **원천별로 반드시 다르다** — 채널 추가 = 체계 추가 | SILVER 가 한 컬럼에 합침 = 헛점 1 의 원인 |
| **B 통신사 결과** | MSG_AT `TRNSMS_FAILR_CD_ID` · SND `CALL_STATUS` | 🟢 **conformed** — 두 채널이 **같은 코드공간**을 공유(실측) | 🔴 **SILVER 전파 0건** |

🟢 **축 B 의 다체계는 사전이 이미 명시 설계해 뒀다** — **`MS283` = `MS056`공통 · `MS057`알림톡 · `MS058`SMS · `MS059`MMS**.
즉 「메시지 타입이 판별자, 결과그룹은 4개」가 **원천 코드사전의 설계**이며 우리가 만들 규약이 아니다.
⇒ 축 B 는 **conformed 이므로 새 채널이 늘어도 코드공간이 유지된다** — 확장성 관점에서 축 A 보다 우월하다.
🔴 **사전 초과값 실재** → DEC-17-B 그대로 라벨 NULL + warn.

**컬럼 형상(결정)** — 축마다 3컬럼 세트:

```
GOLD.FACT_SERVICE_EVENT
  SEND_TYPE            판별자 (= SEND_CHANNEL · 기존 컬럼 · 신설 불요)
  SEND_STATUS          축A 코드 raw 유지            ← 원천 충실(DEC-25 15-A)
  SEND_STATUS_GROUP    축A 코드군 ID                ← 조인키(DEC-21 §11-C 복합키)
  SEND_STATUS_NAME     축A 라벨 (단일 컬럼)          ← SV 정본 노출축(DEC-35 R1)
  SEND_RESULT_CD       축B 코드 raw (신설)
  SEND_RESULT_GROUP    축B 코드군 ID = MS283 4종 (신설)
  SEND_RESULT_NAME     축B 라벨 (신설)
```

⚠️ **대가 명시**: `SEND_STATUS` 를 코드축으로 **단독 필터**하면 여전히 채널 간 오조인이 가능하다.
⇒ ① COMMENT 에 「`SEND_TYPE` 또는 `SEND_STATUS_GROUP` 동반 필수」 ② **게이트로 강제**(4단계 `sv_code_label_gate.py`).
🔴 이것은 O58-C 가 준 처방(*"CHANNEL 과 함께 보라"*)과 **문면은 같으나 위상이 다르다** — 그때는 **COMMENT 문구뿐**이었고, 지금은 **조인키 컬럼 + 게이트**가 구조로 받친다. DEC-25 P32 가 불충분하다고 한 것은 전자다.

### 23-H. 🟠 파생 — 우편 반송 결과 입고 요청 (신규)

`MS001`(정상·주소불명·이사·수취거절·수취인부재·반송함투입·폐문부재·수취인불명 8종)이 **사전에 실재**하는데 이를 담는 BRONZE 컬럼이 없다. 정본 **#87 실패수(명)** 이 우편에서 충족 불가한 원인이다.
⇒ **AD-5 와 같은 유형**(미적재가 아니라 **원천 항목 부재**) ⇒ 문서40 입고 요청 대상.

### 23-J. ✅ 실행 결정 4건 (2026-08-11 O59-N · 사용자 결정 · 1·2단계 착수분)

> §23-F 가 설계 결정을, 이 절이 **실행 결정**을 담는다. 실측 근거는 원장 `01_세션이력.md` §O59-N(R2-6).

| # | 결정 | 내용 | 파생 규약 |
|---|---|---|---|
| **1** | **범위 = 전량** | 축A 4채널 · 참여 3축 · 행사구분 1 · **축B 신설**까지 1·2단계에서 함께 한다 | 축B 는 SILVER 전파 0건이므로 **신규 배선**이다(기존 컬럼 라벨링과 성격이 다르다) |
| **2** | **C 등급 코드군 ID = 값을 채운다** | `*_GROUP` 조인키에 유력 코드군(`MS282`·`MS303`·`MS004`)을 넣고 COMMENT 에 **정황 등급(C)** 을 명시한다 | 🔴 **롤백 조건 명문화**: 현업 회신이 다르면 **해당 `*_GROUP` 값과 그 라벨을 되돌린다.** 조건 = 문서20 **§M-3** 회신. 되돌릴 때 손대는 곳 = SILVER 조인 `CD_ID` 리터럴 · GOLD `*_GROUP` 적재 · COMMENT 문안 |
| **3** | **사전 조인 불가 축은 라벨을 만들지 않는다** | `EMAIL {0,1}`·`SND {Y,N}` 은 **코드 값만 있고 사전 라벨이 없다**(코드군 배타 특정 불가 ⇒ `CRM_CODE` 에서 가져올 문자열이 없다). 「성공/실패」는 **원천 교차로 얻은 우리 해석**이므로 라벨 컬럼은 **NULL 유지** | DEC-17-B·DEC-25 그대로 준수(하드코딩 `CASE` 예외를 **확장하지 않는다**) · 🆕 문서20 **§M-4** 로 현업 확인 이관. 라벨 정보가 들어오면 **조인으로** 채운다 |
| **4** | **`MS304` 영문 라벨 그대로 노출** | `110`=`Success` … `220`=`5_step_fail` 를 사전 값 그대로 적재한다 | DEC-25(라벨 값 = `CRM_CODE` 조인) 준수 · COMMENT 에 **「사전 라벨이 영문 · 현업 한글 표기 회신 대기(문서20 §M-1)」** 명시 |

🟢 **축B 조인 방식 — 하드코딩이 아니다**(실측 확정): `MS056`~`MS059` 4그룹에 걸쳐 **코드값 중복 0**이므로
`ON d.CD_ID IN ('MS056','MS057','MS058','MS059') AND d.DTL_CD_ID = <코드>` 로 조인하면 **매칭된 `CD_ID` 자체가 코드군**이 된다.
⇒ `SEND_RESULT_GROUP` 은 리터럴이 아니라 **조인 결과에서 얻는다**(P31 준수 · 채널이 늘어도 불변).
⚠️ 이 배타성은 **현재 사전 상태의 실측**이다 — 사전에 값이 추가되면 깨진다 ⇒ **게이트로 재검**한다.
