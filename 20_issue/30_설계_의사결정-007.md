## 23. ✅ 결정 — DEC-35: 코드→라벨 계층화를 **다원천 UNION 도메인**까지 확장 [2026-08-11 O58-D 초안 → O59 확정]

> 트리거 = 사용자 설계 요청 *"BRONZE의 코드 데이터를 SILVER, GOLD까지 가져오고, GOLD에서 코드 정의에 따른 라벨을 붙인 후, SV에서는 라벨 기준으로 구성해서 AGENT가 현업이 라벨로 쉽게 이해할 수 있도록"*.
> 🟢 **검토 결론 = 설계 방향은 옳다. 단 신규 설계가 아니라 `DEC-17`·`DEC-25` 의 미적용 도메인 확장이다.**
> 그러므로 **새 규약을 만들지 않는다** — 기존 결정을 그대로 적용하고, 기존 결정이 다루지 않은 **1개 공백(SV 층 노출 규약)** 만 신설한다.

### 23-A. 기존 결정이 이미 규정한 것 (재확인 — 재발명 금지)

|---|---|---|

### 23-C. 🆕 신설 결정 — 기존 결정이 다루지 않은 유일한 공백 = **SV 층 노출 규약**

DEC-25 15-D 는 **WIDE 층**에 「코드+라벨 병기」를 규정했으나 **SV 층 규약이 없다.** 그 공백 때문에 실제로 사고가 났다(§O58-C: `EVENT_KIND` 코드축만 노출하고 옆에 있던 `EVENT_KIND_NAME` 라벨축을 안 썼다 → COMMENT 에 *"업무 의미 미특정"* 이라 적는 **거짓 서술** 생산).

**DEC-35 = SV 층은 라벨축을 정본으로 노출하고 코드축을 보조로 병기한다.**

| 규칙 | 내용 |
|---|---|
| **R1 라벨축 우선** | 라벨 컬럼이 존재하면 **SV 는 라벨축을 노출하고 현업 동의어(`'회원상태'`·`'행사종류'`)를 라벨축에 붙인다.** 코드축에는 `'…코드'` 동의어만 준다 |
| **R2 코드축 병기 유지** | 코드축을 제거하지 않는다 — 필터 재현성·원천 대조·VQR 안정성에 필요하다(DEC-25 15-D 의 WIDE 논리를 SV 로 승계) |
| **R3 라벨 부재 시 명시** | 라벨이 없으면 COMMENT 에 **「라벨 미배선」을 명시**하고 의미 창작을 금지한다. 「미특정」이라 쓰기 전에 **옆 컬럼에 라벨이 있는지 먼저 확인**한다(O58-C 재발 방지) |
| **R4 다체계 축은 판별자 동반 필수** | 헛점 1 해소 전까지는 COMMENT 에 판별자 동반을 요구하는 **잠정 방어**를 두되, 이것을 해결로 적지 않는다(DEC-25 가 불충분하다고 판정했다) |
| **R5 COMMENT 에 폐기 리터럴 금지** | SV COMMENT 는 **LLM 입력**이다. 교정 문안에 폐기값을 인용하지 않는다(P174) |

### 23-E. 범위 실측 (규모)

- 🟢 라벨이 **이미 있는** 축: `DIM_MEMBER`/`DIM_MEMBER_CURRENT`(상태·구분·성별·지역·연령대·가입경로) · `DIM_PAYMENT`(`SETTLE_METHOD`·`PAYMENT_METHOD`·`FEE_TYPE`) · `DIM_CAMPAIGN`(DEC-17 4축) · `DIM_EVENT.EVENT_KIND_NAME` · `DIM_BUDGET_ITEM.BUDGET_CATEGORY`
- 🔴 라벨이 **아예 없는** 축(실측): `DIM_SERVICE` = `SERVICE_SK`·`CHANNEL`·`SUBTYPE` **3컬럼뿐 · 라벨 0** · `DIM_EVENT.EVENT_CATEGORY` · `FSE.SEND_STATUS` · `FEP.PART_STATUS`·`PART_PATH`·`PART_CHANNEL`
- ⇒ **결손이 무작위가 아니다** — 전부 **발송·행사 도메인**이고 그 두 도메인이 정확히 **다원천 UNION 으로 만들어진 도메인**이다. 원인이 하나이므로 처방도 하나로 묶인다.

### 23-G. 🆕 결정 — 결과코드는 **2축**이다 (O59 신규 발견 반영)

초안 §23-B 는 발송 결과를 **1축**으로 전제했다. **틀렸다.**

| 축 | 원천 컬럼 | 성격 | 종전 상태 |
|---|---|---|---|

4. **범위 대비 이득 0.** 리네임 대상 = SILVER 5 + GOLD ref 4 + `_ga4_schema.yml` + `08` DDL +
   `09` 적재쿼리 + 설계문서 4종 + 이슈 ID `GA4-PK-1`·`GA4-LEN-1` + SV/Agent COMMENT.

🟢 **`BRONZE_CRM` ↔ `CRM_*` 가 같아 보이는 것은 우연이다** — CRM 은 시스템명과 도메인명이 같은
단어다. GA4/BigQuery 가 둘이 갈라지는 유일한 사례이고 그래서 이 규약이 여기서만 눈에 띈다.

### 25-D. 예외를 인정한 근거 (사용자 결정 = 「기반 테이블만 BIGQUERY_REFINED_DATA」)

기반 테이블은 **도메인 해석을 하지 않는다** — `event_params` FLATTEN·VARIANT 경로 추출·컬럼
승격만 하고 업무 의미를 부여하지 않는다. 즉 그 내용은 「BigQuery export 를 평탄화한 것」이
전부이고, 그것이 **원천 사실**이다. 도메인 해석은 그 위의 `GA4_*` 5종이 담당한다.

⚠️ **이 예외를 확대하지 말 것** — 기반 테이블이 아닌 새 SILVER 객체는 `GA4_*`/`CRM_*` 를 쓴다.
⚠️ `_REFINED_DATA` 접미는 「레이어명 중복」(SILVER 전체가 refined)이라는 지적이 있었고
   사용자 결정으로 그대로 채택했다 — 다른 기반 테이블이 생기면 접미 규칙을 여기서 정할 것.

### 26-A. 무엇을 정했나

GA4 평탄화 산출물의 **자리를 `GN_DW.SILVER` 로 확정**한다. 다음주 도입되는 Python 저장 프로시저가

⇒ **`BRONZE_BIGQUERY` 는 GA4 계열의 필수 경유지가 아니다**(사용자 발언 「BRONZE_BIGQUERY 는 임시」와 정합).

### 26-B. 개정되는 원칙 — 이것이 이 결정의 비용이다

🔴 `04_silver_design/00_README:51` `P2`(`SERVING→GOLD→SILVER→BRONZE`)의 **최하층이 GA4 계열에서 사라진다.**
종전 원칙은 「모든 SILVER 는 BRONZE 를 원천으로 한다」였고, 이 결정으로 **GA4 계열에 한해 그 전제가 깨진다.**

  ⇒ 「SILVER 원천 겸용」은 **전면 허용이 아니라 명시적 예외 목록**이다.
· 🔴 **예외를 확대하려면 이 절에 행을 추가하고 근거를 적는다.** 적지 않은 확대는 무효로 취급한다
