## 15. ✅ 결정 — DEC-25: 컬럼 명명 = 코드는 BRONZE 원천명 · 라벨은 분석용어 [2026-08-03 O26]

### 15-A. 결정

| 계층 | 규칙 | 예 |
|---|---|---|
| **코드 컬럼** | **BRONZE 원천명 그대로** | `SEX` · `MBER_STAT_CD` · `MBER_DIV_CD` · `JOIN_PATH_CD` · `DVLP_DIV_CD` |
| **코드 값** | **원천 raw 무변환** — 축약·재부호화 금지 | `SEX` = CM013 `0~8`(종전 M/F/U 축약 폐기) |
| **라벨 컬럼** | **분석 용어명 유지** | `GENDER_NAME` · `MEMBER_STATUS_NAME` · `MEMBER_TYPE_NAME` · `ENROLL_PATH_NAME` · `REGION` · `AGE_BAND` |

| **동명이의** | **원천 테이블 변별 토큰을 접두** | `PRCS_STAT_CD` → `MBRFEE_PRCS_STAT_CD`(회비) / `PSTMTR_PRCS_STAT_CD`(발송) |

### 15-B. 근거

- **신개념 도입이 아니다.** BRONZE 가 **이미 수식어 접두 관례**를 쓴다 — `ACT_`/`ACMSLT_`/`REGIST_DEPT_CD` · `EMAIL_`/`MOBLPHON_`/`ETC_CTTPC_STAT_CD` · `TSTM_`/`ETC_TSTM_DIV_CD`. 동명이의 접두는 **원천 관례의 일관 적용**이다. 현업이 아직 BRONZE 를 직접 조회하는 전환기이므로 이 점이 결정적이다(§12-F).
- **라벨을 사전 조인으로 만들면 사전 변경이 자동 반영된다.** 하드코딩은 조용히 갈라지고 `ELSE` 절이 도메인 확장을 은폐한다(**P31**).
- **동명이의 실측은 정확히 2건**(G5, 문서10 §13-A). 광범위한 개명이 아니라 **최소 개입**이다.

### 15-C. 동명이의 해법 선택 규칙 (P32)

**개명과 값 교정 중 무엇을 할지는 "양쪽이 다 원천 충실한가"로 결정한다.**

| 사례 | 판정 | 해법 |
|---|---|---|
| `PRCS_STAT_CD` (R,F,S vs 0,1) | **둘 다 원천 정당** — 서로 다른 두 원천의 서로 다른 코드체계 | **개명**(변별 토큰) |
| `SEX` (M/F/U vs 0~8) | **한쪽이 원천 파괴** — SILVER 가 CM013 8종을 3종으로 축약 | **값 복원**(개명 아님) |

🔴 **개명으로 파괴를 덮으면 파괴가 영구화된다.** 그리고 어느 경우든 **`accepted_values` 가드는 오조인을 막지 못한다** — 가드는 값 도메인만 고정하고, 같은 이름의 다른 체계를 조인하는 실수는 통과시킨다. 동명이의는 **개명으로만** 해소된다.

### 15-D. 구현 시 준수 사항

- 🔴 **`CREATE OR REPLACE` 금지** — `ALTER TABLE … RENAME COLUMN` / `ADD COLUMN` 을 쓴다. FK·GRANT 가 파괴된다(SILVER 구조 소유주 = `08_SILVER_테이블DDL`, §11-A 와 동일 규칙).
- 🔴 개명 시 **소비처 전수 grep 필수** — WIDE·SV·`DIM_MEMBER_CURRENT`·schema.yml. P17(개명 일괄치환이 동명 타컬럼을 오염) 재발 주의.
- 🔴 SV 는 `05_SV_DDL.sql`(정본) 수정 후 **`GN_DW_ADMIN` 역할로 실행** + **§7 GRANT 재실행**. `CREATE OR REPLACE SEMANTIC VIEW` 가 GRANT 를 파괴한다 — 해당 파일이 이를 **8~9행 헤더와 §7 서두(519~520행)** 에서 경고한다. 별개로 **15~16행**은 *역할·소유권* 경고다(`GN_DW_ADMIN` 아닌 역할로 만들면 이후 재배포가 권한 오류로 막힘 · 복구 SQL = §8-11 주석). ⚠️2026-08-03 정정: 종전 이 줄이 "15~16행이 GRANT 파괴를 경고한다"고 적었으나 **행 지목이 틀렸다**(15~16행은 소유권 경고).
- ⚠️ WIDE 는 **코드+라벨 병기**로 노출한다(코드만 노출하면 현업이 라벨을 못 얻고, 라벨만 노출하면 조인·필터가 불가).
- 🔴 **COMMENT 는 별도 산출물이다 — 개명이 데려오지 않는다 (P33)**. `ALTER TABLE RENAME COLUMN` 은 **구 COMMENT 를 승계**하고, `CREATE OR REPLACE` 금지 규칙 때문에 **DDL 정본을 고쳐도 물리에 전파되지 않는다**. 실제로 O26 개명 8건이 구 COMMENT(*"F→여성"*, 존재하지 않는 `DIM_MEMBER.GENDER` 참조)를 그대로 물고 있었고, 후속 검토에서 **물리 16컬럼**(GOLD 테이블 2 · WIDE 뷰 10 · SILVER 4)을 교정했다(문서10 §13-F-2). 개명·값체계 변경의 **DoD 3종**:
  1. **물리 `ALTER … COMMENT`** 실행
  2. **소유 산출물 동기화** — 뷰는 모델 `post_hook`(물리만 고치면 **다음 빌드가 되돌린다**), 테이블은 DDL 정본
  3. **거짓이 된 기존 경고문 회수** — 동명이의를 해소했는데 "비교·UNION 금지" 경고가 남으면 **정상 조인을 막는다**
  → **완료 판정은 문서가 아니라 `INFORMATION_SCHEMA.COLUMNS` 스캔**(구 컬럼명·구 값체계 문자열 검색)으로 한다. COMMENT 는 SV `description` 으로 소비되므로 낡은 COMMENT = **0행 무증상 오답**(AD-4·P19).

## 16. ✅ 결정 — DEC-26: 정본 컬럼정의서의 코드 관련 위상을 참고본으로 강등 [2026-08-03]

> 진단 정본 = 문서10 **§13-E**. **DEC-16(정본 위상표)의 개정**을 포함한다.
> 계기 = 사용자 판정: *"컬럼 정의서가 stale 본이고, 현업도 갱신 의지가 없다. 문서에 없는 코드 그룹은 앞으로 코드 정의 테이블과 실제 적재 데이터를 비교하면서 맞춰갈 수밖에 없다."*

### 16-A. 결정

**컬럼정의서의 코드 관련 기술 전체를 참고본으로 강등**한다. 문서 전체가 아니라 **틀린 축에 한정**한다.

| 대상 | 위상 | 정본 |
|---|---|---|
| 컬럼 존재 여부 | 🟢 정본 유지 | 컬럼정의서 (+ `INFORMATION_SCHEMA` 교차) |
| **비고·특이사항·경고문** | 🟢 **정본 유지** | 컬럼정의서 |
| 코드그룹ID 지정 | ⚠️ **참고본** | `CRM_CODE` × 실적재 distinct 대조 |
| 코드값 정의·열거 | ⚠️ **참고본** | 실적재 distinct |
| 라벨 정의 | ⚠️ **참고본** | `CRM_CODE.DTL_CD_NM` |
| 지표 정의·값 열거 | 🟢 정본 유지 | 지표사전(공#) |

### 16-B. 근거 — 문서가 불완전할 뿐 아니라 **틀렸다**

| 유형 | 실측 사례 |
|---|---|
| **누락** | **CM017** — 실제 성별 라벨축인데 어떤 컬럼에도 지정 안 됨(0건) |
| **오지정** | `RQEST_RST_CD`→**PM021**: 사전 코드 **1개** vs 원천 **101종**(PM018 이 41 적중) |
| **오지정** | `IRSD.AREA_CD`→**CM011**(정식명): 정본 공#131 지역 정의는 **약칭**이라 CM018 이 맞음 |
| **이중지정** | `CARD_DIV_CD`→**PM044/PM052** |
| **갱신 중단** | 현업 갱신 의지 없음 확인(2026-08-03) → **시간이 지나도 해소되지 않는다** |

🔴 이 오지정들은 관문측정 G1 의 **모집단(85건) 자체를 흔든다** — G2·G3 수치도 같은 기반이다(문서10 §13-A).

🟢 **비고를 정본으로 남긴 이유**: O24(`RDCAMT_YN`)와 O26(`SEX`) **두 번 모두 비고가 옳았고 우리가 무시했다**. `SEX` 비고는 *"컬럼설명은 성별이나 성별만으로는 사용하지는 않음"* 이라고 명시하고 있었다(**P30**).

### 16-C. 운영 규약 (P29) — 코드그룹 확정 3단계

문서에 없거나 문서와 어긋나는 코드그룹은 **추정하지 않고 대조로 확정**한다.

1. **3원 대조** — 원천 코드사전(`CRM_CODE`) × 실적재 `distinct` × 지표사전 값정의
2. **판정 근거를 COMMENT 에 명시** — *무엇과 대조해 무엇으로 정했는지*. 근거를 남기지 않으면 다음 세션이 같은 판단을 다시 하거나 **다르게** 한다
3. **`accepted_values` 가드로 도메인 고정** — 실측 distinct 전량 열거(폐지코드 포함)

⚠️ **`USE_YN='Y'` 를 필터로 쓰지 않는다.** 폐지코드가 실적재에 남아 있어(`STOP_REASON` 20종 중 6종·366행) 필터를 걸면 **라벨이 조용히 사라진다**. `USE_YN` 은 **관측 축**으로만 쓴다.

- **최초 적용례 = CM017 채택**. 근거는 '정본 지정'이 아니라 **'정본 공#130 값정의와 5종 정확 일치'** 이며, 이 판단 경로를 COMMENT 에 남겼다. 현업 확인은 문서20 §H 로 **병렬 진행**하되, 회신 없이도 진행 가능한 것이 이 규약의 요점이다.
- **선례로 재판정할 후보**: `SVL-1`(`SNDNG_TY_CD` 값 `0` 미존재) · `SVL-2`(`SNDNG_RST_CD` 의 `0`/`N`/`Y` 미매핑) — 종전 "현업 회신 대기"였으나 본 규약으로 **대조 확정 가능**(문서10 §13-I #6).

### 16-D. 파생 효과 — 대조 스캔이 **필수**가 된다

문서10 **§12-H #8**(P27 정례화: 전 코드성 컬럼 ↔ `CRM_CODE` 도메인 대조 스캔)이 **선택 과제에서 필수로 승격**된다. 컬럼정의서가 코드 정본이 아니게 된 이상, **대조 스캔이 코드 정본을 확정하는 유일한 수단**이다. 이것이 없으면 신규 코드 컬럼을 배선할 때마다 근거 없는 추정으로 되돌아간다.

## 17. ✅ 결정 — DEC-27: 분석가 직접조회(GOLD-only) 대응 — 안전 진입점 신설 + '미상' 정상화 [2026-08-03]

> 진단 정본 = 문서10 §13-F-4(개념 부재 오라벨) · §13-F-5(팬아웃).

### 17-A. 🔴 최우선 위험 — `DIM_MEMBER` SCD2 팬아웃 (실증)

회원 관련 FACT 4개(`FACT_MEMBER_MONTHLY`·`FACT_MEMBER_EVENT`·`FACT_EVENT_PARTICIPATION`·`FACT_SERVICE_EVENT`)가 **전부 `MEMBER_DK` 로 조인**하는데 `DIM_MEMBER` 는 SCD2다 — 회원 1명 = **평균 4.50행**(최대 218 · 56.5%가 다버전).

| 실측(202606 단월) | 값 |
|---|---:|
| `FACT_MEMBER_MONTHLY` 원 행수 | 734,521 |
| `join DIM_MEMBER using (MEMBER_DK)` | **2,645,714 (3.60배)** |
| `+ where IS_CURRENT` | 734,521 (일치 ✅) |
| 납입회비 실제 | 17,132,725,212 |
| 순진한 조인 후 | **50,747,852,886 (2.96배 과대)** |

🔴 그런데 **GOLD 에는 비-WIDE 뷰가 0개**였고 안전한 현재본은 `SERVING` 스키마에만 있었다 — GOLD-only 분석가에게는 **안전한 기본값이 아예 없었다.** 에러도 경고도 없이 3배 과대계상되는 경로다.

### 17-B. '미상' 정상화 — 개념 부재와 결측을 분리한다

**원인**: `COALESCE(라벨, '미상')` 이 **개념 부재를 결측으로 뭉갰다.** 일시회원(ONCE)은 원천에 회원상태·가입경로가 **없다**.

### 18-D. 판정 순서 규칙 (P37 — §17-C 규칙의 선행 단계 신설)

§17-C 의 사용자 확정 규칙(①같은 역할 컬럼 有→DROP ②BRONZE 근거 有→채움 ③둘 다 아니면 DROP)에 **grain 판정을 ② 앞에 삽입**한다.

```
① 같은 테이블에 같은 역할 컬럼이 있는가        → 있으면 DROP
②-NEW 대상 grain 에 함수종속하는가             → 아니면 DROP (원천이 있어도)
③ BRONZE/SILVER 근거가 있는가                  → 있으면 채움 (커버리지 병기)

⑤ 위 어디에도 안 걸리면 DROP
```

**근거**: 본 세션 B군이 ②에서 걸렸다. ②가 없으면 "원천이 실재하므로 채움"(P14 논리)으로 잘못 진행된다. 반대로 `AGE_BAND` 는 ②를 통과하고 ④도 **불요**(원천이 이미 구간화)여서 즉시 ③ 이다.

### 18-E. 실행 순서 (DEC-27 §17-C 와 통합 — `dbt build` 는 사용자 실행)

### 19-B. 🔴 선행 지목의 오류가 결정으로 이어진 경로

`99_NEXT_SESSION.md` §3 과 문서10 §14-H·§14-I 는 **결론(두 체계 혼입 · 96.6% 소실 · 단위 오류)은 전부 옳았다.** 틀린 것은 **조치안의 세부 지정**이었고, 그대로 실행하면 다음이 발생했다:

- 조치안 ②를 문면대로 하면 → 고아 23.2% 에서 **판별 실패**(결정 3으로 교체)

📌 **일반 규칙으로 승격**: 인수인계 문서의 조치안은 **결론과 별개로 재검증한다.** 결론은 실측에 근거하지만 **조치안은 그 시점의 추론**이며, 특히 *"어느 컬럼을 쓰라"* 는 지정은 §18-D ①(같은 역할 컬럼 확인)·`INFORMATION_SCHEMA` 실재 확인을 통과해야 한다. 미이행 시 P38(결손 창작)의 변형인 **"조치 창작"** 이 된다.

### 19-C. 구현 시 준수 사항

- 🟢 **GOLD 팩트 테이블 COMMENT 는 영구적이다** — `gold.fact` 는 `incremental + append + pre-hook TRUNCATE` 이고 **COMMENT 를 세팅하는 `post_hook` 이 없다**. `TRUNCATE` 는 COMMENT 를 지우지 않는다(본 세션 검증). 따라서 `ALTER … COMMENT` 만으로 충분하며 재빌드 불요.
- 🔴 **WIDE 뷰는 반대다** — `post_hook` 이 소유주이므로 **모델 파일 수정이 필수**다. 물리 ALTER 는 보조 수단.
- ⚠️ **`post_hook` 문자열에 이중인용부호를 넣지 말 것** — Jinja 문자열 이스케이프가 얽힌다. 본 세션은 `\"…\"` 를 **`「…」`** 로 교체해 회피했고 `dbt compile` 로 검증했다.
- 🔴 **완료 판정은 `INFORMATION_SCHEMA` 스캔**(P33) — 본 세션 결과 FEP 17/17 · WIDE_EP 16/16 · `DURATION_SEC` 3/3. 거짓 경고문 스캔(`온라인`) 잔존 1건은 **교정문이 구 문구를 인용해 설명하는 의도적 이력 서술**이다(§13-F-2 ④ 선례).
- 🔴 **정본 DDL 동기화 필수**(P33 ②) — GOLD 테이블 COMMENT 의 소유 산출물은 `06_DDL.sql` 이다. 물리만 고치면 다음 `CREATE OR REPLACE TABLE` 실행 시 되돌아간다.

| 발송구분 **無** | 1,612,690 | 30,159,195 | 18.7명 |
| **커버리지** | 0.106% | **21.58%** | **260배 차** |

→ 발송구분이 붙는 요청은 **대량 발송**이다. 요청 grain 분모는 이 축의 업무 가치를 **약 200배 과소평가**했다. 🔴 **분모를 잘못 고르면 "지어내기"가 아니라 "지워버리기"가 발생한다** — 실재하는 축을 저가치로 오판해 폐기 후보로 만든다.

### 20-C. ⚠️ 자기정정 — 직전 세션의 `*_TIMES` 권고가 틀렸다

직전 세션(2026-08-04 전반)에 나는 문서10 §15-G #10 · `FEP` COMMENT · 핸드오프에 *"`PARTICIPATION_TIMES`·`CUM_APPLY_TIMES` 는 `PARTCPT_SEQ`(100% 채움) 기반이라 **O28 무관하게 배선 가능**"* 이라고 적었다. **이것은 §18-D ② 를 스스로 건너뛴 오류다.**

실측: 참여행 grain 에 회원/쌍 단위 카운트를 얹으면 `SUM` 이 **168.0배**((행사,회원) 기준) · **458.5배**(회원 기준) 과대계상된다(최대 18,755행사/회원).

⚠️ 다만 **부가산성만이 이유가 아니다.** 0/1 플래그로 인코딩하면 가산성은 확보된다. 진짜 차단 사유는 **정의 부재**다 — `*_CNT`(인원)와 `*_TIMES`(횟수)의 구분이 지표용어사전에 *"숫자"* 로만 있고 **산식·구분 기준이 없다**. 내가 정하면 O26(성별 하드코딩)과 같은 **정의 창작**이다.
→ **배선 보류 + 현업 확인 항목 신설**(문서20 §K). `RECRUIT_CNT` 를 grain 으로 걸러낸 바로 그 세션에서 같은 함정에 걸렸다는 점이 P45 의 근거다.

### 20-D. 아키텍트 관점 재검토 결과 (실행 전 게이트)

| 검토 축 | 판정 |
|---|---|
| 계층 차원 모델링 | 🟢 대/중/소 3단을 **한 차원에 평탄화**(Kimball 표준). 스노플레이크 분해 불요 |
| 자연키 선택 | 🟢 **전체 경로**여야 한다 — 중분류 코드 단독은 코드 16종 vs 라벨 26종으로 **모호**하다. (TOP,MID,BOT) 65 = 라벨결합 65 · NULL 0 ⇒ 라벨 100% 함수종속 |
| 기존 적재 보호 | 🟢 `DIM_SERVICE`·`SERVICE_SK` 불변. FSE 는 **컬럼 추가만** |
| 센티넬 규약 | 🟢 `SEND_TYPE_SK=0` + `'(미매핑)'` — 프로젝트 규약 준수. 미매칭 78.42% 가 조인에서 유실되지 않는다 |
| 코드+라벨 병기 | 🟢 DEC-25 준수 — `SEND_GBN_*`(원천명) + `SEND_TYPE_L/M/S`(분석 라벨) 병설 |
| 🔴 **파괴적 의존성** | 🔴 **DROP 대상의 하류 소비처를 전수 조사해야 한다** — `WIDE_EVENT_PARTICIPATION`(`RECRUIT_CNT` select+post_hook) · `WIDE_SERVICE_EVENT`(`SEND_TYPE_L/M/S` select+post_hook) 4곳 발견. 미수정 시 **다음 빌드가 실패**한다 → 동시 수정 완료 |

📌 **재검토에서 실제로 걸러낸 것** = ① `*_TIMES` 배선(§20-C) ② WIDE 4곳 파괴 의존성 ③ `TRY_TO_TIME` 함정(아래). 재검토 없이 실행하면 빌드 실패 + 무성 오답이 발생했다.

### 20-E. 구현 시 준수 사항

- 🔴 **`TRY_TO_TIME` 을 O29 파싱에 쓰지 말 것** — 실측 `TRY_TO_TIME('30000000')` 이 실패하지 않고 **`05:20:00`(19,200초)** 를 반환한다. 단위 미확정 숫자를 그럴듯한 초수로 조용히 바꿔 **O29 와 동일한 무성 오답을 재도입**한다. 반드시 `LIKE '%:%'` 로 표기를 먼저 가른 뒤 `SPLIT_PART` 로 파싱한다.
- 🔴 **O29 숫자 3종(30/60/90 ×10⁶)은 NULL 을 유지**한다 — µs 해석은 추론이므로 현업 확인 전 금지(문서20 §J). 파싱 후 컬럼에 **초 단위와 µs 단위가 섞이면 지금보다 나쁘다**(현재는 최소한 단위가 일관되게 틀려 있다).
- 🔴 `DIM_SEND_TYPE` 은 신규 객체이므로 `CREATE` 가 정상이나, **기존 테이블은 `ALTER` 만** 쓴다(FK·GRANT 파괴 금지).
- ⚠️ `PARTCPT_SEQ` 는 **식별자 전용**이다 — 원천에 음수 20,844행(765행사·12,333회원)과 `INT_MIN`(-2147483647) 1행이 있어 **정렬·범위 조건에 쓰면 안 된다**.
- ⚠️ `DIM_EVENT.RECRUIT_HEADCOUNT` 는 **행사 grain 값**이다 — WIDE 에서 참여행마다 반복되므로 `SUM` 금지(행사 단위 `MAX`/평균 또는 DISTINCT 행사 기준).
- 🟢 실행 순서 = `03_top-down_gold/DEC30_STRUCTURE_ALTER.sql` §1~§5 → **사용자 `dbt build`** → §6 검증 9종.
