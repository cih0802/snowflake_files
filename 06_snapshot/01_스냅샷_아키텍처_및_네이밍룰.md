# [GN_DW] dbt Snapshot 아키텍처 및 표준 네이밍 규칙 정의서

> **문서 목적**: 원천 마스터의 덮어쓰기(Overwrite)로 인한 과거 시점 리포팅 왜곡을 방지하고, 시점별 변경 이력(SCD Type 2)을 안정적으로 추적하기 위한 `SNAPSHOT` 스키마 아키텍처 및 테이블 네이밍 규칙을 정의합니다.

---

## 1. 스냅샷 아키텍처 개요

### 1-1. 도입 배경 및 목적
* **문제점**: BRONZE 원천 마스터(캠페인, 부서, 사업 등)는 변경 이력(History) 없이 최신 데이터로 계속 덮어써집니다(SCD Type 1).
* **파급 효과**: ~~2021년 가입 회원의 획득 캠페인명이 2025년 개칭된 최신 명칭으로 소급 변경되어 과거 시점 코호트/실적 보고서가 왜곡됩니다.~~ ➔ 🔴 **[2026-09-11 한정 표기]** dbt snapshot은 최초 실행(2026-09-09) 이후의 변경만 감지하므로, 과거 이미 덮어써진 이력을 소급 복구하지 못합니다. 따라서 목적은 **과거 왜곡 복원이 아니라 향후 발생하는 변경 이력의 왜곡 방지**입니다.
* **해결책**: `dbt snapshot`을 통해 변경분만 1행씩 유효기간(`dbt_valid_from` ~ `dbt_valid_to`)과 함께 영구 누적(SCD Type 2)하고, 향후 변경 발생 시점의 유효 명칭을 Point-in-Time Join으로 정확히 복원할 수 있는 기반을 구축합니다.

### 1-2. 전체 데이터 파이프라인 흐름 (선이력·후배선 아키텍처)

```
[BRONZE 원천 마스터] (SCD Type 1: 최신값)
       │
       ├─▶ (dbt snapshot 일배치: 변경분 이력 독립 누적) ➔ [SNAPSHOT 스키마] (SCD2 이력 보존 · 소비처 0 대기)
       │
       ▼ (dbt run: 정제 및 변환)
[SILVER 계층 모델]  (CRM_MEMBER_DEV, CRM_ORG 등)
       │
       ▼ (dbt run: 최종 분석 마트 배포)
[GOLD 차원/팩트]    (DIM_MEMBER, DIM_ORG, FACT_MEMBER_EVENT 등)
```

> 🔴 **스냅샷과 GOLD 빌드의 분리**: 스냅샷은 이력을 먼저 축적(선이력)하고, 다운스트림 마트 배선은 현업 요구 및 이력 형성 확인 후 추가(후배선)합니다.

## 2. SNAPSHOT 전용 스키마 정책

### 2-1. 왜 별도 `SNAPSHOT` 스키마로 분리하는가?
1. **생명주기(Lifecycle) 격리**:
   * `SILVER`, `GOLD`는 로직 변경 시 언제든 Truncate-Insert(전체 재적재)되는 가변 영역입니다.
   * `SNAPSHOT`은 과거 변경 이력이 영구 누적되는 불변 보존 영역이므로, 전체 재적재 배치 시 삭제되지 않도록 물리적 스키마를 분리합니다.
2. **운영 실수 방지**:
   * 일괄 Truncate/Drop 스크립트 실행 사고로부터 과거 스냅샷 데이터를 안전하게 보호합니다.

### 2-2. 스토리지 및 컴퓨팅 비용
* **스토리지 비용 ($0에 수렴)**: 마스터 테이블은 수십 KB ~ 수 MB 수준이며, 변경된 행만 1행씩 추가되므로 Snowflake 스토리지 비용 증가는 월 수십 원 내외로 극히 미미합니다.
* **컴퓨팅 비용**: 작은 용량의 마스터 비교는 X-Small 웨어하우스로 1~3초 내에 완료됩니다.

### 2-3. 대안 설계 검토 — Stream / BRONZE 전량 이력화 미채택 근거 (비교 분석)
원천 변경 감지 대안으로 제안된 "RAW 적재 ➔ Snowflake Stream 감지 ➔ BRONZE Delta 누적" 방식은 다음 6가지 기술적 사유로 공식 기각되었습니다:
1. **Stream은 오프셋 포인터일 뿐이다**: Stream 자체는 데이터를 보존하지 않으며, 소비 DML이 성공하면 오프셋이 전진하여 과거 변경분을 다시 조회할 수 없습니다.
2. **보존기간(1일) 만료 시 조용한 유실(Stale)**: 계정의 `DATA_RETENTION_TIME_IN_DAYS=1`(기본값) 환경에서 Task가 하루 이상 장애로 멈추면 Stream이 `stale` 상태가 되어 미소비 변경분이 영구 소실됩니다. 반면 `dbt snapshot`은 전량 대조(Full Comparison) 기반이므로 배치 재개 시 자동 복구(Self-healing)됩니다.
3. **Net 변경만 전달하여 중간 버전 소실**: 두 오프셋 사이에 같은 행이 여러 번 바뀌면 최종 상태만 감지되어 중간 SCD2 체인이 깨집니다.
4. **Point-in-Time 조인 유효구간 부재**: Stream 출력에는 `dbt_valid_from ~ to` 구간이 없어 다운스트림마다 `LEAD()` 윈도우 함수를 수제로 개발해야 합니다.
5. **다운스트림 조인 팬아웃 위험 (Foot-gun)**: BRONZE가 이력 테이블이 되면 SILVER/GOLD의 모든 쿼리가 `QUALIFY ROW_NUMBER() = 1`을 강제당하며, 누락 시 집계가 뻥튀기됩니다.
6. **운영 복잡도 순증**: 11개 마스터에 대해 Stream 11개 + Task 11개 + Stale 모니터링 체계가 요구되어 관리 포인트가 대폭 증가합니다.

### 2-4. 소급 복구 리스크와 경량 처방 (RAW_HIST 신설 기각 및 check_cols 감사)
* **RAW_HIST 신설 기각 (YAGNI 원칙)**:
  - "언젠가 스냅샷 설정이 틀렸을 때를 대비해 RAW_HIST 불변 append 테이블을 미리 만들자"는 제안은 `00_guides/04_YAGNI_원천중심_과잉모델링_방지_원칙.md`의 [원칙 1](소비처 없는 테이블 생성 금지) 및 [원칙 4](기존 인벤토리 선실측)에 따라 **과잉 엔지니어링으로 기각**되었습니다.
* **경량 대체 처방 (check_cols 감사)**:
  - 새 스키마를 증설하는 대신, 기존 `check` 전략 스냅샷 6종의 `check_cols` 컬럼 범위를 감사하여 비즈니스 중요 컬럼이 누락되지 않도록 유지 관리합니다. (실측 결함: `snp_crm_tc_cmmn_dtl_cd`에 `RM`(비고) 누락 확인 ➔ 백로그 등재).

## 3. 표준 네이밍 룰 (Naming Rule)

### 3-1. 네이밍 규칙 공식

```
SNP_{출처약어}_{원천물리테이블명_그대로}
```

* **접두사**: `SNP_` (Snapshot 식별자)
* **출처약어 규칙**:
  * `BRONZE_CRM` ➔ `CRM`
  * `BRONZE_ERP` ➔ `ERP`
  * `BRONZE_AGENCY` ➔ `AGENCY`
  * `BRONZE_GA4` ➔ `GA4`
  * `BRONZE_GSC` ➔ `GSC`
  * `SILVER` ➔ `SILVER` (SILVER 파생 상태 스냅샷 시)
  * `GOLD` ➔ `GOLD`
* **테이블명 규칙**: 원천 물리 테이블명을 100% 그대로 보존하여 원천 DB와의 1:1 직관적 매핑 보장.

### 3-4. 소비처 실측 및 실효성 한정 (2026-09-11 실측 판정)
* **소비처 0 (탈배선 정합화)**:
  - dbt 전 범위(`models/`·`tests/`·`macros/`) 실측 결과, 스냅샷 11종의 dbt 다운스트림 소비처는 **0건(의도된 상태)**입니다.
  - 사유: 스냅샷을 먼저 실행하여 이력을 축적(선이력)한 후, 현업의 공식 요건 확정 시 다운스트림에 배선(후배선)하는 원칙을 적용합니다.
* **초과 버전 0 및 Two-tier 실효 0건 실측**:
  - `SNP_CRM_TM_CM_CMPGN_MNG` 36,163행 실측: distinct key 36,163 (초과 버전 0건, 전건 `DBT_VALID_TO IS NULL`).
  - `GOLD.DIM_MEMBER_ACQUISITION` 1,585,949명 실측: 과거 시점동결명(`ACQ_CAMPAIGN_NAME_AT_ACQ`)과 현재 최신명(`ACQ_CAMPAIGN_NAME`)이 **1,585,949명 전건 동일(100%)**하여 실효 차이가 0건이었습니다.
  - 이에 따라 실효가 없고 AI 표명을 왜곡하던 Two-tier 컬럼을 제거하고, 순수 SCD1 마스터 조인으로 정합화했습니다.

    config(

## 5. MSTR 직접 조회 대조 리스크 및 Two-Tier 컬럼 제공 표준

### 5-1. 핵심 리스크: MSTR 운영계 조회와의 숫자 불일치 (Reconciliation Risk)
* 현업 담당자가 MSTR로 CRM 운영계를 직접 조회하면 항상 최신 마스터(SCD Type 1)가 반영된 숫자를 보게 됩니다.
* 반면 DW에서 가입 시점 스냅샷(SCD Type 2)으로 고정하면 과거 특정 연도의 캠페인별 실적이 MSTR과 다르게 집계되어 데이터 불신이 발생할 수 있습니다.

### 5-2. Two-Tier (이중 컬럼) 배선 대기 방침
* **현행 방침 (선이력·후배선에 따른 배선 대기)**:
  - 스냅샷 최초 구축 시점에는 과거 이력이 존재하지 않아 `ACQ_CAMPAIGN_NAME_AT_ACQ`와 `ACQ_CAMPAIGN_NAME`이 100% 동일하므로, 실효가 없고 AI 표명을 왜곡하는 Two-tier 컬럼을 제거하고 **배선 대기 상태**로 전환했습니다.
* **향후 배선 조건**:
  - 향후 원천 마스터 변경이 실제로 누적되어 스냅샷 테이블에 2개 이상의 버전(`DBT_VALID_TO IS NOT NULL`)이 형성되고, 현업의 공식 Two-tier 요구가 있을 때 `DIM_MEMBER_ACQUISITION` 등에 Point-in-Time 조인 컬럼을 추가합니다.
  - 제공 예정 컬럼:
    1. `ACQ_CAMPAIGN_NAME_AT_ACQ` (가입 당시 캠페인명 ➔ Snapshot 기반): **과거 코호트 및 시점 불변 분석용**
    2. `ACQ_CAMPAIGN_NAME` (현재 최신 캠페인명 ➔ Master 직접 조인): **MSTR 및 CRM 운영계 데이터 대조용**
