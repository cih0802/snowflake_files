# [GN_DW] dbt Snapshot 아키텍처 및 표준 네이밍 규칙 정의서

> **문서 목적**: 원천 마스터의 덮어쓰기(Overwrite)로 인한 과거 시점 리포팅 왜곡을 방지하고, 시점별 변경 이력(SCD Type 2)을 안정적으로 추적하기 위한 `SNAPSHOT` 스키마 아키텍처 및 테이블 네이밍 규칙을 정의합니다.

---

## 1. 스냅샷 아키텍처 개요

### 1-1. 도입 배경 및 목적
* **문제점**: BRONZE 원천 마스터(캠페인, 부서, 사업 등)는 변경 이력(History) 없이 최신 데이터로 계속 덮어써집니다(SCD Type 1).
* **파급 효과**: 2021년 가입 회원의 획득 캠페인명이 2025년 개칭된 최신 명칭으로 소급 변경되어 과거 시점 코호트/실적 보고서가 왜곡됩니다.
* **해결책**: `dbt snapshot`을 통해 변경분만 1행씩 유효기간(`dbt_valid_from` ~ `dbt_valid_to`)과 함께 영구 누적(SCD Type 2)하고, 회원 가입 시점의 유효 명칭을 Point-in-Time Join으로 정확히 복원합니다.

### 1-2. 전체 데이터 파이프라인 흐름

```
[BRONZE 원천 마스터] (SCD Type 1: 최신값 덮어쓰기)
       │
       ▼ (dbt snapshot 실행: 변경분 이력 자동 감지 및 누적)
[SNAPSHOT 스키마]   (SCD Type 2: dbt_valid_from ~ dbt_valid_to 보존)
       │
       ▼ (dbt run: 가입일자/발생일자 기준 BETWEEN Point-in-Time 조인)
[SILVER 계층 모델]  (CRM_MEMBER_DEV, CRM_ORG 등)
       │
       ▼ (dbt run: 최종 분석 마트 배포)
[GOLD 차원/팩트]    (DIM_MEMBER_ACQUISITION, DIM_ORG 등)
```

## 2. SNAPSHOT 전용 스키마 정책

### 2-1. 왜 별도 `SNAPSHOT` 스키마로 분리하는가?
1. **생명주기(Lifecycle) 격리**:
   * `SILVER`, `GOLD`는 로직 변경 시 언제든 Truncate-Insert(전체 재적재)되는 가변 영역입니다.
   * `SNAPSHOT`은 과거 변경 이력이 영구 누적되는 불변 보존 영역이므로, 전체 재적재 배치 시 삭제되지 않도록 물리적 스키마를 분리합니다.
2. **운영 실수 방지**:
   * 일괄 Truncate/Drop 스크립트 실행 사고로부터 과거 스냅샷 데이터를 안전하게 보호합니다.

### 2-2. 스토리지 및 컴퓨팅 비용
* **스토리지 비용 ($0에 수렴)**: 마스터 테이블은 수십 KB ~ 수 MB 수준이며, 변경된 행만 1행씩 추가되므로 Snowflake 스토리지 비용 증가는 월 수십 원 내외로 극히 미미합니다.
* **컴퓨팅 비용**: 작은 용량의 마스터 비교는 X-Small 웨어하우스로 1~3초 내에 완료됩니다.

## 3. 표준 네이밍 룰 (Naming Rule)

### 3-1. 네이밍 규칙 공식

```
SNP_{출처약어}_{원천물리테이블명_그대로}
```

* **접두사**: `SNP_` (Snapshot 식별자)
* **출처약어 규칙**:
  * `BRONZE_CRM` ➔ `CRM`
  * `BRONZE_ERP` ➔ `ERP`
  * `BRONZE_AGENCY` ➔ `AGENCY`
  * `BRONZE_GA4` ➔ `GA4`
  * `BRONZE_GSC` ➔ `GSC`
  * `SILVER` ➔ `SILVER` (SILVER 파생 상태 스냅샷 시)
  * `GOLD` ➔ `GOLD`
* **테이블명 규칙**: 원천 물리 테이블명을 100% 그대로 보존하여 원천 DB와의 1:1 직관적 매핑 보장.

## 4. dbt Snapshot 표준 코드 템플릿

### 4-1. Timestamp 전략 템플릿 (`snapshots/snp_crm_tm_cm_cmpgn_mng.sql`)

```sql
{% snapshot snp_crm_tm_cm_cmpgn_mng %}
{{
    config(
      target_database='GN_DW',
      target_schema='SNAPSHOT',
      unique_key='cmpgn_cd',
      strategy='timestamp',
      updated_at='last_updt_dt'
    )
}}

SELECT
    cmpgn_cd,
    cmpgn_nm,
    spnsr_bsns_id,
    use_yn,
    last_updt_dt,
    last_updusr_id
FROM {{ source('bronze_crm', 'tm_cm_cmpgn_mng') }}

{% endsnapshot %}
```

### 4-2. Check (컬럼 비교) 전략 템플릿 (`snapshots/snp_crm_tm_cm_dept_info.sql`)

```sql
{% snapshot snp_crm_tm_cm_dept_info %}
{{
    config(
      target_database='GN_DW',
      target_schema='SNAPSHOT',
      unique_key='dept_id',
      strategy='check',
      check_cols=['dept_nm', 'upper_dept_id', 'acmslt_upper_dept_id', 'use_yn', 'stats_dept_lvl']
    )
}}

SELECT
    dept_id,
    dept_nm,
    upper_dept_id,
    acmslt_upper_dept_id,
    use_yn,
    stats_dept_lvl
FROM {{ source('bronze_crm', 'tm_cm_dept_info') }}

{% endsnapshot %}
```

## 5. MSTR 직접 조회 대조 리스크 및 Two-Tier 컬럼 제공 표준

### 5-1. 핵심 리스크: MSTR 운영계 조회와의 숫자 불일치 (Reconciliation Risk)
* 현업 담당자가 MSTR로 CRM 운영계를 직접 조회하면 항상 최신 마스터(SCD Type 1)가 반영된 숫자를 보게 됩니다.
* 반면 DW에서 가입 시점 스냅샷(SCD Type 2)으로 고정하면 과거 특정 연도의 캠페인별 실적이 MSTR과 다르게 집계되어 데이터 불신이 발생할 수 있습니다.

### 5-2. 표준 해결책: Two-Tier (이중 컬럼) 동시 제공
`GOLD.DIM_MEMBER_ACQUISITION` 차원 마트에 두 관점의 컬럼을 동시에 제공합니다:
1. `ACQ_CAMPAIGN_NAME_AT_ACQ` (가입 당시 캠페인명 ➔ Snapshot 기반): **과거 코호트 및 시점 불변 분석용**
2. `CURRENT_CAMPAIGN_NAME` (현재 최신 캠페인명 ➔ Master 직접 조인): **MSTR 및 CRM 운영계 데이터 대조용**
