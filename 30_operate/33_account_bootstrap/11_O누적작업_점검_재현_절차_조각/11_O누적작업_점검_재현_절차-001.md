# 11_O누적작업_점검_재현_절차 — 누적 작업 비판적 검토(Inspection) 재현 가이드

> 🟢 **이 문서는 「절차서」다. 특정 시점의 잔여작업 목록이 아니다.**
> 열린 작업의 정본은 **항상 `99_NEXT_SESSION` 착수표**이고, 이 문서는 **점검을 다시 돌리는 방법**만 담는다.
> ⇒ 여기에 「지금 열려 있는 항목」을 적지 마라. 적으면 다음 주에 stale 이 된다.

## ▣ 0. 이 점검은 무엇인가

| 축 | 내용 |
|---|---|
| **대상** | O 세션 누적 작업 전체를 **판정식으로 훑어** 결함(도구 오판 · stale 판정 · 라이브 부재 · 등록부 불일치)을 찾는 세션 |
| **왜 주기적으로 돌리나** | 점검은 **그 시점의 문서·도구·라이브**를 본다. 세션이 쌓이면 ㉠ 서식 관례가 바뀌어 도구가 조용히 분모를 잃고 ㉡ 「완료」 문안이 라이브와 어긋나고 ㉢ 두 등록부의 열린 집합이 갈라진다 |
| 🔴 **재실행 트리거** | ㉠ O 세션 **8~10개** 누적마다 ㉡ 브리핑·게이트 도구를 고친 직후 ㉢ 계정 재구축 직후 ㉣ 인수인계 절이 3겹 이상 적층됐을 때 ㉤ **객체·컬럼을 개명한 직후** |
| **입력** | `20_issue/00_BRIEF.md` · `99_NEXT_SESSION` 현행 인수인계 절 · `scripts/` 게이트·테스트 전건 · 라이브 DB |
| **산출물** | 결함 목록(`D`-번호) + 판정식 + **게이트·음성 테스트 신설** + 정본 3곳 갱신 + 근거철 1개 |
| 🔴 **하지 말 것** | 이력 전량 독해(규모는 `doc_census.py` 로 재라) · 라이브 미조회 수치 주장(`R2-8-4-c`) · dbt 실행(`R4-1`) · 현업 대기 항목 배선 |
| 🟢 **성공 판정식** | 「고친 뒤 통과」가 아니라 **「고치기 전 코드에서 반드시 실패하는 음성 테스트」**가 있어야 그 테스트가 결함을 본다는 증거가 된다 |

### 0-1. 🔴🔴 이 점검의 제1 원리 — 게이트 전수 PASS 는 무결의 증거가 아니다

실측으로 **세 번** 확인됐다. 게이트가 전부 🟢 인 상태에서 결함이 살아 있었다:

| 세션 | 게이트 상태 | 그 상태에서 살아 있던 결함 |
|---|---|---|
| `O83-H` | 6종 🟢 | 지침 축별 대조에서 결함 4건 |
| `O143` | 6종 🟢 | 브리핑 승계 절 오선택 · stat 바이트 오탐 · 등록부 불일치 |
| **`O155`** | **11종 🟢** | 개명 전 이름 **536건** · 라이브에 없는 테이블을 가리키는 SV COMMENT |

⇒ 🔴 **점검의 일은 「게이트를 돌리는 것」이 아니라 「게이트가 보지 않는 축을 찾는 것」이다.**

## ▣ 1. 재현용 프롬프트 (복붙)

```markdown
@(skill:init_ihcho)
# 이번 세션은 누적 작업을 비판적으로 전수 점검하는 Inspection 세션이다.
# 절차 정본 = 60_repeat_어카운트시작/11_O누적작업_점검_재현_절차.md

1. `/init_ihcho` 로 지침과 `20_issue/00_BRIEF.md` 를 로드하고 게이트 상태를 확인한다.
2. **점검 구간을 먼저 확정**한다 = 직전 Inspection 세션 라벨 이후 ~ 현재.
   원장 §1 대시보드에서 그 구간의 세션 행을 열거하고 **결번이 있는지** 본다.
3. 전 문서군은 완독하지 않는다(`doc_census.py` 로 규모를 재라). 대신
   **「결함 검출 판정식」**을 세워 정본·이력·스크립트·라이브를 훑는다.
   판정식 카탈로그 = 이 문서 §3. **그 표를 위에서부터 전건 적용**한다.
4. 발견한 결함마다 ㉠ `D`-번호 ㉡ 판정식 ㉢ 실측값 ㉣ 처방을 `20_issue/_o1NN_inspection_evidence.md`
   에 **판정보다 먼저** 기록한다(`R1-3-7-c`).
5. 결함이 「게이트가 보지 않는 축」이면 **게이트를 신설**하고 **음성 테스트**를 같이 만든다(`R3-2`).
   🔴 기준선(baseline)을 발행할 때는 그것이 **「해소」가 아니라 「증가 차단」**임을 출력에 박아라.
6. 승인이 필요한 작업은 사전 승인된 것으로 간주한다. 게이트 전건과 음성 테스트 전건을
   **파이프 없이**(`>/tmp/x.out 2>&1` 후 `rc=$?`) 통과시키고 정본 3곳을 갱신한다.
```

## ▣ 2. Phase 절차 (6단계)

```
[Phase 0: 분모 실측 · 구간 확정 · 라벨 선점]
  ├ 1. doc_census.py 로 문서 규모 실측 ⇒ 전량 독해 불가 확인(수치는 적지 말고 도구로 재라)
  ├ 2. 점검 구간 확정 = 직전 Inspection 라벨 이후 ~ 현재 · 원장 §1 에서 세션 행 열거
  │     🔴 결번을 반드시 확인하라 — O155 는 여기서 `O148` 을 찾아냈다(§4 D2)
  └ 3. id_collision_gate.py --next O 로 라벨 확인 → 원장 §1 에 **한 줄 선점 등재**(R1-4-3)

[Phase 1: 도구 신뢰성 — 「도구가 무엇을 못 보는가」]
  ├ 1. 브리핑·게이트가 **자기 분모를 잃지 않았는가** (분모 stale)
  ├ 2. 같은 것을 **다르게 재는 지점**이 있는가 (R3-9 ㉡)
  └ 3. 결함을 찾으면 **오염 기반 음성 축**을 먼저 만들어 「고치기 전 실패」를 실증한다

[Phase 2: 문서 ↔ 구현 드리프트]
  ├ 1. 개명·이동·폐기된 이름이 살아있는 정본에 남았는가 → rename_stale_gate.py
  ├ 2. 「완료」 문안이 실제 구현과 같은가 (모델 파일을 열어 대조)
  └ 3. 🔴 「0건」을 받으면 **분모를 같은 문장에 적었는지** 확인한다 (§4 D1)

[Phase 3: 라이브 실증]
  ├ 1. 문서가 주장하는 객체가 라이브에 실재하는가 (R2-8-4)
  ├ 2. 라이브 메타데이터(COMMENT)가 라이브 실체를 가리키는가 — 🔴 파일↔라이브 일치는 별 축이다
  └ 3. 0 센티넬 가드가 살아 있는가 (결정 대기 중 배선 금지 축)

[Phase 4: 등록부 결합 · 지침 보충]
  ├ 1. 착수표 열린 집합 ↔ 인수인계 절 = session_brief.py 의 handoff_gap (R3-9 ㉨)
  ├ 2. 내 결정을 인용한 정본이 stale 인가 = decision_closure_gate.py (R3-9 ㉥)
  └ 3. 새로 배운 판정식을 지침(00_guides)·스킬(init_ihcho)·이 문서 §3 에 등재

[Phase 5: 종료]
  ├ 1. 게이트 전건 + 음성 테스트 전건 rc=0 (🔴 파이프 뒤에서 rc 를 읽지 마라 · R0-8-2)
  ├ 2. 신설 도구를 gate_census 에 등재(미분류 0) · 골든 발행 시 --reason 필수
  └ 3. 정본 3곳 갱신 = 원장 §1 행 · 01_세션이력 항목 · 99_NEXT 인수인계 절(승계 취소선)
```
