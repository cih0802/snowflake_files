# 04. 알림 및 거버넌스 전략

Cortex AI 비용·사용량에 대한 실시간 알림 구성과 운영 권장 전략을 정리한다.

## 1. quota 내장 알림 (우선 고려)

Alert를 직접 만들기 전에, Per-user quota가 제공하는 내장 알림을 먼저 쓴다.
사용자별 한도에 대한 실지출·예측지출 임계치를 지원하며 별도 웨어하우스가 필요 없다.

```sql
CALL GN_DW.OPS.AI_USER_QUOTA!SET_ADMIN_EMAILS('admin@example.com');
CALL GN_DW.OPS.AI_USER_QUOTA!ADD_NOTIFICATION_THRESHOLD(80,  'PROJECTED', TRUE);
CALL GN_DW.OPS.AI_USER_QUOTA!ADD_NOTIFICATION_THRESHOLD(100, 'ACTUAL',    TRUE);
CALL GN_DW.OPS.AI_USER_QUOTA!GET_NOTIFICATION_THRESHOLDS();
```

- `SPEND_STRATEGY`: `'ACTUAL'`(실지출) | `'PROJECTED'`(월말 추정)
- 3번째 인자는 해당 사용자 본인에게도 알릴지 여부
- 이메일은 **사전 검증된 주소만** 발송된다. 미검증 시 이벤트 테이블에 정보성 이벤트만 남는다
- `PROJECTED` 임계치는 사용자·임계치당 24시간에 1회, `ACTUAL`은 사이클당 1회로 제한된다

## 2. Alert 기반 알림 (계정 총량 감시)

quota 알림은 **사용자 단위**다. 계정 전체 총량을 감시하려면 Alert를 쓴다.
Alert 자체도 서버리스로 실행되며 소량의 크레딧(`SERVERLESS_ALERTS`)을 소비한다.

```sql
-- 사전 준비: 이메일 notification integration (ACCOUNTADMIN)
CREATE OR REPLACE NOTIFICATION INTEGRATION admin_email_int
    TYPE = EMAIL
    ENABLED = TRUE
    ALLOWED_RECIPIENTS = ('admin@company.com');  -- 검증된 이메일만 허용
```

```sql
-- 일일 AI 크레딧이 임계치 초과 시 알림
--   ⚠️ service_type 을 하드코딩하지 않는다. 이전 판은 존재하지 않는 값
--      ('CORTEX_CODE_SNOWSIGHT' 등)을 IN 절에 넣어 조건이 영구히 거짓이었다.
--      실제 값은 SNOWFLAKE_COCO_SNOWSIGHT 계열이다(02 문서 §1).
--   ⇒ 웨어하우스·저장 등 비AI 항목만 제외하는 방식이 안전하다.
CREATE OR REPLACE ALERT cortex_cost_alert
    WAREHOUSE = COMPUTE_WH
    SCHEDULE = 'USING CRON 0 */2 * * * Asia/Seoul'   -- 2시간마다
    IF (EXISTS (
        SELECT 1
        FROM SNOWFLAKE.ACCOUNT_USAGE.METERING_DAILY_HISTORY
        WHERE usage_date = CURRENT_DATE()
          AND service_type NOT IN (
                'WAREHOUSE_METERING', 'WAREHOUSE_METERING_READER',
                'STORAGE', 'PIPE', 'TELEMETRY_DATA_INGEST',
                'AUTO_CLUSTERING', 'MATERIALIZED_VIEW', 'SEARCH_OPTIMIZATION'
              )
        GROUP BY usage_date
        HAVING SUM(credits_used) > 50            -- 일 50크레딧 초과
    ))
    THEN
        CALL SYSTEM$SEND_EMAIL(
            'admin_email_int',
            'admin@company.com',
            'AI 비용 경고',
            'AI 일일 크레딧 사용량이 50을 초과했습니다.'
        );

-- 생성된 Alert는 기본적으로 일시중지 상태이므로 활성화 필요
ALTER ALERT cortex_cost_alert RESUME;
```

> **주의사항**
> - `METERING_DAILY_HISTORY`는 지연(최대 수 시간)이 있어, 실시간 차단 용도로는 부적합하고
>   "사후 경고" 성격이다. 즉각적인 통제가 목표라면 Per-user quota의 내장 Block을 병행한다.
> - `SYSTEM$SEND_EMAIL`의 인자는 (integration_name, recipients, subject, body) 순서다.
> - CRON 표현식의 타임존은 계정 파라미터가 아니라 문자열 내에서 지정한다.
> - 🔴 **`service_type` 하드코딩 금지.** 값이 틀리면 오류 없이 조건이 항상 거짓이 되어
>   알림이 **조용히 작동하지 않는다.** 배포 후 반드시 `SELECT DISTINCT service_type`으로
>   실제 값을 대조할 것.

## 3. 운영 권장 전략 (계층적 접근)

| 단계 | 수단 | 목적 | 차단 |
|------|------|------|------|
| 가시성 | `GN_DW.OPS.V_AI_SPEND_BY_USER` 대시보드 | 누가·얼마나 쓰는지 | - |
| 사용자 경고 | quota `ADD_NOTIFICATION_THRESHOLD` | 개인 한도 접근 시 경고 | - |
| 총량 경고 | Alert (2~6시간 주기) | 계정 급증 감지 | - |
| **하드 제어(개인)** | **quota `SET_BLOCK_ENFORCEMENT_ENABLED`** | 사용자별 상한 초과 시 차단 | ⭕ 내장 |
| 하드 제어(그룹) | Budget + custom action | 팀 합산 예산 초과 시 역할 회수 | ⚠️ 프로시저 자작 |
| 하드 제어(접근) | RBAC (`CORTEX_USER` 역할 통제) | 비인가 사용자 원천 차단 | ⭕ |

## 4. 거버넌스 체크리스트

- [ ] `SNOWFLAKE.CORTEX_USER` 역할이 `PUBLIC`에 개방되어 있는지 점검 (필요 시 회수)
- [ ] AI 사용 전용 역할을 만들고 승인된 사용자에게만 부여
- [ ] Per-user quota 생성 및 AI 도메인 4종 등록
- [ ] **차단 활성화 전 `GET_USERS()`로 실제 적용 대상 확인** — 관리자가 포함되면 자기차단된다
- [ ] 신규 사용자 온보딩 절차에 `ALTER USER ... SET TAG AI_COST_SCOPE = 'GOVERNED'` 포함
      (태그 누락 시 가드가 조용히 비활성)
- [ ] Alert의 `service_type` 필터를 실제 값과 대조 (조용한 실패 방지)
- [ ] AI 사용량 대시보드(주간/월간)를 정기 리뷰 루틴에 포함
- [ ] `AI_INFERENCE`(REST API, 달러 과금)는 metering 뷰에 없으므로 청구서로 별도 확인
- [ ] 각 뷰의 정본(canonical) 여부를 확인해 중복 합산 방지 (특히 CoCo 계열 — 02 문서 §3)

## 5. 한계 및 유의점

- 서버리스 소비는 **Resource Monitor로 차단할 수 없다.**
- Budget 단독은 알림 전용이다. 차단은 custom action + 저장 프로시저를 직접 작성해야 성립한다.
- **quota의 Block은 AI 도메인 전용이다.** 웨어하우스 지출은 추적만 되고 차단되지 않는다.
- **한도를 설정하지 않으면 quota는 아무 것도 하지 않는다.** 객체 생성만으로는 가드가 아니다.
- 차단은 소비 후 수 분 내 평가이므로 **한도를 약간 초과(overshoot)한 뒤** 멈춘다.
- UTC 자정 리셋이므로 경계 직전 사용자는 두 사이클 한도를 연속 소비할 수 있다.
- `ACCOUNT_USAGE` 뷰는 지연이 있어 "지금 이 순간"의 비용을 실시간 반영하지 못한다.
- Per-user quota는 Preview이므로 구문이 변경될 수 있다.
  실제로 `EXCLUDE_USERS`가 문서상 허용값을 거부하는 결함이 실측되었다(03 문서 §1-4).
- 기능별 사용량 뷰는 metering 총합과 정확히 일치하지 않는 것이 정상이다(부분집합).
