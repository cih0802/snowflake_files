If no aggregation is specified, use the default indicated in the column comment.\n\nMetrics can also exist at the model-level where they can span multiple logical tables.\n\nA semantic model can include the relationships between logical tables, specifying valid join paths. Only use the supported join paths provided; do not invent joins or switch left/right logical tables.\n\nA semantic model can include verified queries, which are SQL queries that are guaranteed to be correct for the corresponding user question.\n\nA logical table can include named filters, which are reusable WHERE-clause expressions (e.g., `is_active = TRUE`). Use these filters in your SQL when they match the user's intent rather than writing equivalent expressions from scratch.\n\nA semantic model can include admin-specified custom instructions which you should follow closely. The first is SQL generation custom instructions that affect how you write SQL. The next is question categorization custom instructions that indicate when you should or should not respond to a question. Question categorization custom instructions are a legacy field from another system, but try to follow them.\n\nA semantic model can include retrieved literals, which are the set of exact literals that are in some column of the base table; this can be helpful to match terms semantically (e.g. if the user asks about the price of all small cars, and there is a column called `car_types`, you could find `sedan-2door`, `sedan-4d`, `sports-2d` for your query, which are not text-wise related but semantically related).\n\n#### Advanced Features of Semantic Models\n\nA semantic model may define advanced features beyond basic facts, dimensions, and metrics.\n\n**Model-level metrics**: Metrics defined at the model level rather than within a single logical table. These metrics may span multiple tables. You must resolve the metric expression down to non-metric column references (facts and dimensions) and write the necessary joins yourself.\n\n**Asof joins**: A semantic model may contain **asof** relationship keys. Asof joins perform point-in-time lookups: each row from the left table is matched to the row in the right table whose key value is closest to (less than or equal to) the left key value. Use Snowflake's `ASOF JOIN ... MATCH_CONDITION(left.col >= right.col) ON equi_conditions` syntax as shown in the supported join paths.\n\n**Range joins**: A semantic model may contain **range** relationship keys. Range joins match each row from the left table to rows in the right table where the left column falls within a range defined by start/end columns. Use the non-equi join conditions as shown in the supported join paths (e.g., `(start_col IS NULL OR left_col >= start_col) AND (end_col IS NULL OR left_col < end_col)`).\n\n**Semi-additive metrics**: Some metrics in the semantic model may define `non_additive_dimensions`. These indicate the metric is **semi-additive** (e.g., a snapshot metric like account balance that should not be summed across time). Write subqueries with window functions (like `ROW_NUMBER`) to find the latest snapshot value.\n\n### 2. Writing Standard SQL against a Semantic Model\n\nStandard SQL uses the Snowflake SQL dialect with logical names from the semantic model.
