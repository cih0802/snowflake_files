# 20. ML 예측결과 Semantic View 설계 (O74 · 실측 단계)

> 🔴 **이 문서는 「머신러닝 예측결과 테이블」을 Agent 에 노출하기 위한 설계다.**
> 대상 스키마 = **`GN_DW.ML`** · 대상 = 사용자가 지정한 **결과 테이블 16종**(요건 14개).
> ⛔ **여기 기재되지 않은 `GN_DW.ML` 테이블은 학습용(`ML_TRAIN_DATA_*`)·중간 스냅샷이며 Agent 에 노출하지 않는다**(사용자 지시).
>
> 🔴🔴 **전제 — 이 데이터는 「테스트 단계의 머신러닝 산출물」이다**(사용자 확정 2026-08-14).
> · 모델·피처·테이블 구조가 **향후 대규모로 교체될 수 있다.**
> · ⇒ 설계는 **교체 내성**을 1급 요구사항으로 둔다(§5).
> · ⇒ Agent 답변에는 **「예측치이며 실적이 아니다」**·**「기준월 `STDR_MT` 의 모델 산출물이다」** 가 항상 붙어야 한다.
>
> 🔴 **발행 단계가 아니다.** 이번 세션 범위 = 실측 + 설계까지. SV DDL 저작·배포는 **별건 승인**(사용자 지시).

## 1. 🔴🔴 발행 전 반드시 해소할 결함 4건 (실측 근거 있음)

### 1-1. `MBER_CHURN_12M`·`MBER_INC_12M` 이 「회원 단위」가 아니다 — 18.0% 팬아웃

**실측**: 91,423행 / distinct `MBER_NO` **74,949** = **중복 16,474행(18.02%)**.
그런데 두 테이블의 **테이블 COMMENT 는 *"회원(MBER_NO) 단위"* 라고 선언**한다.

**원인 특정**: 팬아웃 원천은 `GN_DW.ML.MBER_MONTHLY_INFO` 다.
· `STDR_MT='202606' AND STDR_MT_MBER_STAT_CD<>'12'` 기준 **91,423행 / 74,949명**(= 결과 테이블과 정확히 일치)
· 이 테이블은 회원 스냅샷이 아니라 **상태 spell 행**을 담는다(`SER_NO`·`BF_STAT_CD`·`CHN_STAT_CD`·`STAT_START_DT`/`END_DT`)
· 프로시저의 **학습 데이터 STEP 은 dedup 을 하는데 예측 데이터 STEP 은 하지 않는다** ⇒ 예측 결과에만 중복이 남는다
· 🟢 결제수단 축은 원인이 아니다 — `MBER_MONTHLY_SETLE_INFO` 202606 = 742,640행 / **742,640명(1:1)**

**영향(무증상 오답 경로)**: Agent 가 *"중단 위험 회원 수"* 를 `COUNT(*)` 로 세면 **18% 과대**,
`AVG(확률)` 도 중복 회원에 가중이 실려 **틀린다**. 실측이 없으면 조용히 지나간다(`P18`·`P27` 유형).

**처방 — 우선순위 순**
1. 🥇 **원천 교정**(성현 프로 소관) — 예측 STEP 에 학습 STEP 과 같은 dedup 을 넣는다. 근본 해소.
2. 🥈 **SV base 를 dedup 뷰로 둔다** — `SERVING` 에 `QUALIFY ROW_NUMBER() OVER (PARTITION BY STDR_MT, MBER_NO ORDER BY …)` 뷰를 두고 SV 는 그 뷰를 base 로 한다.
   🔴 그러려면 **어느 행을 대표로 뽑을지**가 업무 결정이다(최종 상태 spell? 최대 확률?) ⇒ **결정 없이 임의 선택 금지**.
3. 🥉 **회원수 measure 를 `COUNT(DISTINCT MBER_NO)` 로만 정의**하고 `COUNT(*)` 계열을 노출하지 않는다.
   ⚠️ 이것은 완화이고 해소가 아니다 — `AVG(확률)` 왜곡은 남는다.

### 1-2. 테이블명은 `12M` 인데 내용은 **6개월** 예측이다

**실측 3중 일치**로 확인:
· 테이블 COMMENT = *"회원(MBER_NO) 단위 **향후 6개월 내** 중단확률 예측 결과"*
· 프로시저명 = **`SP_MBER_CHURN_6M_PREDICT`** · 학습 라벨 컬럼 = **`CHURN_6M`** · 학습 테이블 = `ML_TRAIN_DATA_MBER_CHURN_6M`
· 학습 컷오프 = `V_TRAIN_END = DATEADD(MONTH, **-6**, 기준월)`
반면 **테이블명은 `ML_RST_DATA_MBER_CHURN_12M`** 이고, 사용자 요건 기술도 *"회원별 중단 예측(향후 12개월)"* 이다.

🔴 **셋 중 무엇이 맞는지 우리가 정할 수 없다** — 요건(12M)과 구현(6M)이 다른 것이므로 **성현 프로·현업 확인 사항**이다.
⛔ **확인 전에 SV·Agent 에 기간을 발행하지 않는다.** COMMENT 는 Agent 의 답변 근거이므로(`P212`)
「12개월」이라 쓰면 **6개월 모델 결과를 12개월로 답하는 무증상 오답**이 된다.
🟢 잠정 처방 = 확인 전까지 SV 문안에 **「예측 지평은 원천 확인 중(테이블명 12M ↔ 구현 6M 불일치)」** 을 명시하거나,
이 1종만 **노출 보류**한다. 나머지 15종은 이 결함과 무관하다.

### 1-3. 예측 대상 모집단이 전체 회원이 아니다 — 회원 축 10.1%

**실측(202606)**: 예측 대상 **74,949명** ↔ 같은 달 후원실적 보유 회원 **742,261명** ⇒ **10.10%**.
원인 = `MBER_MONTHLY_INFO` 자체가 그 달 상태 spell 이 있는 회원만 담기 때문(월별 83,364~143,967명 · 최근월로 갈수록 감소).

🔴 **Agent 가 이것을 모르면 *"중단 위험 회원 3,000명"* 을 「전체 회원 중」으로 답한다.**
⇒ SV 문안에 **분모를 명시**한다(`P128` — 분모 확정 후 비율). 「전 회원 대비 비율」은 이 SV 로 답할 수 없다.

### 1-4. `'UNKNOWN'` 창작 라벨이 데이터에 들어 있다 (`R2-7` 위반)

프로시저가 `COALESCE(SETLE_CD,'UNKNOWN')`·`COALESCE(CPR_DIV_CD,'UNKNOWN')` 로 **값을 창작**한다.
**실측 규모는 작다**: `LOYAL_MBER` **1행**(SETLE·CPR 각 1) · `SPNSR_CHURN_12M.SETLE_CD` **29행** ·
`MBER_CHURN_12M`·`MBER_INC_12M` = **0행**.
🟢 규모가 작아 지표를 흔들지 않으나, **코드 도메인에 없는 값**이라 라벨 조인 시 `(미매핑)` 이 아니라 `'UNKNOWN'` 으로 뜬다
⇒ 세 표기(`(미매핑)`/`(해당없음)`/`NULL`)의 뜻을 구분하는 프로젝트 규약(`R2-7-3`)과 **네 번째 표기**가 섞인다.
**처방** = SV 라벨 축에서 `'UNKNOWN'` 을 **원천 창작 센티넬**로 COMMENT 에 명시(창작하지 말라는 규약을 우리가 되풀이하지 않는다). 원천 교정은 성현 프로 소관.

## 3. SV 분할안 — 성격이 다른 것을 한 SV 에 넣지 않는다

🔴 **판정 원칙** = `SEMANTIC VIEW()` 는 단일 뷰 대상이라 Agent 가 SV 간 행 조인을 못 한다(`O35` 기지).
⇒ **함께 물어보는 축은 같은 SV 에**, **grain·해석이 다른 것은 다른 SV 에** 둔다.
아래 4분할은 **grain 이 실제로 다르기 때문**이고, 부서 소속으로 나눈 것이 아니다.

| SV(안) | grain | 담을 결과 테이블 | 왜 묶는가 / 왜 나누는가 |
|---|---|---|---|
| **`SV_ML_FORECAST`** | 기준월 × 계열 × 예측월 | 5·6·7·8·9·15·10·12 (예측 8종) | 전부 `SNOWFLAKE.ML.FORECAST` 산출이고 컬럼 계약이 동일(`SERIES`·`TS`·`FORECAST`·`LOWER/UPPER_BOUND`) · 「무엇의 계열인가」만 다르다 ⇒ **계열축(SERIES_TYPE)** 을 세워 한 SV 로 통합 가능 |
| **`SV_ML_MEMBER_RISK`** | 기준월 × 회원 | 2·3·4 (분류 3종) | 회원 grain 예측 · 확률/클래스 해석이 동일 ⇒ 함께 물어본다("중단 위험이면서 증액 가능성이 낮은 회원") |
| **`SV_ML_SPONSOR_RISK`** | 기준월 × 회원 × 후원건 | 1 (후원건 중단) | 🔴 **회원 grain 과 합칠 수 없다** — 회원당 여러 후원건이라 2·3 과 조인하면 팬아웃(`O8` 유형) |
| **`SV_ML_LTV_SCORE`** | 기준월 × 채널 | 11·13 | 🔴 **예측 SV 와 합칠 수 없다** — 예측은 월 12행, 스코어는 계열당 1행. 한 SV 에 두면 `SUM(FORECAST)` 과 `LTV` 가 서로 다른 분모로 섞인다 |
| **`SV_ML_FEATURE_IMPORTANCE`** | 기준월 × 피처 | 14·16 | 🔴 **측정 대상이 데이터가 아니라 모델이다** — 다른 SV 의 measure 와 같은 표에 두면 「업무 수치」로 읽힌다. 값은 0~1 기여도이며 금액·건수가 아니다 |

🔴 **8·11·13 을 예측 SV 와 나누는 근거는 실측이다** — 예측 5종은 계열수×12행(예: 부서 30계열×12=360)이고

### 3-A. 🔴 전 SV 공통 필수 문안 (없으면 조용한 오답이 난다)

1. **「예측치이며 실적이 아니다」** — 실적 SV(`SV_MEMBER_*`)와 **합산·비교 시 축을 밝힌다**.

   ⇒ 문안을 **지금** 넣는다(증상이 없을 때 넣어야 한다).
3. **「`FORECAST`·`LOWER_BOUND`·`UPPER_BOUND` 는 95% 신뢰구간이다」** — 상·하한을 별개 실적으로 읽지 않는다.
4. **단위** — 개발금액 예측 4종은 **만원 단위**(프로시저가 `/10000` 한다) · 회비·LTV 는 **원** ⇒ **섞으면 10,000배 오차**.

## 4. `PREDICTION` VARIANT 를 어떻게 노출할 것인가

**실측 구조**(`ML_RST_DATA_MBER_CHURN_12M` 표본):
```json
{"class":"0",
 "probability":{"0":0.9277778758,"1":0.0722221242},
 "logs":{"Error":[],"Info":[],"Warning":[]}}
```

🔴 **SV 에 VARIANT 를 그대로 노출하지 않는다** — Cortex Analyst 가 JSON 경로를 조립하게 만들면
`probability:"1"` 같은 따옴표 키에서 조용히 실패하거나 `class` 를 숫자로 오해한다.
🟢 **처방 = SERVING 뷰에서 스칼라로 평탄화**한다.

| 노출 컬럼(안) | 식 | 성격 |
|---|---|---|
| `CHURN_PROB` / `INC_PROB` / `LOYAL_PROB` | `PREDICTION:probability:"1"::FLOAT` | 🟢 metric 가능(단 **AVG 만** · SUM 금지) |
| `PREDICTED_CLASS` | `PREDICTION:class::VARCHAR` | 차원(코드 `0`/`1`) — 라벨은 SV 에서 부여 |
| `PREDICTION_HAS_ERROR` | `ARRAY_SIZE(PREDICTION:logs:Error)>0` | 품질 플래그 |
| ⛔ `logs` 원문 | — | 노출 금지(운영 로그) |

🔴 **확률의 SUM 은 금지**하고 metric 정의 자체를 `AVG`·`COUNT_IF(prob>=임계)` 로만 만든다.
🔴 **임계값(위험 판정선)은 우리가 정하지 않는다** — 현업 결정 사항이다.
프로시저가 주는 `class` 는 모델 기본 임계(0.5)이므로, 업무 임계가 다르면 `class` 를 그대로 「위험 회원」으로 쓰면 틀린다.

## 5. 교체 내성 설계 (사용자 전제 ㉠의 집행)

ML 이 테스트 단계라 **테이블이 `CREATE OR REPLACE` 로 갈릴 수 있다.** 그때 무엇이 깨지는지부터 실측 근거로 적는다.

| 위험 | 왜 생기나 | 처방 |
|---|---|---|
| **GRANT 소실** | 정본 `20_ML_ddl.sql` 은 결과 테이블을 **`create or replace TABLE`** 로 적는다 ⇒ 재실행 시 객체가 새로 생겨 **부여한 SELECT 가 사라진다**(`P125` 계열) | **`GRANT SELECT ON FUTURE TABLES IN SCHEMA GN_DW.ML`** 로 미래 객체까지 덮는다 + 노출 대상만 뷰로 감싼다 |
| **SV 무효화** | SV 가 base 테이블을 직접 참조하면 테이블 교체·컬럼 변경이 SV 로 직접 전파 | **SERVING 뷰 계층을 반드시 끼운다** — SV base = `SERVING.ML_*_V` · 컬럼 계약을 뷰에 고정 |
| **학습 테이블 오노출** | 스키마 단위로 권한을 주면 `ML_TRAIN_DATA_*` **37종이 함께 열린다** | 🔴 **스키마 통짜 GRANT 금지** — 뷰 5~6개에만 SELECT 를 준다(사용자 지시의 집행 장치) |
| **정의 드리프트** | 모델이 바뀌어도 SV COMMENT 는 그대로 남아 **낡은 주장을 계속 발행**(`P212`) | SV 문안에 **모델 실행 기준월과 「테스트 단계」** 를 넣고, 재실행 시 회귀 확인을 게이트에 넣는다 |
| **`SERIES` 의미 이동** | 예측 8종이 전부 `SERIES` 라는 **같은 이름에 다른 뜻**(부서/캠페인/사업/신규구분)을 담는다 | 통합 SV 에서 `SERIES_TYPE` 을 **필수 동반 축**으로 세우고, 라벨 컬럼을 축별로 분리 |

🔴 **결론 = 「SV 를 ML 테이블에 직접 걸지 않는다.」** 뷰 계층이 교체 충격의 흡수대이고,
그것이 없으면 모델이 한 번 갈릴 때마다 SV DDL 을 다시 써야 한다.
🟢 부수 효과 = §1-1 dedup 도 이 뷰 계층에서 처리할 수 있다(원천 교정 전 임시 방어).

**🔴 내가 만든 결함 2건과 그 처리**
1. **`'후원중단'` 오열거** — 원천 프로시저가 상태코드 `12`(후원중단)를 **예측 대상에서 배제**하는데
   나는 COMMENT 에 그 라벨을 열거했다. Agent 가 그 값으로 필터하면 **0행을 「해당 없음」으로 답한다.**
   ⇒ 실제값 **11종 전건 열거** + **「후원중단은 이 SV 에 없다 · 이미 중단한 회원은 예측 대상이 아니다」** 를 명시했다.
   🟢 이것은 게이트가 없었으면 못 잡았을 오답이다.
2. **COMMENT 수치 6건** — 단위 환산 배수와 grain 표현이었지만 규약 위반이다. 숫자를 지우고 말로 바꿨다.

**🟠 의도적 잔여 10건 (열거하지 않는 것이 옳다고 판단 · 사유를 COMMENT 에 남겼다)**
* **`STDR_MT` 7건** — 모델을 다시 돌릴 때마다 값이 늘어난다. 열거하면 **즉시 낡는다.**
  🔴 게다가 기준월은 숫자여서, 열거하면 위 **「COMMENT 수치 금지」 검사와 정면으로 충돌**한다
  ⇒ **두 게이트가 이 축에서 상충한다**는 것이 이 세션의 발견이며, 규약 정리가 필요하다.
* **`FEATURE` 1건** — 피처 목록은 모델 교체 시 바뀐다(ML 이 테스트 단계라는 전제와 직결).
* **`SPNSR_BSNS_ID`·`SPNSR_BSNS_NAME` 2건** — 후원사업 마스터가 늘어나면 낡는다.

**🔴 「필수 문안 소실 5건」은 내 변경과 무관한 기존 상태다 — 실측으로 확인했다**
* 이 세션은 그 5개 SV 의 DDL 파일을 읽지도, 배포하지도 않았다.
* 실측: `GET_DDL('SEMANTIC_VIEW','SV_MEMBER_FEE')` 132,739자에 `배분규칙필요`·`형제팩트중복`·`앵커_경합`·`집계필요`·`O67` **전부 0건**.
  반면 **파일에는 있다** — `05_1`(4토큰×2) · `05_2`(3×2) · `05_4`(2×2) · `05_8`(1×2) · `05_9`(3×2).
* ⇒ **O67 문안이 파일에만 있고 라이브 SV 에는 반영되지 않았다.**
  🔴 인수인계 §0-D 의 「O67 이 7표면에 발행했고 라이브 대조로 전건 반영을 확인했다」와 **충돌한다.**
  ⚠️ 원인(발행 누락인지 이후 되돌림인지)은 **판정하지 않았다** — 근거가 부족하다.
* 🔴 **고치지 않았다** — 5개 SV DDL 재배포는 요청 범위를 넘고, 그 파일들에 미배포 델타가 더 있으면
  의도치 않은 변경이 함께 라이브로 나간다. **다음 세션 확인 항목으로 넘긴다.**

## 8. 이 문서가 하지 않은 것 (잔여)

* 🔴 **NL 스모크 미실행** — Agent 가 자연어 질문에서 실제로 올바른 도구를 고르는지는 **검증되지 않았다.**
  트라이얼 제약으로 `DATA_AGENT_RUN` 이 막혀 있으면 CoWork UI 에서 사람이 수행해야 한다(기존 착수표 ② 와 같은 성질).
  ⚠️ 지금까지 검증한 것은 **SV 가 SQL 로 답한다**는 것까지다 — 라우팅은 별개다.
* 🔴 **성현 프로·현업 확인 4건** — ① 회원 중복 원천 교정(예측 STEP dedup) ② 12M↔6M ③ 업무 위험 임계값
  ④ **후원사업 예측 합이 전사보다 25% 큰 이유**(§7-B-3 신규).
* 🟠 **예측 5종 grain 전건 직접 측정** — §0-A 「동형」 3종은 여전히 미측정이나, 배포 후 뷰 단위 유일성으로 간접 확인됐다.
* 🟠 **회원 인적속성(성별·연령대·지역)별 예측 분해 미배선** — `DIM_MEMBER_CURRENT` 가 1:1 이라 안전하게 붙일 수 있으나
  요청 범위를 넘어 하지 않았다. Agent 문안에 「미배선」으로 명시했다.
* 🟠 **예측 정확도(실적 대비 검증) 미배선** — 예측·실적 교차는 원천·grain 이 달라 별건 설계가 필요하다.
* 🔵 **`'UNKNOWN'` 센티넬** 원천 교정(성현 프로) — 규모는 작다.
* ⬜ 정본 DDL 안에서 결과 테이블 생성 방식이 두 가지(`create or replace TABLE` ↔ 프로시저 `CREATE TABLE IF NOT EXISTS`)
  — 어느 것이 운영 경로인지 미판정. 🔴 전자가 실행되면 **뷰 7종의 GRANT 는 살아남지만 ML 테이블 자체가 새로 생기므로**
  뷰가 컬럼 계약을 지키는지 재확인해야 한다.
