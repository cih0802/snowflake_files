## R0. 셸 명령 안전 규칙 (모든 bash 호출 전 적용)

무한 대기의 최대 원인은 **미완결 셸 구문**이다.
예: `cd /workspace && for d in 05_SV-Agent_ai 02_GN_DW_building 10_dbt_pipeline`
→ `; do ... ; done` 이 없어 bash가 stdin에서 다음 줄을 계속 기다린다(`>` 연속 프롬프트).
실패가 아니라 **입력 대기 상태로 영구 정지**한다.

* **R0-1 구문 완결 필수**
  `for` → `; do ... ; done`, `if` → `fi`, `case` → `esac`, heredoc → 종료 구분자까지
  **하나의 명령 문자열 안에서 반드시 닫는다.**
  전송 직전 점검: 따옴표 짝, 괄호 짝, 백틱 짝, 파이프 뒤 피연산자 존재.
* **R0-2 루프 회피 (우선 선택)**
  여러 디렉터리·파일을 다룰 때 셸 루프를 쓰지 않고 루프 없는 단일 명령으로 대체한다.
  * 나열: `ls -d d1 d2 d3`
  * 탐색: `find -L /workspace/ -maxdepth 2 -name '*.yml'`
  * 검색: `grep -rn pat d1 d2 d3`
  * 대량 반복이 꼭 필요하면 셸 루프 대신 스크립트 파일을 작성해 1회 실행한다.
* **R0-3 stdin 차단**: 입력을 읽을 가능성이 있는 명령에 `</dev/null` 을 붙인다.
* **R0-4 타임아웃 강제**: `timeout 60 <cmd>` 로 감싸거나 `timeout_ms` 를 명시한다.
  60초 초과 예상 작업은 background 실행 후 폴링으로 처리한다.
* **R0-5 비대화형 강제**: `--no-pager`, `-y`, `-n`, `--quiet` 로 프롬프트·페이저를 차단한다.
  `git rebase -i`, `git add -i` 등 대화형 플래그 금지.
* **R0-6 정지 시 복구 절차** (타임아웃·무응답 시)
  1. **같은 명령 문자열을 재시도하지 않는다.**
  2. 구문 완결성을 먼저 재점검한다(R0-1).
  3. `echo ok` 또는 `ls -d <경로1>` 같은 최소 명령으로 환경 생존을 확인한다.
  4. 대상 경로를 하나씩 분해해 재실행한다.
* **R0-7 워크스페이스 파서 제약**
  dbt 명령에는 파이프·리다이렉트·`&&`·`;`·서브셸을 쓸 수 없다.
  단순 명령 1개만 사용하고 경로는 `--project-dir` 로 전달한다. `cd X && dbt ...` 금지.

## R1. 사전 준비 및 정보 파악

* **R1-1** 작업 시작 전 반드시 `20_issue/` 를 먼저 읽고 미해결·pending 항목을 파악한다.
* **R1-2** 지시가 `20_issue/` 와 충돌하면 `20_issue/` 를 우선하거나 사용자에게 문의한다. 임의 판단 금지.
* **R1-3 문서 전량 읽기 (파일 종류 무관)**
  `.md`, `.sql`, `.yml`, `.py`, `.csv` 등 **모든 파일**에 적용한다. 특정 문서에 한정되지 않는다.
  * **R1-3-1 전량 확보 필수**: 파일은 처음부터 끝까지 읽는다. 중간에 끊긴 상태에서 나머지 내용을 추론·단정하지 않는다.
  * **R1-3-2 분할 읽기로 이어 읽기**: `read` 툴은 1회 호출당 **최대 2000줄**, **1줄당 2000자**까지만 반환한다.
    이 한도로 잘리면 `offset`/`limit` 을 옮겨 **끝까지 반복 호출**해 전량 확보한다.
    이는 시간 제약(R0-4 `timeout 60`)과 **무관한 별개 문제**다. 시간을 이유로 읽기를 중단하지 않는다.
  * **R1-3-3 줄 수 선확인**: 대용량 파일은 `timeout 60 wc -l <경로>` 로 총 줄 수를 먼저 확인하고,
    필요한 호출 횟수를 계산해 전량 읽었는지 자가 검증한다.
  * **R1-3-4 bash 로 문서 읽기 금지**: `cat`/`head`/`tail` 은 출력 절단으로 내용이 손실된다.
    내용 파악은 반드시 `read` 툴을 쓴다. bash 는 줄 수·크기 확인 용도로만 쓴다.
  * **R1-3-5 부분 읽기 명시**: 사용자가 특정 구간만 요청한 경우에만 부분 읽기를 허용하고, 그 사실을 응답에 명시한다.
  * **R1-3-6 이력 파일 예외 (2026-08-11 O59-J 신설)**
    전량 독해 의무는 **정본**에만 적용한다. 정본 = 본 지침 · `20_issue/00_INDEX_이슈원장.md`(인덱스) ·
    `10_진단_원인분석.md` · `30_설계_의사결정.md` · `31_코드군_매핑등재부.md` · `40_…` · `50_dbt_…md` · `99_NEXT_SESSION.md`.
    **append-only 이력 파일**(`20_issue/01_세션이력.md`)은 **필요한 세션 구간만** 읽는다.
    * 🔴 **왜 예외가 필요한가**: 이력이 정본과 한 파일에 섞여 있어 원장이 **4,686줄/612KB** 까지 커졌고,
      `read` 1회 한도(2,000줄·1줄 2,000자·출력 10만자)를 넘겨 **R1-3 이 여러 세션 연속 미충족**이었다.
      예외를 명문화하지 않으면 다음 세션도 같은 곳에서 막히거나, **읽지 않고 읽은 척하게 된다.**
    * ⚠️ **예외의 한계**: 이력에서 **판정·수치를 근거로 인용하려면 그 세션 항목 전체를 읽는다.**
      부분 인용은 P170(분모 미확인 반박)·P154 오판의 실제 경로였다.
    * 🔴 **이력이 다시 커지면 정본이 아니라 이력을 쪼갠다.** 정본 파일이 1회 read 한도를 넘기면
      그것은 **정본에 이력이 섞였다는 신호**다 ⇒ 분리 대상이다(성격 혼합이 원인이고 크기는 증상이다).

## R2. 데이터 작업 및 검증 (실측 중심)

* **R2-1 사전 검증 우선**: 정본(yml 등)만으로 검증 가능한 항목은 **산출물 생산 전에** 검증한다.
  `dbt build` 를 단순 검증기로 사용하지 않는다.
* **R2-2 사후 검증 한정**: 물리적 반영 확인처럼 산출물 실체가 필요한 검증만 생산 이후에 수행한다.
* **R2-3 원본 실측**: COMMENT나 문서를 근거로 단정하지 않는다. `BRONZE` 스키마 원본을 직접 스캔한 결과만 근거로 삼는다.
* **R2-4 완료 판정 기준**: 완료 기준은 문서 작성이나 DDL 실행 여부가 아니라 **실제 스캔 결과**(INFORMATION_SCHEMA 스캔, P33)다.
* **R2-5 파일 상태 검증**: 파일 생성·수정 후 반드시 `cortex ws ls` 로 스테이지 실체를 확인한다(§9 P102).
  `/workspace` 마운트의 `ls` 성공은 스테이지 반영을 의미하지 않는다.
* **R2-6 메타데이터 분리**: 코드 COMMENT에는 코드값만 기록한다. 실측 수치는 문서10과 이슈 원장에만 기록한다.
