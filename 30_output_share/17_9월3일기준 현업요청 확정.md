## 1. 회원 및 발송 서비스 영역

### 1-1. [L-1] 마케팅·캠페인성 발송 vs 단순 행정통보성 발송 구분 기준 확정
* **요청 배경 및 의사결정 필요 사항**:
  * 발송 후 반응(중단·증액)을 측정할 때, 마케팅 자극성 메시지와 단순 행정/결과 통보성 메시지의 구분 기준 확정 필요.
  * 요건 정의(서비스 30~40)에는 총 발송 모수 산식만 있을 뿐 제외 필터링 룰이 없습니다.
* **DB 실측 근거** (🟢 [2026-09-08 O144-E] 실행 확인 · 상위 제목을 실측값으로 교체):
  * 2025년 중단 회원(115,129명)의 직전 발송 대조 결과, **중단 당일(D+0) 발송 비중이 62.1% (70,231건)** 에 달함.
  * 당일 발송 상위 제목 **실측**: `NN2-사단-CRM중단-A(경제)` **49.6%** · `문의답변_20190925` **17.1%** · `사복_CRM 중단회원(A경제적)` **7.8%** · `8월 미납중단안내_3,254` 3.4% · `4월 미납중단안내_2,777` 2.9% · `N-사단-CRM중단-D(기타)` 2.6%.
  * 🔴 **상위 6건만으로 이미 83% 를 넘고, 전부 「중단 처리 결과·미납 안내」 계열**입니다 — 즉 마케팅 자극이 아니라 **중단이 확정된 뒤 나간 통보**입니다.
  * 사후 통보 메시지를 모수에서 배제하지 않으면 "중단 처리가 완료되어 발송된 안내 문자"가 "발송을 받고 중단한 것"으로 인과관계가 정반대로 왜곡됨.
  * 🔴 **다만 「행정통보 몇 %」는 제목 문자열 분류에 의존하므로 DW 가 확정할 수 없습니다** — 아래 보강 쿼리는 패턴으로 잠정 분류한 것이고, **공식 분류 기준은 현업 회신 사항**입니다.
* **현업 확인 요청 사항**:
  1. 발송 템플릿 코드 또는 발송 유형 중 행정/통보성으로 분류하여 반응 모수에서 제외할 공식 기준.
  2. 🔴 제목 문자열이 아니라 **코드 컬럼으로 구분할 수 있는 축이 원천에 있는지**(예: 템플릿 유형·발송 목적 코드). 없다면 제목 패턴 규칙을 공식 승인해 주셔야 합니다.
* **실증 쿼리**:

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [1-1. L-1] 중단 회원의 직전 발송 당일(D+0) 상위 메시지 제목 실측
--
-- ▣ 이 쿼리가 답하는 질문
--   "중단 당일에 나간 발송은 실제로 어떤 메시지였나?"
--   → 제목을 보면 '마케팅 자극'인지 '중단 처리 결과 통보'인지 사람이 판단할 수 있다.
--
-- ▣ 읽는 법
--   원천: 중단이력(x) × 알림톡 발송상세(s) × 발송마스터(m)
--   조인 조건의 핵심 = `발송일(YYYYMMDD) = 중단일(spnsr_dscntc_de)` ⇒ **같은 날(D+0)만** 남긴다.
--   ⚠️ s.sndng_dt 는 TIMESTAMP 이므로 TO_CHAR 로 날짜만 잘라 문자열 중단일과 맞춘다.
--   비중_PCT = 윈도우 SUM 으로 낸 '당일 발송 전체 대비' 점유율이다(중단 전체 대비가 아니다).
--
-- ▣ 주의(오독 방지)
--   🔴 이 쿼리는 '발송이 중단을 유발했다'를 증명하지 않는다. 오히려 그 반대 가능성
--      (중단 처리 → 결과 통보 발송)을 보여 주는 것이 목적이다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    m.tit AS "발송제목",
    COUNT(*) AS "당일발송건수",
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS "비중_PCT"
FROM GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_SPNSR_DSCNTC x
JOIN GN_DW.BRONZE_CRM.TD_MS_MSG_AT_SNDNG_DTLS s
    ON s.mber_no = x.mber_no
   AND TO_CHAR(s.sndng_dt, 'YYYYMMDD') = x.spnsr_dscntc_de
JOIN GN_DW.BRONZE_CRM.TM_MS_MSG_AT_SNDNG m
    ON m.sndng_key = s.sndng_key
WHERE x.spnsr_dscntc_de BETWEEN '20250101' AND '20251231'
GROUP BY 1
ORDER BY 2 DESC
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────────
-- [1-1-B. L-1 보강 🆕] 행정통보성 vs 마케팅성 **비중을 직접 집계**
--
-- ▣ 왜 추가했나
--   종전 쿼리는 제목을 '나열'만 해서 「행정통보가 80% 이상」이라는 문서 주장을
--   **뒷받침하지 못했다**. 사람이 상위 20건을 눈으로 더해야 했다.
--   ⇒ 제목 패턴으로 잠정 분류하고 **비중을 숫자로 낸다**.
--
-- ▣ 분류 규칙 (🔴 잠정이며 현업 승인 대상)
--   중단/해지 처리 통보 : 제목에 '중단' 또는 '해지'
--   미납/납부 결과 통보 : '미납' · '납부' · '결과'
--   회원정보 변경 통보  : '변경' · '정보'
--   문의 응답           : '문의' · '답변'
--   그 외               : 마케팅성 후보
--
-- ▣ 읽는 법
--   이 결과에서 '마케팅성 후보' 비중이 작다면, 현재 반응 모수는 사실상
--   **사후 통보로 채워져 있다**는 뜻이다 ⇒ 필터링 룰 없이는 지표가 성립하지 않는다.
--
-- ▣ 주의
--   🔴 제목 문자열 분류는 **근거가 아니라 가설**이다. 원천에 목적 코드가 있으면
--      그 코드로 바꿔야 한다(위 현업 확인 요청 2번).
-- ─────────────────────────────────────────────────────────────────────
WITH d0 AS (
    SELECT m.tit
    FROM GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_SPNSR_DSCNTC x
    JOIN GN_DW.BRONZE_CRM.TD_MS_MSG_AT_SNDNG_DTLS s
        ON s.mber_no = x.mber_no
       AND TO_CHAR(s.sndng_dt, 'YYYYMMDD') = x.spnsr_dscntc_de
    JOIN GN_DW.BRONZE_CRM.TM_MS_MSG_AT_SNDNG m
        ON m.sndng_key = s.sndng_key
    WHERE x.spnsr_dscntc_de BETWEEN '20250101' AND '20251231'
)
SELECT
    CASE
        WHEN tit LIKE '%중단%' OR tit LIKE '%해지%' THEN '1.중단·해지 처리 통보'
        WHEN tit LIKE '%미납%' OR tit LIKE '%납부%' OR tit LIKE '%결과%' THEN '2.미납·납부 결과 통보'
        WHEN tit LIKE '%변경%' OR tit LIKE '%정보%' THEN '3.회원정보 변경 통보'
        WHEN tit LIKE '%문의%' OR tit LIKE '%답변%' THEN '4.문의 응답'
        ELSE '9.마케팅성 후보(그 외)'
    END AS "잠정분류",
    COUNT(*) AS "당일발송건수",
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS "비중_PCT",
    COUNT(DISTINCT tit) AS "제목종수"
FROM d0
GROUP BY 1
ORDER BY 1;
```

### 1-2. [L-1 부속] 채널별 반응 귀속 기간 차등 적용 여부

* **DB 실측 근거** (🟢 [2026-09-08 O144-E] 실행으로 전건 일치 확인):
  * 발송 후 중단 발생 시점 분포 **실측**: 당일(D+0) **62.1%(70,231건)** · D+1~5 **15.3%(17,262건)** · D+11~30 **12.5%(14,195건)** · D+6~10 **5.7%(6,501건)** · D+31~90 2.3%(2,550건) · D+91 이상 2.2%(2,445건).

  * 🔴 **한계**: 이 분포는 **채널 구분 없이 알림톡 기준으로만** 집계된 것입니다. 채널별 차등을 판단하려면 채널축이 필요하므로 아래 보강 쿼리를 추가했습니다.
  * 🟢🟢 **[보강 쿼리 실행 결과] 채널별 차등이 필요하다는 근거가 확보됐습니다.**

| 채널 | 중단건수 | D+0 | **D+5 누적** | D+30 누적 | **평균 간격** |
|---|---:|---:|---:|---:|---:|
| 알림톡 | 113,184 | 62.1% | **77.3%** | 95.6% | **9.8일** |
| 이메일 | 73,454 | 63.3% | **64.8%** | 78.5% | **41.5일** |

  * 🔴 **이메일은 D+5 누적이 64.8% 로 알림톡(77.3%)보다 12.5%p 낮고, 평균 간격이 41.5일 대 9.8일로 4배 이상 깁니다.**
  * ⇒ **일괄 D+5 를 적용하면 이메일 반응의 35% 가 모수에서 누락됩니다.** 채널 특성(알림톡은 즉시 확인, 이메일은 뒤늦게 열람)과 정합하는 결과입니다.
  * ⚠️ 우편은 회원별 발송 상세가 소량이어서 이 대조에서 제외했습니다 — **우편 귀속 기간은 별도 판단이 필요**합니다.
* **현업 확인 요청 사항**:
  1. 전 채널 일괄 D+5일 적용 여부, 또는 채널별(예: 우편 D+14일 등) 차등 적용 여부.
  2. 🔴 **D+11~30 구간(12.5%)을 반응으로 인정할지** — 인정하면 귀속 기간을 D+30 까지 늘려야 합니다.
* **실증 쿼리**:

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [1-2. L-1 부속] 발송 후 중단 발생 간격(D+n) 분포 실측
--
-- ▣ 이 쿼리가 답하는 질문
--   "발송을 받고 며칠 뒤에 중단하는가?" → 귀속 기간(D+5)을 몇 일로 잡아야 하는지의 근거.
--
-- ▣ 읽는 법 (2단 CTE)
--   stop      : 2025년 중단 사건을 회원·중단일 단위로 뽑는다.
--   prev_send : 각 중단 사건에 대해 **중단일 이전 마지막 발송일**을 MAX 로 찾는다.
--               ⇒ '직전 발송'을 1건으로 확정해야 간격이 하나로 정해진다.
--   최종 SELECT: DATEDIFF 로 간격을 구간화(D+0 / D+1~5 / ...)해 비중을 낸다.
--
-- ▣ 주의(오독 방지)
--   🔴 발송을 한 번도 받지 않은 중단 회원은 INNER JOIN 에서 빠진다
--      ⇒ 이 분포의 분모는 '중단 전체'가 아니라 **'직전 발송이 있는 중단'**이다.
--   🔴 간격이 짧다는 것이 '발송이 원인'을 뜻하지 않는다(§1-1 참조).
--   🔴 채널 구분이 없다 — 알림송 상세(TD_MS_MSG_AT_SNDNG_DTLS) 단일 원천이다.
-- ─────────────────────────────────────────────────────────────────────
WITH stop AS (
    SELECT mber_no, TO_DATE(spnsr_dscntc_de, 'YYYYMMDD') AS stop_date
    FROM GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_SPNSR_DSCNTC
    WHERE spnsr_dscntc_de BETWEEN '20250101' AND '20251231'
), prev_send AS (
    SELECT
        x.mber_no,
        x.stop_date,
        MAX(TO_DATE(s.sndng_dt)) AS last_send_date
    FROM stop x
    JOIN GN_DW.BRONZE_CRM.TD_MS_MSG_AT_SNDNG_DTLS s
        ON s.mber_no = x.mber_no
       AND TO_DATE(s.sndng_dt) <= x.stop_date
    GROUP BY x.mber_no, x.stop_date
)
SELECT
    CASE
        WHEN DATEDIFF(day, last_send_date, stop_date) = 0 THEN '당일(D+0)'
        WHEN DATEDIFF(day, last_send_date, stop_date) BETWEEN 1 AND 5 THEN 'D+1~5'
        WHEN DATEDIFF(day, last_send_date, stop_date) BETWEEN 6 AND 10 THEN 'D+6~10'
        WHEN DATEDIFF(day, last_send_date, stop_date) BETWEEN 11 AND 30 THEN 'D+11~30'
        WHEN DATEDIFF(day, last_send_date, stop_date) BETWEEN 31 AND 90 THEN 'D+31~90'
        ELSE 'D+91 이상'
    END AS "발송_중단_간격",
    COUNT(*) AS "중단건수",
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS "비중_PCT"
FROM prev_send
GROUP BY 1
ORDER BY 2 DESC;

-- ─────────────────────────────────────────────────────────────────────
-- [1-2-B. L-1 부속 보강 🆕] **채널별** 반응 간격 — 차등 적용 판단의 직접 근거
--
-- ▣ 왜 추가했나
--   현업 질문은 "채널별로 다르게 잡을까?" 인데, 종전 쿼리에는 **채널축이 없었다**.
--   ⇒ 알림톡·이메일 2채널을 UNION 으로 합쳐 **채널별 누적 도달률**을 낸다.
--
-- ▣ 읽는 법
--   D0_PCT / D5_누적_PCT / D30_누적_PCT 를 채널끼리 **가로로 비교**한다.
--   채널 간 D5 누적률 차이가 크면 → 차등 적용 근거가 된다.
--   차이가 작으면 → 일괄 D+5 로 충분하다는 근거가 된다.
--   ⇒ 🟢 **어느 쪽이든 이 표 하나로 결정할 수 있다**는 것이 이 쿼리의 목적이다.
--
-- ▣ 주의
--   🔴 채널별 발송상세 테이블의 **발송일 컬럼명이 서로 다르다** — 알림톡은 `SNDNG_DT`,
--      이메일은 `SNDNG_DE` 다(회원키는 둘 다 `MBER_NO`). 실측으로 확인한 사실이며,
--      같은 이름일 것이라 가정하면 컴파일 오류가 난다.
--   🔴 우편(`TM_MS_PSTMTR_SNDNG`)은 발송 **마스터**만 있고 회원별 상세가 소량이라
--      이 대조에서 제외했다 ⇒ 우편 귀속 기간은 이 표로 판단할 수 없다.
-- ─────────────────────────────────────────────────────────────────────
WITH stop AS (
    SELECT mber_no, TO_DATE(spnsr_dscntc_de, 'YYYYMMDD') AS stop_date
    FROM GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_SPNSR_DSCNTC
    WHERE spnsr_dscntc_de BETWEEN '20250101' AND '20251231'
), sends AS (
    SELECT '1.알림톡' AS ch, mber_no, TO_DATE(sndng_dt) AS send_date
    FROM GN_DW.BRONZE_CRM.TD_MS_MSG_AT_SNDNG_DTLS
    UNION ALL
    SELECT '2.이메일', mber_no, TO_DATE(sndng_de)   -- ⚠️ 이메일은 SNDNG_DE
    FROM GN_DW.BRONZE_CRM.TD_MS_EMAIL_SNDNG_DTLS
), gap AS (
    SELECT s.ch, x.mber_no, x.stop_date,
           MAX(s.send_date) AS last_send_date
    FROM stop x
    JOIN sends s
        ON s.mber_no = x.mber_no
       AND s.send_date <= x.stop_date
    GROUP BY s.ch, x.mber_no, x.stop_date
)
SELECT
    ch AS "채널",
    COUNT(*) AS "중단건수",
    ROUND(COUNT(CASE WHEN DATEDIFF(day, last_send_date, stop_date) = 0
                     THEN 1 END) * 100.0 / COUNT(*), 1) AS "D0_PCT",
    ROUND(COUNT(CASE WHEN DATEDIFF(day, last_send_date, stop_date) <= 5
                     THEN 1 END) * 100.0 / COUNT(*), 1) AS "D5_누적_PCT",
    ROUND(COUNT(CASE WHEN DATEDIFF(day, last_send_date, stop_date) <= 30
                     THEN 1 END) * 100.0 / COUNT(*), 1) AS "D30_누적_PCT",
    ROUND(AVG(DATEDIFF(day, last_send_date, stop_date)), 1) AS "평균간격_일"
FROM gap
GROUP BY 1
ORDER BY 1;
```

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [1-3. L-2] 중단보고 후원사업: 끊은 사업(가) vs 최초 유입 사업(나) 대조
--
-- ▣ 이 쿼리가 답하는 질문
--   "같은 약정인데 '획득 사업'과 '해지 사업'이 실제로 다른가? 어떤 조합으로 다른가?"
--
-- ▣ 읽는 법
--   acq CTE : 회원별 **최초 개발 시점의 사업**을 뽑는다.
--             MIN_BY(사업ID, 발생일) = '발생일이 가장 이른 행의 사업ID' ⇒ 이것이 '나(획득)'.
--   본문    : 중단 플래그가 'Y' 인 약정 사업(b)을 '가(해지)'로 두고 나란히 놓는다.
--   같은 값이 대각선처럼 나오면 일치, 서로 다른 칸이 나오면 불일치 조합이다.
--
-- ▣ 주의(오독 방지)
--   🔴 이 쿼리는 상위 20개 **조합만** 보여 준다 — 불일치'율'은 알 수 없다.
--      ⇒ 비율은 아래 [1-3-B] 로 직접 계산하라.
--   🔴 LEFT JOIN 으로 사업명을 붙이므로 마스터에 없는 사업ID 는 이름이 NULL 로 나온다.
-- ─────────────────────────────────────────────────────────────────────
WITH acq AS (
    SELECT mber_no,
           MIN_BY(spnsr_bsns_id, occrrnc_de) AS acq_spnsr_bsns_id
    FROM GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_DVLP_AMT
    WHERE spnsr_bsns_id IS NOT NULL
    GROUP BY mber_no
)
SELECT
    bn.spnsr_bsns_nm AS "획득_후원사업_나",
    bs.spnsr_bsns_nm AS "중단_후원사업_가",
    COUNT(*) AS "약정건수"
FROM GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_SPNSR_BSNS b
JOIN GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_SPNSR s
    ON s.spnsr_no = b.spnsr_no
JOIN acq a
    ON a.mber_no = s.mber_no
LEFT JOIN GN_DW.BRONZE_CRM.TM_CM_SPNSR_BSNS_INFO bn
    ON bn.spnsr_bsns_id = a.acq_spnsr_bsns_id
LEFT JOIN GN_DW.BRONZE_CRM.TM_CM_SPNSR_BSNS_INFO bs
    ON bs.spnsr_bsns_id = b.spnsr_bsns_id
WHERE b.spnsr_dscntc_yn = 'Y'
GROUP BY 1, 2
ORDER BY 3 DESC
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────────
-- [1-3-B. L-2 보강 🆕] 불일치율을 **직접 계산** — 「16.9%」의 근거
--
-- ▣ 왜 추가했나
--   문서는 「불일치 16.9%」라고 적었지만, 위 쿼리는 상위 20조합만 내므로
--   **그 수치를 확인할 수 없었다**. 분모·분자를 한 줄로 낸다.
--
-- ▣ 읽는 법
--   STOP_BSNS_ROWS = 분모 = 중단 플래그 'Y' 인 약정 사업 행수
--   MISMATCH_ROWS  = 분자 = 그중 획득 사업 ≠ 해지 사업 인 행수
--   ⚠️ `<>` 는 NULL 에 대해 참이 되지 않는다 ⇒ 획득 사업을 못 찾은 회원은
--      INNER JOIN 단계에서 이미 빠져 있어 분모에 포함되지 않는다.
-- ─────────────────────────────────────────────────────────────────────
WITH acq AS (
    SELECT mber_no, MIN_BY(spnsr_bsns_id, occrrnc_de) AS acq_id
    FROM GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_DVLP_AMT
    WHERE spnsr_bsns_id IS NOT NULL
    GROUP BY mber_no
)
SELECT
    COUNT(*) AS "중단약정_전체",
    COUNT(CASE WHEN b.spnsr_bsns_id <> a.acq_id THEN 1 END) AS "불일치_건수",
    ROUND(COUNT(CASE WHEN b.spnsr_bsns_id <> a.acq_id THEN 1 END)
          * 100.0 / COUNT(*), 2) AS "불일치율_PCT"
FROM GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_SPNSR_BSNS b
JOIN GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_SPNSR s ON s.spnsr_no = b.spnsr_no
JOIN acq a ON a.mber_no = s.mber_no
WHERE b.spnsr_dscntc_yn = 'Y';

-- ─────────────────────────────────────────────────────────────────────
-- [1-3-C. L-2 보강 🆕] 🔴 **동시중단 팬아웃 규모** — 이 결정의 영향 범위를 확정한다
--
-- ▣ 왜 이 쿼리가 가장 중요한가
--   "중단을 사업별로 어떻게 귀속하나"가 어려운 이유는 **한 회원이 같은 날 여러 사업을
--   동시에 중단**하기 때문이다. 사업이 1개뿐이면 어떤 규칙을 택해도 결과가 같다.
--   ⇒ 즉 **결정이 실제로 영향을 주는 범위**를 이 쿼리가 확정해 준다.
--   ⇒ 착수표 ⑭ 「현업 결정 전 배선 금지」가 풀리는 조건이 바로 이 규칙이다.
--
-- ▣ 읽는 법
--   x CTE : (회원, 중단일) 을 하나의 '중단 사건'으로 보고, 그 사건에서 중단된
--           **서로 다른 사업 수**를 센다.
--   본문   : 사업 수별로 사건이 몇 건인지 + 비중을 낸다.
--   SAME_DAY_BSNS_CNT = 1 인 비중이 크면 → 결정의 영향 범위가 작다는 뜻이다.
--
-- ▣ 결정별 파급 (회신 시 이 셋 중 하나를 골라 주십시오)
--   ㉠ 대표 1개 사업에만 귀속  → 나머지 사업의 중단이 보고서에서 사라진다
--   ㉡ 사업 수로 분수 배분     → 사업별 합이 정수가 아니게 된다(0.5건 등)
--   ㉢ 사업마다 1건씩 계상     → 사업별 합계 > 실제 중단 회원수 (중복계상 명시 필요)
-- ─────────────────────────────────────────────────────────────────────
WITH x AS (
    SELECT s.mber_no,
           b.spnsr_dscntc_de AS stop_de,
           COUNT(DISTINCT b.spnsr_bsns_id) AS bsns_n
    FROM GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_SPNSR_BSNS b
    JOIN GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_SPNSR s ON s.spnsr_no = b.spnsr_no
    WHERE b.spnsr_dscntc_yn = 'Y'
      AND b.spnsr_dscntc_de IS NOT NULL
    GROUP BY 1, 2
)
SELECT
    bsns_n AS "같은날_중단사업수",
    COUNT(*) AS "중단사건수",
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS "비중_PCT"
FROM x
GROUP BY 1
ORDER BY 1;
```

* **실증 쿼리**:

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [2-1. I-2] 특수문자 ')' 침투 행 실측 — 스캐너 유입 여부 판별
--
-- ▣ 이 쿼리가 답하는 질문
--   "깨진 값이 몇 건이고, 언제 들어왔나?"
--   → 특정 하루에 몰려 있으면 '취약점 스캐너가 폼을 찔러 본 흔적'이라는 가설이 성립한다.
--     여러 해에 흩어져 있으면 업무상 실제 입력일 가능성이 생긴다 ⇒ 처분이 달라진다.
--
-- ▣ 읽는 법
--   WHERE 절에 회원번호·채널·경로·상태·비고 등 **여러 컬럼을 OR 로** 나열한다.
--   ⇒ 어느 한 컬럼이라도 값이 정확히 ')' 이면 잡는다.
--   참여일로 GROUP BY 하므로 결과 행수 = 이상값이 발생한 **날짜 수**다.
--
-- ▣ 주의
--   🔴 `= ')'` 는 **정확히 그 한 글자**인 경우만 잡는다. ')' 를 포함한 긴 문자열은
--      잡히지 않는다 ⇒ 더 넓게 보려면 LIKE '%)%' 로 바꿔 재측정하라.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    TO_CHAR(partcpt_dt, 'YYYY-MM-DD') AS "참여일",
    COUNT(*) AS "이상값행수",
    COUNT(DISTINCT mber_no) AS "관여회원수"
FROM GN_DW.BRONZE_CRM.TD_MS_EVENT_PRTCPNT_DTL
WHERE mber_no = ')' OR partcpt_chnnl_cd = ')' OR partcpt_path_cd = ')'
   OR partcpt_stat_cd = ')' OR rm = ')' OR rm2 = ')'
GROUP BY 1
ORDER BY 1;

-- ─────────────────────────────────────────────────────────────────────
-- [2-2. I-2 부속] S+8자리 형식 회원번호 목록 (예시 확인용)
--
-- ▣ 이 쿼리의 한계 (🔴 이것만 보고 판단하지 말 것)
--   DISTINCT + LIMIT 20 이므로 **개수를 세지 않는다**. 「1,016건」 같은 수치는
--   이 쿼리로 확인할 수 없다 ⇒ 반드시 아래 [2-2-B] 를 함께 보라.
-- ─────────────────────────────────────────────────────────────────────
SELECT DISTINCT mber_no AS "S형식_회원번호"
FROM GN_DW.BRONZE_CRM.TD_MS_EVENT_PRTCPNT_DTL
WHERE REGEXP_LIKE(mber_no, '^S[0-9]{8}$')
ORDER BY 1
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────────
-- [2-2-B. I-2 보강 🆕] 🔴 **S+8자리가 정말 「마스터에 없는 이상치」인지 검증**
--
-- ▣ 왜 이 쿼리가 결정적인가
--   문서는 이 형식을 '비표준 이상치'로 보고 삭제 승인을 요청하려 했다.
--   그런데 `S+8자리`는 **일시회원(ONCE) 의 정규 회원번호 체계**일 수 있다.
--   ⇒ 삭제 승인을 요청하기 전에 **마스터 매칭률을 반드시 먼저 세야 한다.**
--
-- ▣ 읽는 법
--   S형식_종수      : S+8자리 고유 회원번호 개수 (= 문서가 '건수'로 오기한 값)
--   S형식_행수      : 실제 참여 기록 행수 (종수와 다르다 — 한 회원이 여러 번 참여)
--   마스터_매칭_종수 : 일시회원 마스터에 실재하는 것 ⇒ **정상 회원이므로 지우면 안 된다**
--   마스터_미매칭_종수: 진짜 처분 대상 후보
--
-- ▣ 판정 규칙
--   🔴 마스터_매칭_종수 가 크면 → 「이상치」 프레임 자체가 틀린 것이다.
--      정제 대상은 미매칭 분으로 좁혀야 한다.
--   ⚠️ LEFT JOIN 후 `o.once_mber_no IS NOT NULL` 로 매칭을 판정한다
--      (INNER JOIN 으로 세면 미매칭이 사라져 비교가 불가능해진다).
-- ─────────────────────────────────────────────────────────────────────
SELECT
    COUNT(DISTINCT p.mber_no) AS "S형식_종수",
    COUNT(*) AS "S형식_행수",
    COUNT(DISTINCT CASE WHEN o.once_mber_no IS NOT NULL
                        THEN p.mber_no END) AS "마스터_매칭_종수",
    COUNT(DISTINCT CASE WHEN o.once_mber_no IS NULL
                        THEN p.mber_no END) AS "마스터_미매칭_종수"
FROM GN_DW.BRONZE_CRM.TD_MS_EVENT_PRTCPNT_DTL p
LEFT JOIN GN_DW.BRONZE_CRM.TM_MM_ONCE_MBER_INFO o
       ON o.once_mber_no = p.mber_no
WHERE REGEXP_LIKE(p.mber_no, '^S[0-9]{8}$');
```

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [2-3. M-2, M-4] 채널별 발송 마스터의 발신유형·발송결과 코드값 분포
--
-- ▣ 이 쿼리가 답하는 질문
--   "같은 이름의 코드 컬럼인데 채널마다 값 집합이 다른가?"
--   → 다르면 채널별로 별도 코드군을 써야 하고, 같으면 하나로 통합할 수 있다.
--
-- ▣ 읽는 법
--   UNION ALL 로 채널별 테이블을 이어 붙이고 첫 컬럼에 채널 이름을 문자열로 박는다.
--   ⇒ 결과를 채널 기준으로 세로로 읽으면 **각 채널의 도메인(값 집합)**이 보인다.
--   ⚠️ 마지막 블록은 발신유형이 아니라 **발송결과**(sndng_rst_cd)다 — 컬럼 의미가 다르므로
--      "(결과)" 라고 표시해 두었다. 같은 표에 있다고 같은 축으로 비교하지 말 것.
--
-- ▣ 주의
--   🔴 값이 공백으로 보이는 행은 NULL 이다 — '없음'이 아니라 '미기재'다.
-- ─────────────────────────────────────────────────────────────────────
SELECT 'EMAIL TM_MS_EMAIL_SNDNG' AS "채널", sndng_ty_cd AS "발신유형코드", COUNT(*) AS "행수"
FROM GN_DW.BRONZE_CRM.TM_MS_EMAIL_SNDNG GROUP BY 1, 2
UNION ALL
SELECT 'MSG_AT TM_MS_MSG_AT_SNDNG', sndng_ty_cd, COUNT(*)
FROM GN_DW.BRONZE_CRM.TM_MS_MSG_AT_SNDNG GROUP BY 1, 2
UNION ALL
SELECT 'EMAIL TD_MS_EMAIL_SNDNG_DTLS (결과)', sndng_rst_cd, COUNT(*)
FROM GN_DW.BRONZE_CRM.TD_MS_EMAIL_SNDNG_DTLS GROUP BY 1, 2
ORDER BY 1, 2;

-- ─────────────────────────────────────────────────────────────────────
-- [2-4. M-5, M-6] 통신사 전송실패코드 중 공통코드 사전 미등재 현황
--
-- ▣ 이 쿼리가 답하는 질문
--   "어떤 실패코드가 사전에 없어서 한글 라벨을 붙일 수 없나?"
--
-- ▣ 🔴 종전 쿼리에서 고친 점 (중요)
--   종전에는 `trnsms_failr_cd_id NOT IN (SELECT dtl_cd_id ...)` 였다.
--   SQL 의 `NOT IN` 은 **서브쿼리 결과에 NULL 이 하나라도 있으면 전체가 UNKNOWN** 이 되어
--   행이 조용히 사라진다 ⇒ 「몇 종」이 실제와 달라질 수 있다.
--   ⇒ `NOT EXISTS` 로 바꿨다. NOT EXISTS 는 NULL 에 안전하다.
--
-- ▣ 읽는 법
--   결과 행수 = 사전에 없는 **코드 종수**. ROWS_N 은 그 코드가 실제로 찍힌 행수다.
--   행수가 큰 코드부터 라벨을 받는 것이 효율적이다(상위 2종이 대부분을 차지).
-- ─────────────────────────────────────────────────────────────────────
SELECT
    d.trnsms_failr_cd_id AS "미등재_실패코드",
    COUNT(*) AS "행수",
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS "미등재내_비중_PCT"
FROM GN_DW.BRONZE_CRM.TD_MS_MSG_AT_SNDNG_DTLS d
WHERE d.trnsms_failr_cd_id IS NOT NULL
  AND NOT EXISTS (
        SELECT 1 FROM GN_DW.BRONZE_CRM.TC_CMMN_DTL_CD c
        WHERE c.cd_id IN ('MS056', 'MS057', 'MS058', 'MS059')
          AND c.dtl_cd_id = d.trnsms_failr_cd_id)
GROUP BY 1
ORDER BY 2 DESC;

-- ─────────────────────────────────────────────────────────────────────
-- [2-4-B. M-5 보강 🆕] 분모 대조 — 「사전이 비었나, 이 코드만 빠졌나」를 구별
--
-- ▣ 왜 추가했나
--   미등재 종수만 보면 "사전 자체가 부실한 것"처럼 읽힌다.
--   ⇒ 실패코드 전체 종수 · 사전 보유 코드수를 **함께** 내서 원인을 좁힌다.
--
-- ▣ 읽는 법
--   실패코드_전체종수 vs 미등재_종수 를 비교한다.
--   사전보유_코드수 가 충분히 크면 → 사전은 정상이고 **특정 코드만 누락**된 것이다
--   ⇒ 현업에 요청할 것은 '사전 전면 정비'가 아니라 **누락 코드의 라벨**이다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    (SELECT COUNT(DISTINCT trnsms_failr_cd_id)
       FROM GN_DW.BRONZE_CRM.TD_MS_MSG_AT_SNDNG_DTLS
      WHERE trnsms_failr_cd_id IS NOT NULL)              AS "실패코드_전체종수",
    (SELECT COUNT(DISTINCT d.trnsms_failr_cd_id)
       FROM GN_DW.BRONZE_CRM.TD_MS_MSG_AT_SNDNG_DTLS d
      WHERE d.trnsms_failr_cd_id IS NOT NULL
        AND NOT EXISTS (SELECT 1 FROM GN_DW.BRONZE_CRM.TC_CMMN_DTL_CD c
                         WHERE c.cd_id IN ('MS056','MS057','MS058','MS059')
                           AND c.dtl_cd_id = d.trnsms_failr_cd_id)) AS "미등재_종수",
    (SELECT COUNT(*) FROM GN_DW.BRONZE_CRM.TC_CMMN_DTL_CD
      WHERE cd_id IN ('MS056','MS057','MS058','MS059'))  AS "사전보유_코드수";
```

* **현업 확인 요청 사항**:
  1. `SNDNG_TY_CD`(발신유형)의 공식 코드군 ID — 채널별로 다른 체계를 쓰는 것이 **의도된 설계**입니까?
  2. `SNDNG_RST_CD`(발송결과) `1`·`0` 의 공식 한글 라벨과 코드군 ID.
  3. `EVENT_DIV_CD`(행사구분)의 공식 코드군 ID.
* **파급**: 확정 전까지 시맨틱 뷰·마트의 해당 라벨은 **NULL 또는 원천값 그대로** 제공되며 한글 라벨 집계가 불가합니다.
* **실증 쿼리**:

```sql
-- [2-5. D/SVL-1~4] 채널별 발신유형(SNDNG_TY_CD) 및 발송결과 코드값 분포
SELECT 'EMAIL TM_MS_EMAIL_SNDNG (SNDNG_TY_CD)' AS "원천구분", sndng_ty_cd AS "코드값", COUNT(*) AS "행수"
FROM GN_DW.BRONZE_CRM.TM_MS_EMAIL_SNDNG GROUP BY 1, 2
UNION ALL
SELECT 'MSG_AT TM_MS_MSG_AT_SNDNG (SNDNG_TY_CD)', sndng_ty_cd, COUNT(*)
FROM GN_DW.BRONZE_CRM.TM_MS_MSG_AT_SNDNG GROUP BY 1, 2
UNION ALL
SELECT 'PSTMTR TM_MS_PSTMTR_SNDNG (SNDNG_TY_CD)', sndng_ty_cd, COUNT(*)
FROM GN_DW.BRONZE_CRM.TM_MS_PSTMTR_SNDNG GROUP BY 1, 2
UNION ALL
SELECT 'EMAIL TD_MS_EMAIL_SNDNG_DTLS (SNDNG_RST_CD)', sndng_rst_cd, COUNT(*)
FROM GN_DW.BRONZE_CRM.TD_MS_EMAIL_SNDNG_DTLS GROUP BY 1, 2
UNION ALL
SELECT '일반행사 TM_MS_EVENT (EVENT_DIV_CD)', event_div_cd, COUNT(*)
FROM GN_DW.BRONZE_CRM.TM_MS_EVENT GROUP BY 1, 2
ORDER BY 1, 2;

-- ─────────────────────────────────────────────────────────────────────
-- [2-6. D/SVL-1~4 보강 🆕] 🔴 **판별력 있는 후보 추출** — 종전 쿼리를 교체했다
--
-- ▣ 종전 쿼리가 왜 쓸모없었나 (실행해 보고 알았다)
--   종전에는 `TC_CMMN_DTL_CD` 를 `dtl_cd_id` **하나만으로** 조인했다.
--   상세코드 값이 '100', '300' 처럼 짧은 숫자라서, 의미가 전혀 다른 코드군까지
--   전부 매칭됐다 — 실행 결과에 `PM019 휴대폰결과`, `CM021 직군코드`,
--   `CM008 홍보방법` 이 나란히 붙어 나왔다. ⇒ **후보를 좁혀 주지 못한다.**
--
-- ▣ 그래서 판정식을 바꿨다 — 「포함관계」로 좁힌다
--   후보 코드군이 맞다면 반드시 다음이 성립한다:
--     **원천에 실재하는 값 집합 ⊆ 그 코드군의 상세코드 집합**
--   ⇒ 원천 값 중 **단 하나라도** 코드군에 없으면 그 코드군은 후보에서 탈락이다.
--   이 쿼리는 그 조건을 통과한 코드군만 남긴다.
--
-- ▣ 읽는 법
--   src        : 원천 EVENT_DIV_CD 의 고유값과 종수를 구한다(= 반드시 덮여야 하는 집합).
--   cand       : 모든 코드군에 대해, 원천 값을 몇 개 덮는지 센다.
--   최종 SELECT: 덮은 개수 = 원천 종수 인 코드군만 남긴다(=완전 포함).
--   결과가 1건이면 → 그 코드군으로 확정 제안 가능.
--   결과가 여러 건이면 → 배타적 특정 불가 ⇒ **현업 회신이 반드시 필요**하다는 증거.
--   결과가 0건이면 → 어떤 코드군도 원천을 다 덮지 못한다 ⇒ 사전 보강이 필요하다.
--
-- ▣ 주의
--   🔴 「완전 포함」은 필요조건이고 충분조건이 아니다 — 우연히 덮는 코드군도 있다.
--      그래서 코드군명·라벨 예시를 함께 내어 **사람이 의미로 최종 판단**하게 한다.
-- ─────────────────────────────────────────────────────────────────────
WITH src AS (
    SELECT DISTINCT event_div_cd AS v
    FROM GN_DW.BRONZE_CRM.TM_MS_EVENT
    WHERE event_div_cd IS NOT NULL
), src_n AS (
    SELECT COUNT(*) AS need FROM src
), cand AS (
    SELECT d.cd_id,
           COUNT(DISTINCT s.v) AS covered
    FROM GN_DW.BRONZE_CRM.TC_CMMN_DTL_CD d
    JOIN src s ON s.v = d.dtl_cd_id
    GROUP BY d.cd_id
)
SELECT
    c.cd_id AS "후보_코드군ID",
    cc.cd_nm AS "코드군명",
    c.covered AS "덮은_원천값수",
    (SELECT need FROM src_n) AS "덮어야_할_원천값수",
    (SELECT COUNT(*) FROM GN_DW.BRONZE_CRM.TC_CMMN_DTL_CD z
      WHERE z.cd_id = c.cd_id) AS "코드군_상세코드수",
    LISTAGG(d2.dtl_cd_id || '=' || d2.dtl_cd_nm, ' · ')
        WITHIN GROUP (ORDER BY d2.dtl_cd_id) AS "라벨_예시"
FROM cand c
JOIN GN_DW.BRONZE_CRM.TC_CMMN_CD cc ON cc.cd_id = c.cd_id
JOIN GN_DW.BRONZE_CRM.TC_CMMN_DTL_CD d2
      ON d2.cd_id = c.cd_id
     AND d2.dtl_cd_id IN (SELECT v FROM src)
WHERE c.covered = (SELECT need FROM src_n)     -- 🔴 완전 포함만 남긴다
GROUP BY 1, 2, 3, 4, 5
ORDER BY 5;
```

```sql
--      문자 순서로 정렬되므로 숫자 크기와 다를 수 있다 — 자리수별로 나눠 봐야 안전하다.

--   "깨진 값 하나하나가 몇 행·몇 명인가?" → 센티넬(소수)과 패딩누락(다수)을 구별한다.

-- [2-9. A 보강 🆕] 🔴 **보정식 검증** — 두 후보식을 나란히 놓고 결과를 본다

-- ▣ 왜 이 쿼리가 필요했나
--   문서는 「LPAD 보정 승인」을 요청하려 했다. 그런데 실행해 보니
--   `LPAD('20251',6,'0')` = **'020251'** 이다 — 연도가 0202 년이 되어 **무의미**하다.
--   ⇒ 승인 요청을 보내기 **전에** 식이 옳은지 검증해야 한다.
--
-- ▣ 두 후보식
--   naive_lpad : LPAD(값,6,'0')                        ⇒ 앞에 0 → 연도가 깨진다 🔴
--   ym_fix     : LEFT(값,4) ‖ LPAD(RIGHT(값,1),2,'0')  ⇒ 연도 4자리 보존 + 월에만 0 🟢
--
-- ▣ 읽는 법
--   기존_6자리_행수 = 보정 후 귀속될 달에 **이미 존재하는** 행수다.
--   ⇒ 0 이 아니면 '키 충돌'이 아니라 **같은 달 실적에 합산(병합)**된다는 뜻이다.
--     회비 실적은 월 단위 합산이 정상이므로 병합은 안전하다.
--   ⇒ 만약 0 이라면 그 달 실적이 전부 5자리로만 들어온 것이므로 더더욱 보정이 필요하다.
--
-- ▣ 주의
--   🔴 ym_fix 는 5자리가 「연4+월1」 구조라는 가정에 기댄다. 실측상 20251~20259 가
--      2025년 1~9월과 정확히 대응하므로 성립하지만, **가정임을 명시**한다.
-- ─────────────────────────────────────────────────────────────────────
WITH five AS (
    SELECT DISTINCT
           mbrfee_mt AS raw5,
           LPAD(mbrfee_mt, 6, '0') AS naive_lpad,
           LEFT(mbrfee_mt, 4) || LPAD(RIGHT(mbrfee_mt, 1), 2, '0') AS ym_fix
    FROM GN_DW.BRONZE_CRM.TM_PM_MBRFEE_ACMSLT
    WHERE LENGTH(mbrfee_mt) = 5
)
SELECT
    f.raw5 AS "원천_5자리값",
    f.naive_lpad AS "종전식_LPAD_결과",
    f.ym_fix AS "올바른식_결과",
    (SELECT COUNT(*) FROM GN_DW.BRONZE_CRM.TM_PM_MBRFEE_ACMSLT a
      WHERE a.mbrfee_mt = f.raw5)   AS "보정대상_5자리_행수",
    (SELECT COUNT(*) FROM GN_DW.BRONZE_CRM.TM_PM_MBRFEE_ACMSLT a
      WHERE a.mbrfee_mt = f.ym_fix) AS "기존_6자리_행수",
    (SELECT COUNT(*) FROM GN_DW.BRONZE_CRM.TM_PM_MBRFEE_ACMSLT a
      WHERE a.mbrfee_mt = f.naive_lpad) AS "종전식_결과값_기존행수"
FROM five f
ORDER BY 1;
```

```sql
-- [2-10. E] 행사 참여 외래키 고아행(행사 마스터 부재) 비율
--
-- ▣ 이 쿼리가 답하는 질문
--   "참여 기록이 가리키는 행사가 마스터에 실제로 있나?"
--
-- ▣ 읽는 법
--   LEFT JOIN 후 `e.event_cd IS NULL` 이면 **마스터에서 짝을 찾지 못한 것** = 고아행이다.
--   ⚠️ LEFT JOIN 이어야 한다 — INNER JOIN 으로 세면 고아행이 사라져 0% 가 나온다.
--   두 블록(일반행사·캠페인행사)을 UNION ALL 로 나란히 놓아 **비교**하는 것이 목적이다.
--
-- ▣ 주의(오독 방지)
--   🔴 이 비율은 **행수** 기준이다. 종수 기준과 크게 다를 수 있다
--      (실측: 종수로는 8.8% 인데 행수로는 26.79% ⇒ 대형 행사가 빠졌다는 신호).
--      ⇒ 반드시 아래 [2-12] 를 함께 보라.
-- ─────────────────────────────────────────────────────────────────────
SELECT '일반행사 TD_MS_EVENT_PRTCPNT_DTL' AS "참여원천",
    COUNT(*) AS "참여행_전체",
    COUNT(CASE WHEN e.event_cd IS NULL THEN 1 END) AS "고아행_마스터부재",
    ROUND(COUNT(CASE WHEN e.event_cd IS NULL THEN 1 END) * 100.0 / COUNT(*), 2) AS "고아비율_PCT"

LEFT JOIN GN_DW.BRONZE_CRM.TM_MS_EVENT e
    ON p.event_cd = e.event_cd
UNION ALL
SELECT '캠페인행사 TD_MS_CRMN_PRTCPNT',
    COUNT(*),
    COUNT(CASE WHEN c.crmn_cd IS NULL THEN 1 END),
    ROUND(COUNT(CASE WHEN c.crmn_cd IS NULL THEN 1 END) * 100.0 / COUNT(*), 2)

-- ─────────────────────────────────────────────────────────────────────
-- [2-11. B] 행사 참여 회원번호의 회원 마스터 부재 **유형별** 분포

--     S+8자리            → 일시회원 체계 ⇒ 다른 마스터를 봐야 한다
--     1~2자 짧은 ID      → 테스트·오입력 ⇒ 폐기 후보
--
-- ▣ 읽는 법
--   NOT EXISTS 를 **정기·일시 두 마스터 모두**에 걸어 '어느 쪽에도 없는' 것만 남긴다.
--   ⚠️ 일시회원 마스터의 키는 `mber_no` 가 아니라 `once_mber_no` 다 — 컬럼명이 다르다.

    CASE
        WHEN REGEXP_LIKE(p.mber_no, '^[0-9]{7}$') THEN '정상 7자리 FDRM'
        WHEN REGEXP_LIKE(p.mber_no, '^S[0-9]{8}$') THEN 'ONCE S+8자리'
        WHEN LENGTH(p.mber_no) <= 2 THEN '짧은/비정상 ID'
        ELSE '기타'
    END AS "유형",

    COUNT(*) AS "참여행수"

WHERE NOT EXISTS (
        SELECT 1 FROM GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_INFO m
        WHERE m.mber_no = p.mber_no)
  AND NOT EXISTS (
        SELECT 1 FROM GN_DW.BRONZE_CRM.TM_MM_ONCE_MBER_INFO o
        WHERE o.once_mber_no = p.mber_no)
GROUP BY 1
ORDER BY 2 DESC;

-- ─────────────────────────────────────────────────────────────────────
-- [2-12. B/E 보강 🆕] 🔴 **연도별 고아 추이** — 「추출 기간 누락」인지 판별한다
--
-- ▣ 왜 추가했나
--   현업 질문은 "추출 조건이 걸려 있나?" 인데, 종전 쿼리는 **전체 비율 한 줄**만 냈다.
--   ⇒ 원인을 좁힐 수 없었다. 연도축을 넣으면 패턴으로 원인이 갈린다.
--
-- ▣ 판정 규칙 (이 표를 이렇게 읽으십시오)
--   ㉠ **과거 연도만** 고아 → 마스터를 최근 것만 추출했다(기간 하한 존재)
--   ㉡ **최근 연도만** 고아 → 마스터 적재가 최신을 따라가지 못한다(증분 누락)
--   ㉢ **전 연도 고르게**   → 코드 체계 자체가 다르다(조인키 문제)
--   ⇒ 실측은 ㉡ 패턴이었다(2025년 36.7% · 2026년 49.9%).
--
-- ▣ 읽는 법
--   partcpt_dt 를 연도로 잘라 그룹핑하고, 그 안에서 고아행 수를 센다.
--   고아율_PCT 가 연도별로 어떻게 움직이는지가 핵심이다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    LEFT(TO_CHAR(p.partcpt_dt, 'YYYYMMDD'), 4) AS "참여연도",
    COUNT(*) AS "참여행수",
    COUNT(CASE WHEN e.event_cd IS NULL THEN 1 END) AS "고아행수",
    ROUND(COUNT(CASE WHEN e.event_cd IS NULL THEN 1 END) * 100.0
          / NULLIF(COUNT(*), 0), 2) AS "고아율_PCT"
FROM GN_DW.BRONZE_CRM.TD_MS_EVENT_PRTCPNT_DTL p
LEFT JOIN GN_DW.BRONZE_CRM.TM_MS_EVENT e
       ON e.event_cd = p.event_cd
GROUP BY 1
ORDER BY 1;

-- ─────────────────────────────────────────────────────────────────────
-- [2-13. B/E 보강 🆕] **종수 대비 행수** — 「소수의 대형 행사가 빠졌나」를 본다
--
-- ▣ 왜 추가했나
--   고아 26.79% 만 보면 "행사 마스터의 1/4 이 없다"로 오독한다.
--   실제로는 **종수로는 8.8% 인데 행수로 26.79%** ⇒ 참여자가 많은 대형 행사
--   몇 개가 빠진 것이다. 이 구별이 재추출 우선순위를 정한다.
--
-- ▣ 읽는 법
--   마스터_행수        : 마스터가 담고 있는 행사 수 (실측 376)
--   참조된_행사코드_종수: 참여 기록이 실제로 가리키는 행사 수 (실측 341)
--   고아_행사코드_종수  : 그중 마스터에 없는 것 (실측 30)
--   ⇒ 고아 종수는 작은데 고아 행수가 크면 **대형 행사 누락**이다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    (SELECT COUNT(*) FROM GN_DW.BRONZE_CRM.TM_MS_EVENT) AS "마스터_행수",
    COUNT(DISTINCT p.event_cd) AS "참조된_행사코드_종수",
    COUNT(DISTINCT CASE WHEN e.event_cd IS NULL
                        THEN p.event_cd END) AS "고아_행사코드_종수",
    COUNT(CASE WHEN e.event_cd IS NULL THEN 1 END) AS "고아_참여행수"
FROM GN_DW.BRONZE_CRM.TD_MS_EVENT_PRTCPNT_DTL p
LEFT JOIN GN_DW.BRONZE_CRM.TM_MS_EVENT e
       ON e.event_cd = p.event_cd;
```

```sql
--
-- ▣ 이 쿼리가 답하는 질문
--   "컬럼은 있는데 값이 정말 하나도 없나?"
--
-- ▣ 읽는 법
--   전체행수 vs 값있는행수 를 비교한다. `COUNT(컬럼)` 은 **NULL 을 세지 않는다**
--   ⇒ 값있는행수 = 0 이면 전건 NULL 이다.
--   ⚠️ `COUNT(*)` 와 `COUNT(컬럼)` 의 차이가 이 쿼리의 핵심 장치다.
--
-- ▣ 주의(오독 방지)
--   🔴 값있는행수 0 은 **「0 이라는 값이 들어있다」가 아니다** — 아무것도 없다는 뜻이다.
--      따라서 집계 시 0 으로 취급해서는 안 된다(합계·평균이 거짓이 된다).
--   🔴 이 결과가 '미수집'인지 '추출 누락'인지는 **DW 가 판단할 수 없다** ⇒ 그래서 요청 항목이다.
-- ─────────────────────────────────────────────────────────────────────
SELECT 'BRONZE_AGENCY.VIDEO_AD_CMPGN_DTLS.CONV_CALL_CNT' AS "대상",
       COUNT(*) AS "전체행수", COUNT(conv_call_cnt) AS "값있는행수"
FROM GN_DW.BRONZE_AGENCY.VIDEO_AD_CMPGN_DTLS
UNION ALL
SELECT 'BRONZE_AGENCY.DGT_AD_CMPGN_DTLS.MEDIA_PTNT_CUST_CNT',
       COUNT(*), COUNT(media_ptnt_cust_cnt)
FROM GN_DW.BRONZE_AGENCY.DGT_AD_CMPGN_DTLS
UNION ALL
SELECT 'BRONZE_CRM.TD_MS_MSG_AT_LQY_SNDNG.TOT_CLICK_CNT_CTNT',
       COUNT(*), COUNT(tot_click_cnt_ctnt)
FROM GN_DW.BRONZE_CRM.TD_MS_MSG_AT_LQY_SNDNG;

-- ─────────────────────────────────────────────────────────────────────
-- [2-15. D 부속] DW 가 이미 사유를 명시한 컬럼 전량 (고정 수치 대신 **세는 법**)
--
-- ▣ 이 쿼리가 답하는 질문
--   "DW 는 이 결손들을 어떻게 문서화해 두었나?"
--   → 이미 사유가 발행된 컬럼은 **분석가가 오독하지 않는다** ⇒ 조치 완료분이다.
--
-- ▣ 왜 문서에 개수를 적지 않고 쿼리를 두었나
--   🔴 「5개 컬럼」처럼 개수를 문서에 박으면 반드시 stale 이 된다.
--      ⇒ 항상 이 쿼리로 **현재 수를 센다**.
--
-- ▣ 주의
--   🔴 `WIDE_AD_COMBINED` 계열에 붙은 「원천 부재」 COMMENT 는 **위성 완전분할에 따른
--      정상 NULL** 이며 이 절의 결손과 다른 축이다 — 같은 표에 섞어 세지 말 것.
-- ─────────────────────────────────────────────────────────────────────
SELECT TABLE_SCHEMA, TABLE_NAME, COLUMN_NAME, COMMENT
FROM GN_DW.INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA IN ('GOLD', 'SILVER')
  AND (COMMENT ILIKE '%원천 부재%' OR COMMENT ILIKE '%원천 미수집%')
ORDER BY 1, 2, 3;
```

### 3-1. [N-1 ~ N-4] 개발목표 원천 입고 범위 및 지표 대체 여부
* **요청 배경 및 의사결정 필요 사항**:
  * '월 목표(건)'와 기존 '연사업목표(건)'의 동일 지표 여부.
  * (명)/(원) 단위나 신규/기존 분해가 추가된 10건의 지표 번호 대체 여부.
  * 부서별 개발목표 외 '활동회원 목표' 및 '금액(원) 목표'의 원천 제공 여부.
* **DB 실측 근거** (🟢 [2026-09-08 O144-E] 실행 · **신규 발견 포함**):
  * 현재 원천(`BRONZE_CRM.TM_CM_MBER_DVLP_GOAL`)은 총 25,344행(2020~2026년 · 연도별 69~76개 부서 · 12개월)이며 **'부서별 건수 목표'만** 존재합니다. 금액(원) 및 활동회원 목표는 부재합니다.
  * 🔴🔴 **신규 발견 — 개발구분 3종 중 2종은 사실상 목표가 설정돼 있지 않습니다.**

| 개발구분코드 | 라벨(`MM003`) | 행수 | 목표건수 합계 | 목표>0 인 행수 |
|---|---|---:|---:|---:|
| `1` | 신규 | 13,668 | **4,577,473** | **10,629** |
| `2` | 증액 | 5,844 | 39,732 | 🔴 **36** |
| `4` | 지정교체 | 5,832 | 4,898 | 🔴 **12** |

  * ⇒ `증액`·`지정교체` 는 행은 각각 5천여 개 있는데 **목표값이 들어간 행이 36개·12개뿐**입니다. 즉 **행은 만들어졌지만 목표가 채워지지 않은 빈 껍데기**입니다.
  * 🔴 이대로 「개발목표 달성률」을 산출하면 증액·지정교체의 분모가 0 이 되어 **달성률이 무한대 또는 NULL** 로 나옵니다.
  * `SILVER.CRM_BIZ_TARGET` 은 원천 부재로 0행 스텁 상태입니다.
* **현업 확인 요청 사항**:
  1. 신규 개발 중인 목표 데이터(`법인>부서>팀>유입채널`)에 건수 외 금액(원) 목표 포함 여부 확인.
  2. 🔴 **`증액`(코드 2)·`지정교체`(코드 4) 에 목표를 설정하는 업무가 실제로 있습니까?** 없다면 이 두 구분은 **달성률 산출 대상에서 제외**하겠습니다(있다면 목표값 입고가 필요합니다).
  3. '월 목표(건)'과 기존 '연사업목표(건)'이 같은 지표인지 확정.
* **실증 쿼리**:

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [3-1. N-1~N-4] 개발목표 원천 데이터 적재 범위 실측
--
-- ▣ 이 쿼리가 답하는 질문
--   "목표 원천은 어느 연도·어느 구분·몇 개 부서까지 담고 있나?"
--   → 요건이 요구하는 축(금액·활동회원)이 원천에 있는지 없는지 판별하는 출발점.
--
-- ▣ 읽는 법
--   기준연도 × 개발구분코드로 그룹핑한다.
--   부서수·월수는 COUNT(DISTINCT) 이므로 **커버리지**를 뜻한다(월수 12 면 연중 전체).
--   목표건수_합계 가 0 이면 → 행은 있는데 **값이 비어 있다**는 신호다(아래 3-1-B 로 확인).
--
-- ▣ 주의
--   🔴 SUM 은 NULL 을 무시한다 ⇒ 합계 0 과 '전건 NULL' 이 구별되지 않는다.
--      그래서 아래 [3-1-B] 에서 `목표>0 인 행수` 를 따로 센다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    stdyy AS "기준연도",
    mber_dvlp_div_cd AS "개발구분코드",
    COUNT(*) AS "행수",
    COUNT(DISTINCT dept_id) AS "부서수",
    COUNT(DISTINCT stdr_mt) AS "월수",
    SUM(goal_cnt) AS "목표건수_합계"
FROM GN_DW.BRONZE_CRM.TM_CM_MBER_DVLP_GOAL
GROUP BY 1, 2
ORDER BY 1 DESC, 2;

-- ─────────────────────────────────────────────────────────────────────
-- [3-1-B. N-1~N-4 보강 🆕] 🔴 **개발구분코드의 뜻 + 목표 미설정 실태**
--
-- ▣ 왜 추가했나
--   종전 쿼리는 개발구분코드를 `1`·`2`·`4` 라는 **숫자로만** 냈다. 현업도 우리도
--   그게 무슨 구분인지 모른 채 집계를 읽어야 했다.
--   ⇒ 공통코드 사전(MM003)을 조인해 **라벨을 붙이고**, 동시에
--     "행은 있는데 목표값이 비었는지"를 함께 센다.
--
-- ▣ 읽는 법
--   행수            : 그 구분으로 만들어진 목표 행의 개수
--   목표설정된_행수 : 그중 goal_cnt > 0 인 행 ⇒ **실제로 목표가 입력된 행**
--   목표설정률_PCT  : 둘의 비율. 🔴 이 값이 매우 낮으면 **빈 껍데기 행**이라는 뜻이다.
--   ⇒ 달성률 지표의 분모로 쓸 수 있는지가 이 컬럼으로 판정된다.
--
-- ▣ 주의
--   🔴 코드군 `MM003` 은 **추정**이다(라벨이 '신규/증액/지정교체'로 맞게 나오지만
--      배타적으로 확정된 것은 아니다) ⇒ 라벨이 NULL 로 나오면 코드군을 바꿔 찾아야 한다.
--   ⚠️ LEFT JOIN 이므로 사전에 없어도 행이 사라지지 않는다(라벨만 빈다).
-- ─────────────────────────────────────────────────────────────────────
SELECT
    g.mber_dvlp_div_cd AS "개발구분코드",
    MAX(d.dtl_cd_nm) AS "라벨_MM003",
    COUNT(*) AS "행수",
    COUNT(CASE WHEN g.goal_cnt > 0 THEN 1 END) AS "목표설정된_행수",
    ROUND(COUNT(CASE WHEN g.goal_cnt > 0 THEN 1 END) * 100.0
          / NULLIF(COUNT(*), 0), 1) AS "목표설정률_PCT",
    SUM(g.goal_cnt) AS "목표건수_합계"
FROM GN_DW.BRONZE_CRM.TM_CM_MBER_DVLP_GOAL g
LEFT JOIN GN_DW.BRONZE_CRM.TC_CMMN_DTL_CD d
       ON d.dtl_cd_id = g.mber_dvlp_div_cd
      AND d.cd_id = 'MM003'
GROUP BY 1
ORDER BY 1;
```

### 3-2. [F-1, F-2] 조직 계층(본부 vs 지부) 및 ML 후원사업 4그룹 매핑 기준
* **요청 배경 및 의사결정 필요 사항**:
  * 단일 레벨에 명칭으로만 혼재된 본부와 지부를 구별할 공식 기준 확정.
  * ML 예측 모델에서 요구하는 4개 후원사업 그룹 및 11개 대상 사업의 공식 매핑 기준 확정.
* **DB 실측 근거** (🔴 [2026-09-08 O144-E] 실행 결과 **두 전제 모두 시정**):
  * **F-1 조직 계층** — `BRONZE_CRM.TM_CM_DEPT_INFO` 총 1,314개 부서:
    * 루트 부서 9개 하위에 본부와 지부가 **레벨 2~5 에 혼재**합니다(종전 기재 `LVL=2~4` 를 시정).
      레벨2: 본부 6 · 지부 4 / 레벨3: 본부 50 · 지부 65 / 레벨4: 본부 67 · 지부 280 / 레벨5: 본부 4 · 지부 5.
    * 🔴🔴 **전용 구분 컬럼 `STATS_DEPT_LVL` 은 판별에 쓸 수 없습니다** — 1,314개 중 **1,306개가 NULL** 이고, 값이 있는 것은 `0`(3개)·`5`(5개) 뿐입니다(**결측률 99.4%**).
    * ⇒ 즉 명칭 `LIKE '%본부%'` 파싱 외에 **다른 방법이 원천에 없습니다.**
  * **F-2 후원사업 그룹** — `BRONZE_CRM.TM_CM_SPNSR_BSNS_INFO` 총 50개 사업:
    * 🔴🔴 **약어코드(`SPNSR_BSNS_ABRV_CD`)는 4종이 아니라 6종입니다.**

| 약어코드 | 소속 사업 수 |
|---|---:|
| `1` | 17 |
| `2` | 1 |
| `3` | 6 |
| `4` | 3 |
| `5` | 21 |
| `6` | 2 |

    * ⇒ ML 요건의 「**4개 그룹**」이 원천의 6종 중 **어느 4개를 묶은 것인지 알 수 없습니다.** 또한 「예측 대상 총 11개 사업」이 어느 사업인지도 특정되지 않습니다(50개 중 11개를 고르는 기준이 없습니다).
* **현업 확인 요청 사항** (🔴 실측에 맞춰 재작성):
  1. 🔴 조직 마스터 내 본부/지부/팀의 공식 구분 분류표. **`STATS_DEPT_LVL` 이 99.4% 비어 있으므로**, 명칭 파싱 규칙(`'%본부%'` 포함 여부)을 공식 승인하시거나 **부서ID 기준 분류표**를 제공해 주셔야 합니다.
  2. 🔴 **약어코드 6종을 4그룹으로 묶는 매핑표** — 어느 코드끼리 합치는지 알려 주십시오(6→4 로 줄이는 규칙이 원천에 없습니다).
  3. 🔴 **예측 대상 11개 사업의 공식 코드 목록** — 전체 50개 중 어느 11개인지 명시가 필요합니다.
* **실증 쿼리**:

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [3-2. F-1] 부서 계층 구조 및 본부/지부 명칭 혼재 실측
--
-- ▣ 이 쿼리가 답하는 질문
--   "본부와 지부가 트리의 같은 깊이에 섞여 있나?"
--   → 섞여 있으면 '레벨로 본부/지부를 구분'하는 방법이 불가능하다는 뜻이다.
--
-- ▣ 읽는 법 (재귀 CTE)
--   tree 의 앵커부: 상위부서가 없는 행(= 루트)을 lvl 1 로 잡는다.
--                   ⚠️ LEFT JOIN + `p.dept_id IS NULL` 로 '부모가 없음'을 판정한다.
--   재귀부       : 부모의 lvl + 1 로 자식을 따라 내려간다.
--   최종 SELECT  : 레벨별로 '본부' 포함 부서수와 '지부' 포함 부서수를 나란히 센다.
--   🔴 같은 레벨 행에 본부수와 지부수가 **둘 다 0 이 아니면** = 혼재 확정이다.
--
-- ▣ STATS_DEPT_LVL_값종류 를 왜 함께 내나
--   원천에 통계용 레벨 컬럼이 있으니 그것으로 구분되면 가장 좋다.
--   이 값이 1 이하로 나오면 → 컬럼이 사실상 비어 있어 **쓸 수 없다**는 신호다.
--   ⇒ 정확한 결측률은 아래 [3-2-B] 로 센다.
--
-- ▣ 주의
--   🔴 명칭 LIKE 는 '본부'가 이름에 들어간 것만 잡는다 — 이름에 안 들어간 본부는 놓친다.
--      그래서 이 방법은 **근거이면서 동시에 한계**다(그래서 현업 승인이 필요하다).
-- ─────────────────────────────────────────────────────────────────────
WITH RECURSIVE tree AS (
    SELECT d.dept_id, d.dept_nm, d.upper_dept_id, d.stats_dept_lvl, 1 AS lvl
    FROM GN_DW.BRONZE_CRM.TM_CM_DEPT_INFO d
    LEFT JOIN GN_DW.BRONZE_CRM.TM_CM_DEPT_INFO p
        ON p.dept_id = d.upper_dept_id
    WHERE p.dept_id IS NULL
    UNION ALL
    SELECT d.dept_id, d.dept_nm, d.upper_dept_id, d.stats_dept_lvl, t.lvl + 1
    FROM GN_DW.BRONZE_CRM.TM_CM_DEPT_INFO d
    JOIN tree t ON d.upper_dept_id = t.dept_id
)
SELECT
    lvl AS "트리레벨",
    COUNT(*) AS "부서수",
    COUNT(CASE WHEN dept_nm LIKE '%본부%' THEN 1 END) AS "본부_명칭포함",
    COUNT(CASE WHEN dept_nm LIKE '%지부%' THEN 1 END) AS "지부_명칭포함",
    COUNT(DISTINCT stats_dept_lvl) AS "STATS_DEPT_LVL_값종류"
FROM tree
GROUP BY lvl
ORDER BY lvl;

-- ─────────────────────────────────────────────────────────────────────
-- [3-2-B. F-1 보강 🆕] 🔴 **STATS_DEPT_LVL 의 판별력을 직접 센다**
--
-- ▣ 왜 추가했나
--   "전용 코드 컬럼이 있는데 왜 명칭을 파싱하느냐"는 반론이 당연히 나온다.
--   ⇒ 그 컬럼이 **실제로 비어 있음**을 숫자로 보여야 명칭 파싱 승인을 요청할 수 있다.
--
-- ▣ 읽는 법
--   값이 NULL 인 행이 압도적이면 → 이 컬럼으로는 어떤 분류도 불가능하다.
--   값 종류가 2~3개뿐이고 각 몇 개 수준이면 → 일부 부서에만 시범 입력된 상태다.
--   ⇒ 어느 쪽이든 "이 컬럼으로 본부/지부를 나눌 수 없다"는 결론이 나온다.
--
-- ▣ 주의
--   ⚠️ GROUP BY 에서 NULL 은 **하나의 그룹**으로 묶인다 ⇒ 결과에 빈 값 행으로 나타난다.
--      이것을 '값 0' 으로 오독하지 말 것.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    COALESCE(TO_VARCHAR(stats_dept_lvl), '(NULL · 미입력)') AS "STATS_DEPT_LVL_값",
    COUNT(*) AS "부서수",
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS "비중_PCT"
FROM GN_DW.BRONZE_CRM.TM_CM_DEPT_INFO
GROUP BY 1
ORDER BY 2 DESC;

-- ─────────────────────────────────────────────────────────────────────
-- [3-3. F-2] 후원사업 약어코드 및 후원구분코드 분포
--
-- ▣ 이 쿼리가 답하는 질문
--   "후원사업을 묶는 축이 원천에 있나? 그 축은 몇 개 그룹을 만드나?"
--
-- ▣ 읽는 법
--   약어코드 × 후원구분코드 조합별로 사업 수를 세고, LISTAGG 로 **소속 사업명을 나열**한다.
--   ⇒ 그룹의 성격(국내/해외/북한/기타)이 사업명 목록으로 사람 눈에 드러난다.
--   ⚠️ LISTAGG 는 길어질 수 있다 — 잘려 보이면 사업수를 함께 보라.
--
-- ▣ 주의
--   🔴 ML 요건은 「4그룹」을 말하지만 이 쿼리의 약어코드는 **6종**이 나온다
--      ⇒ 6→4 매핑 규칙이 원천에 없다는 것이 이 쿼리의 결론이다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    spnsr_bsns_abrv_cd AS "사업약어코드",
    spnsr_div_cd AS "후원구분코드",
    COUNT(*) AS "사업수",
    LISTAGG(spnsr_bsns_id || '=' || spnsr_bsns_nm, ' · ')
        WITHIN GROUP (ORDER BY spnsr_bsns_id) AS "소속사업_목록"
FROM GN_DW.BRONZE_CRM.TM_CM_SPNSR_BSNS_INFO
GROUP BY 1, 2
ORDER BY 1, 2;

-- ─────────────────────────────────────────────────────────────────────
-- [3-3-B. F-2 보강 🆕] 🔴 **「4그룹」 전제 검증** — 약어코드가 정말 4종인가
--
-- ▣ 왜 추가했나
--   요건서는 「4개 후원사업 그룹」을 전제한다. 위 쿼리는 약어코드 × 후원구분 **조합**을
--   내므로 행수가 9행이 되어 "그룹이 몇 개인지" 한눈에 안 보였다.
--   ⇒ 약어코드 종수만 딱 세서 **전제가 맞는지 확인**한다.
--
-- ▣ 읽는 법
--   약어코드_종수 = 원천이 실제로 만드는 그룹 수.
--   이 값이 4 가 아니면 → 요건의 '4그룹'은 **원천 축이 아니라 별도 사업 분류**이며,
--   그 매핑표를 현업에서 받아야 한다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    COUNT(DISTINCT spnsr_bsns_abrv_cd) AS "약어코드_종수",
    COUNT(DISTINCT spnsr_div_cd) AS "후원구분_종수",
    COUNT(*) AS "사업_전체수"
FROM GN_DW.BRONZE_CRM.TM_CM_SPNSR_BSNS_INFO;
```

* **현업 확인 요청 사항**:

* **실증 쿼리**:

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [4-1. F-3] 이메일 오픈 데이터 부재 실측 (전건 0/NULL)
--
-- ▣ 이 쿼리가 답하는 질문
--   "ML 피처로 쓰려는 '이메일 오픈율' 이 원천에 정말 없나?"
--   → 없으면 그 피처를 쓰는 모델 요건은 **성립할 수 없다**.
--
-- ▣ 읽는 법 — 3단 판정이 핵심이다
--   전체행수  : COUNT(*)                              = 모수
--   값있는행  : COUNT(컬럼)                           = NULL 이 아닌 행
--   0초과행   : COUNT(CASE WHEN TRY_TO_NUMBER(..)>0)  = **의미 있는 값이 있는 행**
--   ⇒ 값있는행이 0 이면 전건 NULL, 값은 있는데 0초과행이 0 이면 **전건 0** 이다.
--     둘은 원인이 다르다(미수집 vs 0 으로 채움) ⇒ 그래서 세 컬럼을 함께 낸다.
--   ⚠️ 컬럼이 TEXT 이므로 `TRY_TO_NUMBER` 로 감싼다 — 숫자가 아니면 NULL 이 되어 안전하다.
--
-- ▣ 주의
--   🔴 오픈율이 0 이라는 것과 '아무도 열지 않았다'는 것은 다르다.
--      **추적 자체가 없으면** 0 으로 기록된다 ⇒ 0 을 '열지 않음'으로 해석하면 안 된다.
-- ─────────────────────────────────────────────────────────────────────
SELECT 'EMAIL 오픈 URL_OTHBC_CNT_CTNT' AS "항목",
    COUNT(*) AS "전체행수",
    COUNT(url_othbc_cnt_ctnt) AS "값있는행",
    COUNT(CASE WHEN TRY_TO_NUMBER(url_othbc_cnt_ctnt) > 0 THEN 1 END) AS "0초과행"
FROM GN_DW.BRONZE_CRM.TD_MS_EMAIL_LQY_SNDNG
UNION ALL
SELECT 'EMAIL 오픈율 URL_OTHBC_RT_CTNT',
    COUNT(*),
    COUNT(url_othbc_rt_ctnt),
    COUNT(CASE WHEN TRY_TO_NUMBER(url_othbc_rt_ctnt) > 0 THEN 1 END)
FROM GN_DW.BRONZE_CRM.TD_MS_EMAIL_LQY_SNDNG;

-- ─────────────────────────────────────────────────────────────────────
-- [4-1-B. F-3 보강 🆕] **대체 피처 후보의 실재 여부** — 대안이 있는지 함께 본다
--
-- ▣ 왜 추가했나
--   현업 질문은 "오픈율을 클릭률로 대체해도 되나?" 다.
--   ⇒ 그런데 **클릭률 쪽도 비어 있으면 대체가 불가능**하다. 대안의 실재를 먼저 세야
--     "대체 승인" 을 물을 수 있다.
--
-- ▣ 읽는 법
--   후보 3종(이메일 오픈 · 알림톡 총클릭 · 알림톡 개별클릭)의 0초과행을 나란히 본다.
--   🔴 전부 0 이면 → 「대체」가 아니라 **피처 제외**를 결정해야 한다.
--   🟢 하나라도 0 초과가 있으면 → 그것이 대체 후보다.
-- ─────────────────────────────────────────────────────────────────────
SELECT '이메일 오픈수' AS "피처후보",
       COUNT(*) AS "전체행수",
       COUNT(CASE WHEN TRY_TO_NUMBER(url_othbc_cnt_ctnt) > 0 THEN 1 END) AS "0초과행"
FROM GN_DW.BRONZE_CRM.TD_MS_EMAIL_LQY_SNDNG
UNION ALL
SELECT '알림톡 총클릭수',
       COUNT(*),
       COUNT(CASE WHEN TRY_TO_NUMBER(tot_click_cnt_ctnt) > 0 THEN 1 END)
FROM GN_DW.BRONZE_CRM.TD_MS_MSG_AT_LQY_SNDNG;
```

* **DB 실측 근거** (🟢 [2026-09-08 O144-E] 실행 결과 **0행 = 부재 확인**):
  * BRONZE 전체 스키마의 테이블 **56개** 중 공휴일·근무일·캘린더 키워드에 해당하는 테이블이 **0개**입니다.
  * 🔴 **「0행」이 쿼리 오류가 아님을 증명하기 위해 대조군 쿼리를 추가했습니다** — 같은 방식으로 세면 BRONZE 테이블 총수는 56 으로 정상 집계되므로, 캘린더 0 은 **진짜 부재**입니다.
* **현업 확인 요청 사항**:
  1. 사내 근무일 캘린더 데이터 제공 가능 여부 및 연동 방식.
  2. 제공이 어렵다면, **공공 공휴일 데이터로 대체**해도 되는지(사내 창립기념일·특별휴무는 반영되지 않습니다).
* **실증 쿼리**:

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [4-2. F-5] 공휴일/근무일 캘린더 원천 테이블 입고 여부
--
-- ▣ 이 쿼리가 답하는 질문
--   "영업일 기준 통계를 내려면 캘린더가 필요한데, 원천에 있나?"
--
-- ▣ 읽는 법
--   🔴 **결과가 0행이면 「없다」는 뜻이다.** 이 쿼리는 0행이 정답인 유형이다.
--   키워드 4종(HOLIDAY · CALENDAR · HLDY · WORKDAY)으로 넓게 훑는다.
--
-- ▣ 주의(가장 중요)
--   🔴 0행은 **「쿼리가 잘못됐다」와 구별되지 않는다.** 스키마명 오타 하나로도 0행이 된다.
--      ⇒ 그래서 반드시 아래 [4-2-B] 대조군을 **함께 실행**해야 한다.
--        대조군이 정상 숫자를 내면 → 이 0행은 진짜 부재다.
-- ─────────────────────────────────────────────────────────────────────
SELECT table_schema, table_name
FROM GN_DW.INFORMATION_SCHEMA.TABLES
WHERE table_schema LIKE 'BRONZE%'
  AND (table_name LIKE '%HOLIDAY%' OR table_name LIKE '%CALENDAR%'
    OR table_name LIKE '%HLDY%' OR table_name LIKE '%WORKDAY%')
ORDER BY 1, 2;

-- ─────────────────────────────────────────────────────────────────────
-- [4-2-B. F-5 보강 🆕] 🔴 **대조군** — 위 0행이 쿼리 오류가 아님을 증명한다
--
-- ▣ 왜 추가했나
--   「0건」이라는 근거는 그 자체로는 약하다. 조건을 잘못 써도 0 이 나오기 때문이다.
--   ⇒ **같은 스키마 조건**으로 전체 테이블을 세어, 조건 자체는 정상 작동함을 보인다.
--
-- ▣ 읽는 법
--   BRONZE_테이블_총수 가 0 이 아니면 → 스키마 조건(`LIKE 'BRONZE%'`)은 정상이다.
--   캘린더_키워드_해당 이 0 이면 → **조건은 살아 있는데 대상이 없다** = 진짜 부재.
--   🟢 이 두 숫자를 한 줄에 나란히 놓는 것이 이 쿼리의 전부이자 요점이다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    COUNT(*) AS "BRONZE_테이블_총수",
    COUNT(CASE WHEN table_name LIKE '%HOLIDAY%' OR table_name LIKE '%CALENDAR%'
                 OR table_name LIKE '%HLDY%' OR table_name LIKE '%WORKDAY%'
               THEN 1 END) AS "캘린더_키워드_해당",
    COUNT(DISTINCT table_schema) AS "BRONZE_스키마수"
FROM GN_DW.INFORMATION_SCHEMA.TABLES
WHERE table_schema LIKE 'BRONZE%';
```

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [5-1. AD-2] 디지털 광고 개발건수 소수점 유입 실측
--
-- ▣ 이 쿼리가 답하는 질문
--   "개발건수가 정수가 아니라 소수로 들어오는가? 얼마나?"
--   → 소수는 '매체 기여도 배분' 의 결과일 가능성이 높다 ⇒ 반올림 규칙이 필요해진다.
--
-- ▣ 읽는 법
--   `crm_dvlp_cnt <> FLOOR(crm_dvlp_cnt)` = 내림값과 다르면 **소수부가 있다**는 뜻이다.
--   최소값·최대값을 함께 보면 값의 스케일이 보인다(0.x 배분치인지 큰 정수인지).
--   ⚠️ WHERE 로 NULL 을 제외했으므로 분모는 '값 있는 행' 이다(전체 행수가 아니다).
--
-- ▣ 주의
--   🔴 반올림 시점이 총계를 바꾼다 — 행별 반올림 후 합산과 합산 후 반올림은 다르다.
--      그래서 이것이 현업 확정 사항이다(임의로 정하면 실적이 달라진다).
-- ─────────────────────────────────────────────────────────────────────
SELECT
    COUNT(*) AS "값있는행수",
    COUNT(CASE WHEN crm_dvlp_cnt <> FLOOR(crm_dvlp_cnt) THEN 1 END) AS "소수점보유행수",
    ROUND(COUNT(CASE WHEN crm_dvlp_cnt <> FLOOR(crm_dvlp_cnt) THEN 1 END) * 100.0 / COUNT(*), 1) AS "소수점비율_PCT",
    MIN(crm_dvlp_cnt) AS "최소값",
    MAX(crm_dvlp_cnt) AS "최대값"
FROM GN_DW.BRONZE_AGENCY.DGT_AD_CMPGN_DTLS
WHERE crm_dvlp_cnt IS NOT NULL;

-- ─────────────────────────────────────────────────────────────────────
-- [5-2. AD-3] 2026-06 이후 개발건수 ➔ 단가 포맷 교체 실측
--
-- ▣ 이 쿼리가 답하는 질문
--   "원천 보고 포맷이 언제부터 바뀌었나? 두 컬럼이 겹치는 구간이 있나?"
--
-- ▣ 읽는 법 — **바통 터치**를 보는 것이 목적이다
--   개발건수_값있는행 이 어느 달부터 0 이 되고, 같은 달 단가_값있는행 이 채워지면
--   그 달이 **전환 시점**이다. 두 컬럼이 동시에 채워진 달이 있으면 겹침 구간이다.
--   ⇒ 겹침이 없으면 '완전 교체' 이므로 단가를 채택하지 않으면 그 이후 실적이 **0** 이 된다.
--
-- ▣ 주의
--   🔴 `date >= '2026-01-01'` 은 문자열 비교다(컬럼이 TEXT). 포맷이 'YYYY-MM-DD' 로
--      일정해야 의도대로 동작한다 ⇒ 다른 포맷이 섞이면 결과가 어긋난다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    TO_CHAR(date, 'YYYY-MM') AS "기간",
    COUNT(*) AS "전체행수",
    COUNT(crm_dvlp_cnt) AS "개발건수_값있는행",
    COUNT(dev_unit_price) AS "단가_값있는행"
FROM GN_DW.BRONZE_AGENCY.DGT_AD_CMPGN_DTLS
WHERE date >= '2026-01-01'
GROUP BY 1
ORDER BY 1;

-- ─────────────────────────────────────────────────────────────────────
-- [5-3. AD-5] 방송광고(VIDEO) 내 개발건수·전환수 보유 현황
--
-- ▣ 이 쿼리가 답하는 질문
--   "방송 광고에는 성과 지표가 아무것도 없나, 일부만 없나?"
--   → 전부 없으면 '리포트 추가 요청', 일부만 없으면 **있는 것으로 대체** 가능하다.
--
-- ▣ 읽는 법
--   전환콜_값있는행 이 0 인데 인바운드콜_값있는행 이 크면
--   ⇒ 🟢 **대체 지표가 존재한다**는 뜻이다(인바운드콜로 성과를 볼 수 있다).
--   총광고비가 채워져 있으면 최소한 '비용' 축은 분석 가능하다.
--
-- ▣ 주의
--   🔴 전환콜과 인바운드콜은 **다른 개념**이다 — 대체하려면 현업 승인이 필요하다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    COUNT(*) AS "전체행수",
    COUNT(conv_call_cnt) AS "전환콜_값있는행",
    COUNT(inbound_call_cnt) AS "인바운드콜_값있는행",
    SUM(actl_pur_ad_cost_krw) AS "총광고비"
FROM GN_DW.BRONZE_AGENCY.VIDEO_AD_CMPGN_DTLS;
```

### 5-2. [J-2] 방송 광고 초수(AD_SEC) 단위 정규화 확인
* **요청 배경 및 의사결정 필요 사항**:
  * `VIDEO_AD_CMPGN_DTLS.AD_SEC`의 8자리 정수(`30000000`, `60000000`)의 초 단위(30초, 60초) 환산 규칙 확인.
* **DB 실측 근거** (🟢 [2026-09-08 O144-E] 실행 결과 **환산 규칙이 실측으로 좁혀졌습니다**):
  * 🔴 종전 기재 「8자리 정수와 시분초가 혼재」는 비중을 잘못 읽게 합니다 — 실측은 **시분초 표기가 압도적 다수**이고 8자리 정수는 소수입니다:
    * 시분초 표기: `00:01:00` **27,788건** · `0:01:30` 2,285 · `00:01:30` 1,107 · `00:02:00` 1,082 · `0:00:30` 477 …
    * 8자리 정수: `60000000` **1,184건** · `90000000` 644 · `30000000` 104 (**총 1,932건 · 값 3종뿐**)
  * 🟢🟢 **환산 규칙이 사실상 규명됐습니다 — 8자리는 마이크로초(µs)입니다.**

| 8자리 정수 | ÷ 1,000,000 | 대응하는 시분초 표기 | 그 표기의 건수 |
|---|---:|---|---:|
| `60000000` | **60초** | `00:01:00` (= 60초) | 27,788 (최다값) |
| `90000000` | **90초** | `00:01:30` · `0:01:30` (= 90초) | 3,392 |
| `30000000` | **30초** | `0:00:30` (= 30초) | 477 |

  * ⇒ 8자리 값 3종이 **시분초 표기의 실재 값과 1:1 로 정확히 대응**합니다. 광고 초수가 30·60·90초인 것도 업계 관행과 맞습니다.
  * 🔴 따라서 요청은 「30000000 이 30초인가?」가 아니라 **「÷1,000,000(µs→초) 환산을 공식 규칙으로 채택해도 되는가?」** 로 바뀝니다.
  * ⚠️ 참고 — `GOLD.FACT_AD_BROADCAST.DURATION_SEC` 는 현재 이 환산 없이 적재되어 **값 신뢰 금지 상태**입니다(COMMENT 에 명시). 회신 후 환산을 배선합니다.
* **현업 확인 요청 사항**:
  1. 🟢 8자리 숫자를 **`÷ 1,000,000` (마이크로초 → 초)** 로 환산하는 규칙의 공식 승인 (⇒ 30초·60초·90초).
  2. 🔴 시분초 표기(`00:01:00` 등)와 8자리 표기가 **왜 혼재하는지** — 입력 시스템이 둘인지, 시기에 따라 바뀐 것인지.
* **실증 쿼리**:

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [5-4. J-2] 방송 광고 초수(AD_SEC) 표기 방식 실측
--
-- ▣ 이 쿼리가 답하는 질문
--   "초수 컬럼에 어떤 모양의 값들이 들어 있나? 각각 몇 건인가?"
--
-- ▣ 읽는 법
--   `ad_sec LIKE '%:%'` 로 시분초 표기와 숫자 표기를 가른다.
--   원천값을 그대로 GROUP BY 하므로 **실재하는 값 전량**이 보인다
--   ⇒ 값 종류가 적으면(3~10종) 환산 규칙을 사람이 눈으로 맞출 수 있다.
--
-- ▣ 주의
--   🔴 표기 종류가 '혼재' 라는 사실만 보지 말고 **각 표기의 건수 비중**을 보라.
--      실측에서는 시분초가 압도적 다수이고 8자리는 소수다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    CASE WHEN ad_sec LIKE '%:%' THEN '시:분:초 표기' ELSE '숫자 표기' END AS "표기방식",
    ad_sec AS "원천값",
    COUNT(*) AS "건수"
FROM GN_DW.BRONZE_AGENCY.VIDEO_AD_CMPGN_DTLS
WHERE ad_sec IS NOT NULL
GROUP BY 1, 2
ORDER BY 1, 3 DESC;

-- ─────────────────────────────────────────────────────────────────────
-- [5-4-B. J-2 보강 🆕] 🟢 **환산 규칙 검증** — 8자리가 마이크로초인지 증명한다
--
-- ▣ 왜 추가했나
--   문서는 「30000000 ➔ 30초」로 읽자고 제안했다. 그런데 그 근거가 없었다.
--   앞 2자리를 떼는 것인지, 1,000,000 으로 나누는 것인지 식이 불분명했다.
--   ⇒ **두 표기를 같은 '초' 단위로 환산해 나란히 놓으면** 대응 여부가 증명된다.
--
-- ▣ 읽는 법 — 이 쿼리의 핵심 장치
--   시분초 표기: SPLIT_PART 로 분·초를 떼어 `분×60 + 초` 로 초를 만든다.
--   숫자 표기  : `÷ 1,000,000` 으로 마이크로초를 초로 만든다.
--   ⇒ 두 경로의 결과(환산_초)가 **같은 값 집합(30·60·90)에 모이면** µs 해석이 맞다.
--     서로 다른 값으로 흩어지면 µs 해석은 틀린 것이다.
--
-- ▣ 주의
--   ⚠️ `0:01:30` 처럼 시가 1자리인 경우도 있으므로 시(1번째 조각)는 쓰지 않고
--      분(2번째)·초(3번째)만 사용한다 — 광고 초수는 1시간을 넘지 않는다는 전제다.
--   🔴 값 종류가 3개뿐이라 두 해석(앞 2자리 읽기 / ÷1,000,000)이 우연히 같은 답을 낸다.
--      그래도 시분초 최다값 `00:01:00`(=60초)이 `60000000`과 1:1 로 맞으므로
--      **µs 해석이 정합적**이다 ⇒ 최종 확정은 현업 회신으로 한다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    ad_sec AS "원천값",
    CASE WHEN ad_sec LIKE '%:%' THEN '시:분:초' ELSE '숫자(µs 가정)' END AS "표기방식",
    COUNT(*) AS "건수",
    CASE
        WHEN ad_sec LIKE '%:%'
            THEN TO_NUMBER(SPLIT_PART(ad_sec, ':', 2)) * 60
                 + TO_NUMBER(SPLIT_PART(ad_sec, ':', 3))
        ELSE TRY_TO_NUMBER(ad_sec) / 1000000
    END AS "환산_초"
FROM GN_DW.BRONZE_AGENCY.VIDEO_AD_CMPGN_DTLS
WHERE ad_sec IS NOT NULL
GROUP BY 1, 2
ORDER BY 4, 3 DESC;
```

### 5-3. [N-9] 캠페인명 시점 동결(Snapshot) 확장 여부
* **요청 배경 및 의사결정 필요 사항**:
  * `SV_MEMBER_COHORT.CAMPAIGN_NAME`을 획득 당시 시점으로 동결할지, 실시간 조인으로 유지할지 결정.
* **DB 실측 근거** (🔴 [2026-09-08 O144-E] 실행 결과 **결정적 근거를 새로 확보**):
  * 캠페인 마스터(`TM_CM_CMPGN_MNG`, 36,163행): 코드당 단 1행의 **현재** 캠페인명만 보관하며 **변경 이력 테이블이 부재**합니다.
  * 🔴 **개칭은 활발히 일어나고 있습니다** — 마스터 최종변경일 분포: 2019년 13,569 · 2024년 **4,865** · 2025년 **5,456** · 2026년 **4,015** ⇒ 최근 3년에만 **14,336개 캠페인**이 수정됐습니다.
  * 🔴🔴 **그런데 GOLD 의 「동결」 값이 현재 값과 100% 동일합니다 — 즉 동결이 실효하지 않습니다.**

| 대조 | 실측 |
|---|---:|
| `DIM_MEMBER_ACQUISITION` 행수 | 1,585,949 |
| 획득 시점 동결명(`ACQ_CAMPAIGN_NAME`) ≠ 현재명(`DIM_CAMPAIGN.CAMPAIGN_NAME`) | **0행** |
| 불일치가 발생한 캠페인 수 | **0개** |

  * ⇒ 캠페인명은 「동결 컬럼」에 담겨 있지만 **값이 현재 마스터명과 구별되지 않습니다.** 개칭이 일어나면 과거 코호트 실적의 캠페인명도 **함께 바뀔 것**입니다(현재는 최신 적재 시점 기준으로 덮여 있는 상태).
  * 🟢 반면 획득 부서·채널·브랜드 등 다른 속성은 `ACQ_*` 로 동결 배선돼 있습니다 ⇒ **캠페인명만 예외**입니다.
* **현업 확인 요청 사항**:
  1. 🔴 캠페인명 개칭 시 **과거 코호트 실적의 캠페인명을 소급 변경할지, 획득 당시 이름으로 고정할지** 확정.
     * **㉠ 소급 변경(현행 유지)**: 보고서에 항상 최신 이름이 나옵니다. 과거 보고서와 이름이 달라져 **연도 간 대조가 끊깁니다**.
     * **㉡ 획득 시점 고정**: 과거 보고서가 재현됩니다. 대신 같은 캠페인이 이름 2개로 보입니다 ⇒ DW 에 **개칭 이력 스냅샷 파이프라인 신설**이 필요합니다.
  2. ㉡ 를 택하실 경우, **언제부터의 이름을 정본으로 볼지**(스냅샷 시작 시점) 알려 주십시오. 과거 개칭 이력은 원천에 없어 **소급 복원이 불가능**합니다.
* **실증 쿼리**:

```sql
-- ─────────────────────────────────────────────────────────────────────
-- [5-5. N-9] 캠페인 마스터의 최종변경일 및 캠페인별 획득 회원수
--
-- ▣ 이 쿼리가 답하는 질문
--   "이름이 바뀔 수 있는 캠페인에 실적이 얼마나 걸려 있나?"
--   → 최종변경일이 오래됐는데 획득회원수가 크면, 그 캠페인 이름이 바뀔 때
--     **대량 실적의 표기가 한꺼번에 달라진다** ⇒ 위험 규모를 보여 준다.
--
-- ▣ 읽는 법
--   마스터_최종변경일 = 그 캠페인 레코드가 마지막으로 수정된 날.
--   ⚠️ 이것은 '이름이 바뀐 날'이 아니다 — 어떤 컬럼이든 수정되면 갱신된다.
--      즉 **개칭의 증거가 아니라 개칭 가능성의 지표**다.
--   획득회원수 = 그 캠페인으로 유입된 고유 회원 수 = 영향 규모.
--
-- ▣ 주의
--   🔴 이 쿼리만으로는 "동결이 필요한가"를 답할 수 없다 — 이름이 실제로 갈렸는지
--      모르기 때문이다. ⇒ 반드시 아래 [5-5-B] 를 함께 보라.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    c.cmpgn_cd AS "캠페인코드",
    c.cmpgn_nm AS "캠페인명_현재값",
    TO_CHAR(c.last_updt_dt, 'YYYY-MM-DD') AS "마스터_최종변경일",
    COUNT(DISTINCT s.mber_no) AS "획득회원수"
FROM GN_DW.BRONZE_CRM.TM_MM_FDRM_MBER_SPNSR s
JOIN GN_DW.BRONZE_CRM.TM_CM_CMPGN_MNG c
    ON c.cmpgn_cd = s.cmpgn_cd
GROUP BY 1, 2, 3
ORDER BY 4 DESC
LIMIT 20;

-- ─────────────────────────────────────────────────────────────────────
-- [5-5-B. N-9 보강 🆕] 🔴 **동결이 실효하는지 직접 대조한다** (가장 중요)
--
-- ▣ 왜 이 쿼리가 결정적인가
--   DW 에는 `ACQ_CAMPAIGN_NAME` 이라는 **'획득 시점 동결' 이라는 이름의 컬럼**이 있다.
--   그런데 이름만 동결이고 값이 현재 마스터명과 같다면, 실질은 **실시간 조인과 동일**하다.
--   ⇒ "동결로 바꿀까요?" 를 묻기 전에 **지금 동결이 되고 있는지**를 먼저 세야 한다.
--
-- ▣ 읽는 법 — 판정이 두 갈래로 갈린다
--   불일치_행수 = 0 이면
--     🔴 현재 동결 컬럼은 **현재값과 구별되지 않는다** = 동결이 실효하지 않는다.
--        (개칭이 일어나면 과거 실적의 이름도 함께 바뀐다)
--   불일치_행수 > 0 이면
--     🟢 이미 동결이 작동하고 있다 = 과거 이름이 보존되고 있다.
--        이때 불일치 규모가 곧 '이름이 갈린 실적'의 크기다.
--
-- ▣ 주의
--   ⚠️ `<>` 는 NULL 을 참으로 만들지 않는다 ⇒ 어느 한쪽이 NULL 인 행은 불일치로 세지
--      않는다. NULL 규모가 궁금하면 별도로 COUNT 하라.
--   🔴 이 쿼리는 GOLD 대상이다(BRONZE 가 아니다) — 원천 문제가 아니라
--      **DW 모델링 상태**를 보는 것이 목적이기 때문이다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    COUNT(*) AS "대조_행수",
    COUNT(CASE WHEN a.ACQ_CAMPAIGN_NAME <> c.CAMPAIGN_NAME
               THEN 1 END) AS "불일치_행수",
    COUNT(DISTINCT CASE WHEN a.ACQ_CAMPAIGN_NAME <> c.CAMPAIGN_NAME
                        THEN a.ACQ_CAMPAIGN_SK END) AS "불일치_캠페인수",
    COUNT(CASE WHEN a.ACQ_CAMPAIGN_NAME IS NULL THEN 1 END) AS "동결명_NULL_행수"
FROM GN_DW.GOLD.DIM_MEMBER_ACQUISITION a
JOIN GN_DW.GOLD.DIM_CAMPAIGN c
  ON c.CAMPAIGN_SK = a.ACQ_CAMPAIGN_SK;

-- ─────────────────────────────────────────────────────────────────────
-- [5-5-C. N-9 보강 🆕] **개칭이 실제로 활발한지** — 연도별 마스터 수정 건수
--
-- ▣ 왜 추가했나
--   "동결이 필요하다"는 주장은 **개칭이 실제로 일어난다**는 전제에 기댄다.
--   ⇒ 마스터 수정이 최근에도 활발하면 위험이 현재진행형이라는 근거가 된다.
--
-- ▣ 읽는 법
--   최근 연도에 수정 건수가 많으면 → 소급 변경 위험이 **지금도** 있다.
--   과거 연도에만 몰려 있으면 → 위험이 낮아 현행 유지도 선택지가 된다.
--
-- ▣ 주의
--   🔴 다시 말하지만 최종변경일은 '이름이 바뀐 날'이 아니다 — 상한(최대 위험)을 보는 것이다.
-- ─────────────────────────────────────────────────────────────────────
SELECT
    LEFT(TO_CHAR(last_updt_dt, 'YYYYMMDD'), 4) AS "마스터_수정연도",
    COUNT(*) AS "캠페인수",
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS "비중_PCT"
FROM GN_DW.BRONZE_CRM.TM_CM_CMPGN_MNG
GROUP BY 1
ORDER BY 1;
```
