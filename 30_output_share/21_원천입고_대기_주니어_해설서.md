# [GN_DW] 「원천에 없어서 못 하는 일」 해설서 — 주니어 가이드

> **문서 대상**: GN_DW 에 새로 합류한 데이터 엔지니어·데이터 분석가
> **문서 목적**: `19_원천입고_및_항목신설_대기.md` 의 12개 항목이 **왜 우리 힘으로 해결할 수 없는지**,
> 그리고 **각 항목을 어떻게 다뤄야 하는지**를 처음 보는 사람도 이해할 수 있게 풀어 쓴 문서입니다.
>
> ⏱️ **읽는 시간** 약 20분 · 🎯 **읽고 나면** 결손 데이터를 만났을 때 *"누구에게 무엇을 요청해야 하는지"*
> 를 스스로 판단할 수 있습니다.

---

## 📌 0. 시작 — 두 종류의 「못 함」을 구별하는 것이 이 일의 절반입니다

DW 를 만들다 보면 원하는 숫자가 안 나오는 상황을 하루에도 몇 번 만납니다.
그런데 **원인은 딱 두 가지**뿐이고, **이걸 구별하지 못하면 일이 영원히 안 끝납니다.**

| | ㉠ **규칙을 몰라서 못 함** | ㉡ **데이터가 없어서 못 함** |
|---|---|---|
| 예시 | *"중단을 어느 사업에 귀속시킬까?"* | *"우편이 반송됐는지 알려주는 컬럼이 아예 없다"* |
| 데이터는? | **있다** (다만 어떻게 쓸지 모른다) | **없다** (판단할 대상 자체가 없다) |
| 누가 푸나 | **현업 비즈니스 오너** (규칙 결정) | **원천 시스템 담당자** (제공·신설) |
| 정본 문서 | **17번** (해설서 = 20번) | **19번** (해설서 = 이 문서) |
| 우리가 할 일 | 선택지 + 실측 근거를 만들어 결정을 요청 | 무엇이 없는지 증명하고 제공을 요청 |

> 🔴 **왜 굳이 문서를 두 개로 나눴을까요?**
>
> 한 장에 섞어서 보내면 **아무도 답하지 못합니다.**
> 현업 오너에게 *"우편 반송 컬럼을 만들어 주세요"* 라고 하면 *"그건 제 권한이 아닙니다"* 라고 하고,
> 시스템 담당자에게 *"중단을 어느 사업에 붙일까요?"* 라고 하면 *"그건 업무팀이 정해야죠"* 라고 합니다.
> 그러면 메일이 몇 주를 돌다가 **아무 결론 없이 흐지부지**됩니다.
>
> 🟢 **요청을 쪼개는 것은 예의가 아니라 기술입니다.** 받는 사람이 **혼자서 답할 수 있는 단위**로 쪼개세요.

## 🧭 1. 「데이터가 없다」는 말에도 4가지 층이 있습니다

주니어가 가장 많이 하는 실수는 **"없다"를 한 단어로 처리하는 것**입니다.
실무에서는 아래 4가지가 **완전히 다른 요청**으로 갈립니다.

### A. 테이블이 아예 없다 (원천 미입고)

* 상태 = 우리 DW 에 그 데이터를 담을 **테이블이 비어 있거나 존재하지 않는다**.
* 예 = **후원사업별 사업목표**. `SILVER.CRM_BIZ_TARGET` 이 **0행**입니다.
* 요청 = *"이런 컬럼을 가진 테이블을 새로 주세요"* + **컬럼 스펙 문서**.
* 🟢 우리가 미리 해둘 일 = **dbt 모델을 먼저 만들어 두는 것**(스텁). 그러면 데이터가 들어오는 날
  코드를 안 고치고 바로 가동됩니다. 실제로 `CRM_BIZ_TARGET`·`FACT_TARGET_PROJECT` 는 그렇게 준비돼 있습니다.

### B. 테이블은 있는데 **컬럼이 없다** (구조적 부재)

* 상태 = 테이블은 잘 들어오는데, 우리가 필요한 **항목 자체가 원천에 존재하지 않는다**.
* 예 = **우편 반송 결과**. `TD_MS_PSTMTR_SNDNG_DTL` 은 컬럼이 14개인데 결과코드가 **0개**입니다.
* 🔴 **가장 위험한 유형입니다.** 왜냐하면 *"적재가 덜 됐나 봐요, 다시 넣어주세요"* 라고 요청하기
  쉬운데, **다시 넣어도 영원히 안 나옵니다.** 애초에 시스템이 그 값을 만들지 않으니까요.
* 요청 = *"적재 재실행"* 이 아니라 **"항목 신설"** 입니다. 요청 문구가 완전히 달라집니다.

### C. 컬럼은 있는데 **값이 전부 비어 있다**

* 상태 = 컬럼은 있는데 전건 `NULL` 또는 `0`.
* 예 = 이메일 오픈수, 알림톡 총클릭수, 대행사 전환콜수 — **모두 0건**입니다.
* ⚠️ **여기서 갈림길이 생깁니다**:
  * ㉠ 원천 시스템이 **수집을 안 한다** → B 와 같은 성격(신설·설정 필요)
  * ㉡ 수집은 하는데 **우리에게 넘기는 추출에서 빠졌다** → **재추출만 하면 즉시 해소**
* 🔴 **그래서 이 유형의 요청 핵심은 「어느 쪽인지 알려 달라」입니다.** 값을 달라는 게 아닙니다.
  ㉡ 이면 하루면 끝나는 일이고, ㉠ 이면 몇 달짜리 시스템 개발입니다. **일정 추정이 완전히 달라집니다.**

### D. 있다가 **중간에 바뀌었다** (포맷 전환)

* 상태 = 과거엔 주던 항목을 어느 시점부터 다른 항목으로 바꿔서 준다.
* 예 = 대행사가 2026-06 부터 **개발건수 대신 단가**를 보냅니다.
* 🔴 **함정** = 그래프를 그리면 6월부터 갑자기 0 으로 떨어져서 *"실적이 폭락했다"* 로 보입니다.
  실제로는 **측정 방식이 바뀐 것**입니다.
* ⚠️ 대체값을 쓸 때는 **"정의가 같은가"** 를 반드시 확인하세요. 대행사가 계산한 단가를 그대로 쓰면
  **이전 기간과 비교가 불가능**합니다. 비교 불가라는 사실을 지표에 표기해야 합니다.

## 🔬 2. 이번에 배운 가장 중요한 교훈 — 「입고되면 해결된다」의 배신

이 절은 **이 문서에서 딱 하나만 기억해야 한다면 이것**입니다.

### 2-1. 무슨 일이 있었나

우리 문서에는 오래전부터 이런 문장이 적혀 있었습니다.

> *"회원 마스터가 전량 입고되면, 참조무결성 테스트를 `warn` 에서 `error` 로 승격한다."*

배경은 이렇습니다. 행사 참여 기록에 있는 회원번호 중 일부가 **회원 마스터에 없었습니다**(고아).
그때는 *"마스터가 아직 일부만 들어와서 그렇다. 전량 들어오면 다 맞아떨어질 것"* 이라고 판단했고,
그래서 테스트를 **일단 `warn`(경고)으로 낮춰** 두고 나중에 `error`(실패)로 되돌리기로 예약했습니다.

**그리고 2026-09-10, 회원 마스터가 정말로 전량 입고됐습니다.**

| 확인 항목 | 실측값 |
|---|---:|
| 정기회원 마스터 `TM_MM_FDRM_MBER_INFO` | 1,587,343 |
| 일시회원 마스터 `TM_MM_ONCE_MBER_INFO` | 175,722 |
| **두 마스터 합계** | **1,763,065** |
| `SILVER.CRM_MEMBER` | **1,763,065** ✅ |
| `GOLD.DIM_MEMBER` | **1,763,065** ✅ |

입고는 완벽했습니다. 손실 0. 3개 계층이 한 행도 안 틀리고 일치했습니다.
**그런데 고아는 사라지지 않았습니다.**

| 확인 항목 | 실측값 |
|---|---:|
| 행사참여 고아 회원번호 | **7,658 종** |
| 행사참여 고아 행수 | **9,376 행** |
| 전체 대비 | **0.83%** |

### 2-2. 왜 사라지지 않았나

고아 번호를 **형식별로 쪼개 봤습니다.** 이게 결정적이었습니다.

| 회원번호 형식 | 고아 종수 | 고아 행수 |
|---|---:|---:|
| 정기회원 7자리 (정상 형식) | 7,629 | 9,338 |
| 일시회원 `S`+8자리 (정상 형식) | 29 | 38 |
| **기타 (형식 이상)** | **0** | **0** |

🔴 **형식이 깨진 값은 단 하나도 없었습니다.** 전부 **정상 형식의 정상 번호**입니다.
(형식이 깨진 값들은 이미 `I-2` 정제 필터가 걸러냈기 때문입니다.)

즉 이 번호들은 **한때 실제로 존재했던 회원**입니다. 그런데 지금 마스터에 없습니다. 왜?

현업 확인 결과 = **① 테스트로 만들었던 번호** ② **업무 절차상 원본 행을 삭제했는데,
운영 시스템이 cascade 삭제(연쇄 삭제)를 쓰지 않아서 참여 이력에는 번호만 남은 경우**입니다.

⇒ 그래서 현업 지침은 명확했습니다: **"무시하고 파이프라인을 구성하라."**

### 2-3. 그래서 처방이 뒤집혔습니다

* ❌ **폐기** = `warn` → `error` 승격
* ✅ **신 처방** = `severity: warn` 을 **영구 유지**하고, yml 주석에 사유를 적는다

**왜 `error` 로 올리면 안 되나요?** 세 가지 이유가 있습니다.

1. **매일 밤 파이프라인이 실패합니다.** 고아는 구조적으로 계속 생기므로 영원히 실패합니다.
2. **진짜 사고를 못 봅니다.** 항상 빨간불이면 아무도 안 봅니다. 이게 「알람 피로」입니다.
3. **고칠 방법이 없습니다.** 지울 수도 없습니다 — **참여했다는 사실 자체는 진짜**니까요.

**`warn` 은 「실패」가 아니라 「관측」입니다.** 지금 9,376행인 것을 기록해 두고,
다음에 갑자기 90만 행이 되면 **그때 조사**하는 조기경보 장치로 쓰는 것입니다.

### 2-4. 🎯 그래서 무엇을 배웠나

> 🔴 **「조건이 충족되면 X 를 하라」고 문서에 적으면, 조건이 충족된 날 아무도 그 전제를 검증하지 않고
> X 를 실행합니다.**
>
> 미래의 조치를 예약할 때는 **반드시 「실행 전에 다시 측정할 것」을 함께 적으세요.**
> 이번에는 다행히 재측정을 했기 때문에 파이프라인이 매일 실패하는 사고를 막았습니다.

🟢 **참고** = 사실 우리는 이미 비슷한 경험이 있었습니다. `O117` 세션에서 캠페인 코드 축을 조사하다가
*"입고·확정으로 채워지지 않는다"* 는 결론을 냈습니다. 이번 건은 **그 판정이 회원 마스터 축에서도
성립한다는 확인**이었습니다. ⇒ **같은 실수가 다른 축에서 반복된다면, 그건 개인의 실수가 아니라
규칙의 결함입니다.**

## 📋 3. 12개 항목 하나씩 — 무엇이 왜 막혔나

### 3-1. A유형 (테이블 미입고) — 3건

#### ① `E-6` 후원사업별 사업목표 테이블

* 🎯 **하려던 일** = *"국내아동지원 사업이 올해 목표의 몇 %를 달성했나?"* 를 보는 것.
* 🚧 **막힌 이유** = 후원사업 단위 목표를 담은 원천 테이블이 **아직 없습니다**.
  기존 CRM 목표 테이블은 **부서별 개발목표**만 있어서 축이 다릅니다.
* 📊 **현재 상태** = `SILVER.CRM_BIZ_TARGET` **0행** → `GOLD.FACT_TARGET_PROJECT` **0행**.
* 💡 **주니어 포인트** = `FACT_TARGET_PROJECT` 가 0행인 걸 보고 *"모델이 고장났다"* 고 생각하기 쉽습니다.
  아닙니다. **상류가 0행이니 하류가 0행인 게 정상**입니다. 이걸 **스텁(stub)** 이라고 부릅니다.
  🟢 스텁을 미리 만들어 두는 이유 = 데이터가 오는 날 **코드 수정 없이** 바로 가동되게 하려고.

#### ② 채널·경로별 개발목표 테이블 (신규)

* 🎯 **하려던 일** = *"디지털 광고로 유입시키려던 목표 대비 실제 유입은?"* 채널별 ROI 분석.
* 🚧 **막힌 이유** = **실적 쪽에는 유입경로 축이 있는데 목표 쪽에는 없습니다.**
* 💡 **주니어 포인트** = 목표 대비 실적을 비교하려면 **양쪽의 축(grain)이 같아야** 합니다.
  실적이 채널별로 쪼개져 있어도 목표가 부서별 총량뿐이면 **비교 자체가 성립하지 않습니다.**

#### ③ `HOL-1` 공휴일 캘린더

* 🎯 **하려던 일** = *"영업일 기준"* 실적 집계, `D+5 영업일` 반응률.
* 🚧 **막힌 이유** = 공휴일 목록 원천이 **전 스키마에 없습니다**(키워드 검색 결과 0건).
* 📊 **현재 상태** = `GOLD.DIM_DATE` 의 `IS_HOLIDAY` 는 dbt 모델이 **`FALSE` 하드코딩** →
  16,437일 **전건 FALSE**.
* 🔴 **주니어가 반드시 알아야 할 위험** = 컬럼이 **있고**, 값도 **채워져 있습니다**(`FALSE`).
  그래서 이걸 그대로 쓰면 **"3년간 공휴일이 하루도 없었다"** 는 결론이 나옵니다.
  이게 **「전건 센티넬」의 무서움**입니다 — `NULL` 이면 의심하지만 `FALSE` 는 의심하지 않습니다.
* 🟢 **지금의 올바른 대응** = 주말은 `DAY_OF_WEEK` 로 계산할 수 있으니 **주말만 반영**하고,
  *"공휴일 미반영"* 을 지표 설명에 **명시**합니다.

### 3-2. B유형 (컬럼 구조적 부재) — 2건

#### ④ `AD-5` 방송(VIDEO) 광고 개발실적

* 🎯 **하려던 일** = *"방송 광고 1건당 회원 개발 단가는?"*
* 🚧 **막힌 이유** = `VIDEO_AD_CMPGN_DTLS` 에 개발실적 계열 컬럼이 **0개**입니다.

## 🧰 4. 실전 — 요청서를 쓰기 전에 하는 5단계

```
1단계  현상 확인      "무슨 숫자가 안 나오는가?"          → 지표·보고서 이름을 특정
2단계  계층 추적      GOLD → SILVER → BRONZE 역방향       → 어디서 끊겼는지 찾는다
3단계  유형 판정      A(테이블)/B(컬럼)/C(값)/D(포맷)     → 요청 문구가 여기서 결정된다
4단계  실측 첨부      19번 §6 쿼리 실행 결과를 붙인다      → "이미 넣었는데요" 반송 방지
5단계  가치 명시      "해소되면 어떤 지표가 열리는가"      → 우선순위를 확보한다
```

### 4-1. 유형 판정 치트시트

| 이 쿼리를 돌렸을 때 | 판정 | 요청 문구 |
|---|---|---|
| `INFORMATION_SCHEMA.TABLES` 에 테이블이 없다 | **A** | *"신규 테이블 제공"* + 컬럼 스펙 |
| 테이블은 있는데 `COLUMNS` 에 그 컬럼이 없다 | **B** | *"항목(컬럼) 신설"* ← 적재 재실행 아님 |
| 컬럼은 있는데 `COUNT(컬럼) = 0` | **C** | *"수집하는지 / 추출에서 빠졌는지 확인"* |
| 특정 시점부터 값이 0 이고 다른 컬럼이 채워진다 | **D** | *"기존 항목 재제공 또는 환산식 확정"* |

### 4-2. 🔴 요청 전 마지막 점검 6개

| # | 점검 | 안 하면 생기는 일 |
|---|---|---|
| 1 | A·B·C 유형을 한 메일에 섞지 않았나 | 담당자가 자기 몫을 못 골라 회신이 멈춘다 |
| 2 | 의사결정(17번) 항목을 섞지 않았나 | 규칙 논의에 묻혀 항목 요청이 잊힌다 |
| 3 | 「컬럼이 없다」와 「값이 없다」를 구별했나 | 적재를 다시 돌려도 영원히 안 나온다 |
| 4 | 현재 상태 실측을 첨부했나 | *"저희는 보냈습니다"* 로 반송된다 |
| 5 | 해소 시 열리는 지표를 적었나 | 업무 가치가 안 보여 우선순위가 밀린다 |
| 6 | 🔴 **「입고되면 자동 해소」라고 쓰지 않았나** | `BLOCKING-1` 처럼 **전제가 틀린 채 실행**된다 |

## 🎓 5. 이 문서의 핵심 6줄

1. **「규칙을 몰라서 못 함」(17번)과 「데이터가 없어서 못 함」(19번)을 절대 섞지 마라.**
   받는 사람이 혼자 답할 수 있는 단위로 쪼개는 것이 일을 끝내는 기술이다.
2. **「없다」는 4층이다** — 테이블이 없다 / 컬럼이 없다 / 값이 없다 / 바뀌었다.
   층이 다르면 요청 문구와 일정 추정이 완전히 달라진다.
3. **「입고되면 해결된다」는 예약 조치는, 입고된 날 전제부터 다시 재라.**
   회원 마스터 전량입고 후에도 고아 9,376행이 남아 `error` 승격 처방이 폐기됐다.
4. **`warn` 은 실패가 아니라 관측이다.** 구조적으로 상시 발생하는 위반은 지우지도 실패시키지도 말고
   **사유를 적고 추세를 감시**해라.
5. **패턴 매칭 건수를 근거로 쓰지 마라.** `%RST%` 가 `FRST_RGSTR_ID` 를 잡는다.
   **매칭된 실물을 열어 눈으로 확인**한 뒤에 판정해라.
6. **대체안을 제안하기 전에 그 대체안의 채움률을 먼저 재라.**
   이메일 오픈율의 대체 후보였던 알림톡 클릭률도 0건이었다.
