## 1. 개요

```
[A 계정]  --(Direct Share, 동일 리전)-->  [B 계정]
[B 계정]  --(로컬 물리적 다운로드, CSV+GZIP)-->  [작업 서버/로컬(Windows)]
[로컬]    --(업로드)-->                     [C 계정]
```

- **A 계정**: 원본 데이터 보유(Provider)
- **B 계정**: 공유 수신 및 파일 추출/다운로드 수행(Consumer)
- **C 계정**: 최종 적재 대상(Target)

> 전제: A와 B는 **동일 클라우드/동일 리전**이므로 Direct Share가 가능하다.
> C는 리전/클라우드가 다를 수 있으므로 파일 기반(물리적 이관)으로 처리한다.

### 1.1 설계 원칙 (Snowflake 기술문서 기준)
- **파일 포맷: CSV + `COMPRESSION = GZIP`**
  - `GZIP`은 **CSV/JSON** 언로드에서 지원. **PARQUET 언로드는 `SNAPPY/LZO/NONE`만 지원(GZIP 불가)**.
- **전체 스키마 DDL을 먼저 추출**해 C에 동일 구조를 만든 뒤 적재한다.
  - CSV 적재는 **위치(순서) 기반**이며 `MATCH_BY_COLUMN_NAME`을 **지원하지 않는다**(Parquet/ORC/Avro/JSON 전용).
  - 따라서 **원본과 동일한 컬럼 순서·데이터 타입**이 보장되어야 정확히 적재된다.
- **언로드/적재 옵션은 반드시 대칭**: `HEADER=TRUE` ↔ `SKIP_HEADER=1`, `NULL_IF`, `FIELD_OPTIONALLY_ENCLOSED_BY`, `EMPTY_FIELD_AS_NULL`, `TIMESTAMP_FORMAT`.

## 3. 1단계: A → B (Direct Share, 동일 리전)

### 3.1 A 계정 — Share 생성 및 부여
▶ 실행: **`02_데이터마이그 A_PRODUCER.sql`**

- 순서: 공유 생성 → DB `USAGE` → 스키마 4개 `USAGE` → 스키마별 `SELECT ON ALL TABLES` → `ALTER SHARE ADD ACCOUNTS = GB72026` → 확인.
- **스키마 단위 부여가 필수**: DB `USAGE`만 주면 B에서 테이블이 보이지 않는다.
- **`ALL TABLES`는 '현재 존재하는' 테이블만 대상**이다. 이후 테이블이 추가되면 재부여해야 한다.
- 확인 포인트: `SHOW GRANTS TO SHARE` 결과에 DB 1 + 스키마 4 + 테이블 53 권한, `SHOW SHARES LIKE 'MIG_SHARE'` 의 `to` 컬럼에 `GB72026`.
- 공유 직후 스크립트 5단계에서 **이관 대상 목록/규모 스냅샷**(테이블별 `row_count`, `bytes`)을 기록한다. 6장 검증의 원본 기준값이다.

### 3.2 A 계정 — 전체 스키마 DDL 추출
▶ 실행: **`02_데이터마이그 A_PRODUCER.sql`** 의 하단 `GET_DDL` 구간(주석 처리되어 있어 필요 시 해제)
▶ 산출물: **`04_데이터마이그 GN_DW_BRONZE_DDL_20260730.sql`**

- CSV 적재는 위치 기반이라 **C에 원본과 동일한 테이블 구조**를 먼저 만들어야 한다.
- 스키마 4개(`BRONZE_CRM/GA4/ERP/AGENCY`)를 각각 추출 → 테이블 53개 + 시퀀스 2 + 파일포맷 3 포함.
- 공유받은(imported) DB에서는 `GET_DDL`이 제한될 수 있으므로 **DDL 추출은 원본 A에서 수행**한다.
- C에서 실행하기 전, DB/스키마명을 C 환경에 맞게 치환한다(파일 상단 USAGE 참조).

### 3.3 B 계정 — Share로부터 DB 생성
▶ 실행: **`03_데이터마이그 B_BROKER.sql`** (1~3번 구간)

- `SHOW SHARES` 의 **INBOUND** 항목에 `CMRQTUT.XC97295 / MIG_SHARE` 가 보여야 한다.
- 마운트 DB명은 `GN_DW_SHARED`. ACCOUNTADMIN으로 직접 작업하므로 `GRANT IMPORTED PRIVILEGES` 는 생략했다(별도 작업 역할을 쓸 때만 필요).
- **공유받은 DB는 읽기 전용**이다. 파일로 빼려면 스테이지 언로드(4장)가 필수.

## 4. 2단계: B → 로컬 물리적 다운로드 (CSV + GZIP)

### 4.1 스테이지 준비
▶ 실행: **`03_데이터마이그 B_BROKER.sql`** (2번 구간)

- 스테이지: `SANDBOX.TOOLS.my_export_stage`. **스테이지가 먼저 존재해야** `COPY INTO @stage` 가 가능하다.
- 파일 포맷은 별도 객체 없이 **스테이지에 인라인**(`TYPE=CSV`, `FIELD_OPTIONALLY_ENCLOSED_BY='"'`, `COMPRESSION=GZIP`)으로 지정했다.
- ⚠️ **언로드 전 스테이지를 반드시 비운다**(`CREATE OR REPLACE STAGE` 또는 `REMOVE @stage`). `COPY INTO ... OVERWRITE=TRUE` 는 **같은 이름 파일만** 덮어쓰고 폴더는 비우지 않는다. 병렬 워커/분할 개수가 배치마다 달라지면 이름이 겹치지 않은 **이전 배치 파일이 살아남아** 로컬·C까지 함께 옮겨진다(8장-6에서 실제로 겪음).
- ⚠️ 인라인 최소 옵션으로 언로드한 결과 **NULL이 `\\N`(3글자)** 로 기록되었고, C 적재 시 `NULL_IF` 보정이 필요했다(8장-1, `05_..C_CONSUMER.sql` 의 `FF_CSV_LOAD`).
  재이관 시에는 **언로드 단계에서** `NULL_IF`·`EMPTY_FIELD_AS_NULL`·`TIMESTAMP_FORMAT` 을 명시하는 편이 안전하다.

### 4.2 전 테이블 일괄 언로드
▶ 실행: **`03_데이터마이그 B_BROKER.sql`** (5~6번 구간)

- `GN_DW_SHARED.INFORMATION_SCHEMA.TABLES` 를 순회하며 `BRONZE_*` 의 모든 BASE TABLE을 동적 `COPY INTO` 한다.
- **경로 규칙**: `@stage/<스키마>/<테이블>/` — 이 구조가 4.3 다운로드 → 5.3 업로드 → 5.4 적재까지 그대로 이어진다.
- 완료 후 `LIST` 로 **파일 수를 기록**한다. 5.3 업로드 후 C 스테이지 파일 수와 대조할 기준값이다.
- `HEADER = TRUE` → C 적재의 `SKIP_HEADER = 1` 과 짝.
- `MAX_FILE_SIZE` 미지정 → 기본값 분할. 대용량 튜닝 시 `MAX_FILE_SIZE = 268435456`(약 256MB) 등을 지정한다(최대 5GB).
- 소량 검증만 할 때는 스크립트의 `SAMPLE (10000 ROWS)` 주석을 해제한다.
- 익명 블록은 **`EXECUTE IMMEDIATE $$ ... $$;` 로 감싸 놓았다**(8장-3). Workspace의 파일 전체 실행은 `;` 단위로 문장을 자르므로 감싸지 않으면 블록이 조각나 문법 오류가 난다.
- **웨어하우스 크기**: 1.17억 행 / 약 2.8GB 를 언로드한다. XS로는 오래 걸리고 문장 타임아웃 위험이 있어 언로드 구간만 M~L로 올린 뒤 원복한다. 2026-08-12 실행은 LARGE 사용.
- **2026-08-12 실행 결과**: 53개 테이블 → 435 파일 / 52 폴더 / 3,427,853,840 B. `BRONZE_BIGQUERY.SYNC_ERR_INFO`(0행)는 파일이 생성되지 않아 폴더가 52개인 것이 정상이다.

### 4.3 로컬로 다운로드 (Windows)
`GET`은 클라이언트에서 실행해야 한다. **Snowsight 워크시트에서는 불가.**

```powershell
# 0) 로컬 폴더 완전 초기화 — 이전 배치 파일이 남아 있으면 그대로 C까지 올라간다 (8장-6)
Remove-Item -Recurse -Force downloaded_data

# 전체 일괄 다운로드 (B 계정 연결)
snow stage copy "@SANDBOX.TOOLS.my_export_stage/" "downloaded_data/" `
    -c <B_CONNECTION> --recursive

# 스키마 단위로 나눠 받기
foreach ($SCHEMA in @('BRONZE_CRM', 'BRONZE_AGENCY', 'BRONZE_ERP', 'BRONZE_BIGQUERY')) {
    Write-Host "=== 다운로드: $SCHEMA ==="
    snow stage copy "@SANDBOX.TOOLS.my_export_stage/$SCHEMA/" "downloaded_data/$SCHEMA/" `
        -c <B_CONNECTION> --recursive
}

# 다운로드 파일 수 / 용량 확인
Get-ChildItem downloaded_data -Recurse -File | Measure-Object -Property Length -Sum
```

- 파일은 `.csv.gz` 로 **압축 상태 그대로** 저장된다.
- 다운로드 구조: `downloaded_data\<SCHEMA>\<TABLE>\*.csv.gz` (5.3 업로드 구조와 동일)
- 다운로드 후 파일 개수/총 용량을 B의 `LIST` 결과와 대조한다.
- DDL 스크립트(`04_...DDL_20260730.sql`)도 함께 C 작업 폴더에 준비한다.

> 대용량이면 로컬 대신 **외부 스테이지(S3/GCS/Azure)** 경유가 유리하다(GET/PUT 없이 계정 간 직접 이관, 6.2).

### 4.4 참고: 반정형/바이너리 컬럼의 대안 경로 (미사용)
`VARIANT/OBJECT/ARRAY/GEOGRAPHY/GEOMETRY/BINARY` 컬럼은 CSV 왕복 시 손실·오변환 위험이 있어, 일반적으로는 **해당 테이블만 Parquet(SNAPPY)** 로 분리 이관하는 것이 권장된다.

> ⚠️ **이번 이관은 이 경로를 쓰지 않았다.** GA4를 포함한 `BRONZE_*` 전 테이블을 CSV+GZIP으로 일괄 언로드하고,
> GA4 VARIANT는 C 적재 시 `TRY_PARSE_JSON` 으로 복원했다(5.5).
> 이번 대상 중 반정형 컬럼 보유 테이블은 `BRONZE_BIGQUERY.events_20260501` (VARIANT 11개) 하나뿐이었다.
> Parquet 경로를 택할 경우: 언로드는 `COMPRESSION=SNAPPY`, 적재는 `MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE` 사용 가능(CSV와 달리 지원), 업로드 시 재압축 금지.

## 5. 3단계: 로컬 → C 계정 적재

### 5.1 DDL로 스키마/테이블 재생성 — 필수 선행
▶ 실행: **`04_데이터마이그 GN_DW_BRONZE_DDL_20260730.sql`**

CSV는 위치 기반 적재이므로 테이블이 **먼저** 있어야 한다. DDL 미실행 상태로 적재하면 `loaded tables: 0` 이 된다.

```powershell
# DDL 일괄 실행 (C 계정 연결)
snow sql -c <C_CONNECTION> -f "50_handoff\04_데이터마이그 GN_DW_BRONZE_DDL_20260730.sql"

# 생성 확인 (53개 기대: CRM 45 / AGENCY 4 / ERP 1 / GA4 3)
snow sql -c <C_CONNECTION> -q "SELECT table_schema, COUNT(*) FROM GN_DW.INFORMATION_SCHEMA.TABLES WHERE table_schema LIKE 'BRONZE_%' AND table_type='BASE TABLE' GROUP BY 1 ORDER BY 1"
```

### 5.2 적재용 파일 포맷/스테이지 준비
▶ 실행: **`05_데이터마이그 C_CONSUMER.sql`** (상단 ~ A.2 구간)

- 스테이지: `SANDBOX.TOOLS.MIG_LOAD_STAGE`, 파일 포맷: `SANDBOX.TOOLS.FF_CSV_LOAD`.
- ⚠️ **NULL 토큰 주의**: 언로드 데이터의 NULL은 `\\N`(백슬래시 2개 + N, **3글자**)로 기록돼 있었다(언로드 시 백슬래시 이스케이프로 이중화).
  숫자 컬럼에서 `Numeric value '\N' is not recognized` 오류의 직접 원인이므로 `NULL_IF` 에 3글자 토큰을 반드시 포함한다(스크립트에 반영됨).
- 확인법: 스테이지 파일을 `SELECT $n, LENGTH($n) ... WHERE TRY_TO_DOUBLE($n) IS NULL` 로 조회해 NULL 토큰의 실제 길이(3)를 확인.
- `SKIP_HEADER = 1` (언로드 `HEADER=TRUE` 와 대칭), `EMPTY_FIELD_AS_NULL = TRUE`, `TRIM_SPACE = FALSE`, `ESCAPE_UNENCLOSED_FIELD = NONE`.

### 5.3 로컬 파일 → C 스테이지 업로드 (Windows)
다운로드 구조를 그대로 스테이지에 재현한다: `<SCHEMA>/<TABLE>/*.csv.gz`
PowerShell에서는 줄 연속 문자로 `` ` ``(백틱), 배열은 `@( )` 를 사용한다.

```powershell
# 0) C 스테이지 초기화 — 이전 배치 잔존 파일 제거 (8장-6)
snow sql -c <C_CONNECTION> -q "REMOVE @SANDBOX.TOOLS.MIG_LOAD_STAGE/"

# 이미 GZIP 압축 상태이므로 재압축 금지(--no-auto-compress)
```

### 5.4 스테이지 → 테이블 적재 (스키마 일괄)
▶ 실행: **`05_데이터마이그 C_CONSUMER.sql`** (A.3 프로시저 생성 → A.4 `CALL`)

## 8. 이번에 겪은 함정 (핸드오버 핵심)

1. **NULL 토큰 `\\N`(3글자)**: 기본 `NULL_IF` 로는 숫자 컬럼 로드 실패(`Numeric value '\N' is not recognized`). → `05_..C_CONSUMER.sql` 의 `FF_CSV_LOAD` 3종 토큰 필수(5.2).
2. **스크립팅 레코드 점 표기 실패**: `FOR rec IN (쿼리) DO rec.col` → `invalid identifier`. → 커서 + `FETCH INTO`(5.4).
   - 단, `03_..B_BROKER.sql` 처럼 **커서를 먼저 DECLARE 한 뒤** `FOR rec IN c1 DO rec.col` 은 정상 동작했다.
3. **익명 블록 세미콜론 분할**: 툴/CLI가 `;` 에서 문을 잘라 파싱 오류 → `EXECUTE IMMEDIATE $$ ... $$;` 로 감싸거나 저장 프로시저로 실행.
4. **GA4 VARIANT**: CSV 경유 시 JSON이 문자열로 저장 → `TRY_PARSE_JSON` 변환 필수(5.5).
5. **대상 테이블 미생성**: DDL 미실행 상태로 로드하면 `loaded tables: 0`. → 5.1 선행 확인.
6. **스테이지 잔존 파일(2026-07-30)**: B 언로드 스테이지를 비우지 않아 7/13 배치 파일이 살아남았고, 로컬·C 스테이지까지 함께 옮겨졌다.
   `COPY INTO ... OVERWRITE=TRUE` 는 **같은 이름 파일만** 덮어쓴다(폴더를 비우지 않음). 워커 분할 개수가 배치마다 달라 이름이 겹치지 않으면 구 파일이 남는다.
   - 증상 A: `Number of columns in file (62) does not match that of the corresponding table (64)` — `BRONZE_ERP.BDGT_ACMSLT_LEDGER`. 신규 컬럼이 **중간(11·12번)** 삽입이라 `ERROR_ON_COLUMN_COUNT_MISMATCH = FALSE` 로 넘기면 이후 전체가 한 칸씩 밀려 **오적재**된다. 절대 쓰지 말 것.
   - 증상 B: 스키마가 같은 테이블은 오류 없이 **중복 적재**. 예) `TD_MS_PSTMTR_LQY_SNDNG` 의 두 파일이 행수 2,022 / min·max 동일.
   - 대책: 4.1 언로드 전 `REMOVE`, 4.3 로컬 폴더 초기화, 5.3 업로드 전 C 스테이지 `REMOVE`, **5.3.1 적재 전 검증**(스크립트 A.1)을 4중으로 배치했다.

## 9. 주의사항 / 리스크

- **읽기 전용 공유**: B는 공유 DB를 수정할 수 없으므로 스테이지 언로드가 필수.
- **CSV 적재 정확도**: 위치 기반이므로 컬럼 순서/타입을 원본과 동일하게 재현해야 한다. 언로드/적재 옵션 대칭 필수(1.1).
- **반정형/BINARY 타입**: CSV 왕복 시 손실·오변환 위험. 이번에는 `TRY_PARSE_JSON` 으로 복원했으나, 신규 이관은 Parquet(SNAPPY) 분리 권장(4.4).
- **압축 재적용 금지**: 이미 `.csv.gz` 이므로 업로드 시 `--no-auto-compress`.
- **파일 전송은 클라이언트 실행**: Snowsight 워크시트 불가, Snowflake CLI(`snow stage copy`) 필요.
- **파일 크기 제한**: 언로드 파일 최대 5GB, `MAX_FILE_SIZE` 기본 16MB. 대용량은 분할 언로드.
- **용량 산정**: 로컬 다운로드 시 디스크 여유 공간 사전 확인.
- **보안/규정**: 물리적 다운로드 데이터의 PII 포함 여부 확인, 전송/저장 구간 암호화 및 접근 통제.
- **리전 전송 비용**: 계정/리전 간 이관 시 데이터 전송 비용 발생 가능.
- **일관성**: 이관 중 A 원본이 변경되면 스냅샷 시점 기준으로 고정 권장.
