# A1. 운영자 가이드

대상 독자 = GN_DW 를 넘겨받아 사용자·권한·비용·배포를 관리하는 운영자.
롤별 상세 권한은 A2 가 정본이다. 이 문서는 **절차**와 **판단 기준**만 다룬다.

- `[공통]` = 절차·원칙(계정 무관). `[ENV]` = 현재 값(정본 = `_ENV/<계정>/A1_*.csv`).
- 이 문서의 SQL 블록은 전부 **🔴 미실행 템플릿**이다. `<...>` 를 치환하고 운영자가 직접 실행한다.

## 1. [공통] 운영 원칙 6가지

1. **소유는 GN_DW_ADMIN 하나다.** GN_DW 안의 객체는 ADMIN 이 만든다. 예외 = dbt 산출물(GN_DW_DBT 소유).
2. **계정 레벨은 ACCOUNTADMIN 이 한다.** 사용자 생성·네트워크/인증 정책·리소스 모니터·CoWork object·CORTEX 롤 부여.
3. **롤 부여는 SECURITYADMIN(또는 USERADMIN)이 한다.** 사람에게는 GN_DW 롤만 준다. ACCOUNTADMIN·SYSADMIN 을 업무 사용자에게 주지 않는다.
4. **ALL + FUTURE 는 쌍이다.** 스키마를 드롭·재생성하면 FUTURE grant 까지 사라진다 ⇒ 07 §D 를 전량 다시 실행해야 끝난다(07 머리말 O91).
5. **SV·Agent·Streamlit 은 FUTURE grant 가 없다.** 새로 만들면 객체마다 소비 3롤(ANALYST·VIEWER·SERVICE)에 직접 부여한다.
6. **「does not exist or not authorized」는 대개 권한 문제다.** 객체를 다시 만들기 전에 `SHOW GRANTS TO ROLE` 부터 본다(07 §D.4 O121).

## 2. 사용자 온보딩 · 오프보딩

### 2-1. [공통] 업무 유형 → 부여 롤

| 업무 | 부여 롤 | 기본 WH | 비고 |
|---|---|---|---|
| 현업 조회(대시보드·Agent 질의) | GN_DW_VIEWER | GN_DW_ANALYTICS_WH | BRONZE·SILVER 접근 없음 |
| 분석가(SQL·Agent·원천 확인) | GN_DW_ANALYST | GN_DW_ANALYTICS_WH | VIEWER 상속 · BRONZE/SILVER SELECT · 🔴 CoCo 차단은 A3(운영계) |
| 데이터 엔지니어(사람) | GN_DW_ENGINEER | GN_DW_DEV_WH | dbt 실행은 GN_DW_DBT(서비스용) |
| 외부 적재 담당 | GN_DW_LOADER | GN_DW_ETL_WH | BRONZE 쓰기 · 월마감/ML 프로시저 |
| 서비스 계정(API·앱) | GN_DW_SERVICE | GN_DW_ANALYTICS_WH | `TYPE = SERVICE` 권장 · 키 페어 인증 |
| DW 관리자 | GN_DW_ADMIN | GN_DW_DEV_WH | 소수 지정 · 하위 롤 전부 상속 |

### 2-2. [공통] 온보딩 절차 (🔴 미실행 템플릿)

```sql
-- ① 사용자 생성 (ACCOUNTADMIN 또는 USERADMIN)
USE ROLE USERADMIN;
CREATE USER IF NOT EXISTS <USER_NAME>
  LOGIN_NAME = '<login>'
  EMAIL = '<email>'                     -- 알림 수신자 동기화(§5)가 이 값을 쓴다
  DISPLAY_NAME = '<이름/부서>'
  DEFAULT_ROLE = <GN_DW_ROLE>
  DEFAULT_WAREHOUSE = <WH>
  DEFAULT_SECONDARY_ROLES = ()          -- 07 머리 · 권한 합집합 평가로 인한 오판 방지
  MUST_CHANGE_PASSWORD = TRUE;

-- ② 롤 부여 (SECURITYADMIN)
USE ROLE SECURITYADMIN;
GRANT ROLE <GN_DW_ROLE> TO USER <USER_NAME>;

-- ③ 확인
SHOW GRANTS TO USER <USER_NAME>;
```

- `DEFAULT_SECONDARY_ROLES = ()` 를 쓰는 이유: 기본값(ALL)이면 보조 롤 권한이 합쳐져 차단 테스트가 거짓 PASS 가 된다(07 §D.4 실측).
- 서비스 계정은 `TYPE = SERVICE` 와 `RSA_PUBLIC_KEY` 로 만들고 비밀번호를 두지 않는다.
- 롤 부여 직후 §5 알림 수신자 동기화를 1회 실행한다.

### 2-3. [공통] 오프보딩 절차 (🔴 미실행 템플릿)

```sql
-- ① 소유 객체 확인 — 개인 Workspace(USER$)·Personal DB 앱은 사용자 삭제 시 함께 사라진다
SHOW GRANTS TO USER <USER_NAME>;

-- ② 롤 회수 → 비활성화 (DROP 은 최후 · 감사 이력 보존을 위해 DISABLED 를 기본으로)
USE ROLE SECURITYADMIN;
REVOKE ROLE <GN_DW_ROLE> FROM USER <USER_NAME>;
USE ROLE USERADMIN;
ALTER USER <USER_NAME> SET DISABLED = TRUE;

-- ③ 알림 수신자 정리 — 동기화가 IS_ACTIVE_YN='N' 으로 내린다
USE ROLE GN_DW_ADMIN;
CALL GN_DW.OPS.USP_SYNC_ALERT_RECIPIENTS();
```

- 서비스 계정 교체 시: 새 키 등록(`RSA_PUBLIC_KEY_2`) → 앱 전환 → 옛 키 해제 순서로 무중단 교체한다.

## 3. 롤 기반 데이터 노출 범위 제어 (3단계)

노출 범위는 아래 3단계를 **위에서부터** 조인다. 앞 단계로 막을 수 있으면 뒤 단계를 쓰지 않는다.

### 3-1. [공통] 1단계 — 스키마·객체 GRANT (RBAC)

| 노출 수준 | 롤 | 볼 수 있는 계층 |
|---|---|---|
| 원천 포함 | ANALYST · ENGINEER | BRONZE_* · SILVER · GOLD · ML · MSTR · SERVING |
| 정제 결과만 | VIEWER · SERVICE | GOLD · ML · MSTR · SERVING |
| 운영 객체 | ADMIN · ENGINEER · DBT | OPS · DBT_TEST__AUDIT (🟢 ANALYST 의 OPS 접근은 2026-10-20 결정으로 회수 대상) |

- 새 스키마를 추가하면 07 §D 의 패턴(USAGE + ALL + FUTURE)을 그대로 복사한다. MSTR 이 그 선례다(`00_mstr_schema_role.sql`).
- 점검 = `python3 scripts/a2_matrix_build.py <계정>` 의 `A2_설계외부여.csv` 가 0 이어야 한다(A2 §6).

### 3-2. [공통] 2단계 — SERVING 뷰 · SV 로 범위 한정

- 현업·Agent 는 GOLD 테이블이 아니라 **SERVING 의 SV·뷰**로 소비한다. SV 는 노출 컬럼·지표·필터를 정의 안에서 고정한다.
- 특정 롤에만 열 SV·뷰는 그 롤에만 SELECT 를 준다. 🔴 **SV 와 base 뷰를 같은 롤 집합으로 맞춘다** — 반례였던 `SV_ML_REALTIME_SIMULATOR`(SV 소비 3롤 · base 뷰 ANALYST 만)는 2026-10-20 결정으로 base 뷰를 VIEWER·SERVICE 에 연다(A2 §7 · `A2_권한조정_적용완료.sql` [1]).
- Agent 는 spec 에 배선된 SV 목록으로 범위가 정해진다(spec 실측 EXECUTIVE 17 · MARKETING 28 · MEMBER 28 · A0 §4-1). Agent COMMENT 의 SV 수는 낡았으니 판단 근거로 쓰지 않는다. Agent 에 SV 를 추가하면 그 Agent 사용자 전원이 그 SV 를 보게 된다.
- 🔴 owner's rights 주의: Streamlit·소유자 권한 프로시저는 **소유 롤 권한**으로 돈다. 앱 소유를 ADMIN 에 두면 VIEWER 가 BRONZE 를 간접 조회할 수 있다(07 §D.7) ⇒ 앱 소유 = GN_DW_SERVICE · 코드 = caller's rights 연결.

### 3-3. [공통] 3단계 — 마스킹 · 행 접근 정책

- 정책 객체 위치 = `GN_DW.SECURITY`(MANAGED ACCESS · 07 :188).
- 신규 설계는 트랙 B **N02**(정책 SQL · 미실행)로 만든다. 이 문서에서 정책을 새로 만들지 않는다.
- 정책을 붙이기 전에 2단계(SV 노출 컬럼 축소)로 해결되는지 먼저 본다 — 정책은 모든 질의에 비용과 디버깅 부담을 더한다.

두 설계 문서가 다른 안을 적고 있다. 둘 다 라이브에 적용되지 않았다(Streamlit 0 · LAB 스키마 없음).

| 안 | 내용 | 근거 |

## 5. 알림 수신자 관리 (OPS)

### 5-1. [공통] 구조

- 수신자 표 = `GN_DW.OPS.ALERT_RECIPIENT_CONFIG`(사용자 1행 · 페르소나 플래그 4종).
  - `IS_PIPELINE_ADMIN_YN` · `IS_ANALYST_YN` · `IS_BUSINESS_USER_YN` · `IS_DBT_ALERT_YN`
- 동기화 = `CALL GN_DW.OPS.USP_SYNC_ALERT_RECIPIENTS()` — `SHOW USERS` 의 이메일·비활성 상태를 반영한다. 플래그는 보존한다. 이메일 없는 사용자는 제외한다.
- 발송 = `USP_SEND_PIPELINE_ERROR_ALERT(파이프라인, 요약, 스택, 대상)` · 대상 = `PIPELINE_ADMIN`·`ANALYST`·`BUSINESS_USER`·`DBT_ALERT`·`ALL`.
- dbt 경고 메일 = Alert `OPS.ALERT_DBT_WARN_SPNSR_CLS_DUP`(매일 09:00 KST) → `IS_DBT_ALERT_YN='Y'` 수신자.

### 5-2. [공통] 수신자 변경 절차 (🔴 미실행 템플릿)

```sql
USE ROLE GN_DW_ADMIN;
USE WAREHOUSE GN_DW_ETL_WH;
CALL GN_DW.OPS.USP_SYNC_ALERT_RECIPIENTS();              -- 신규 사용자 반영

-- dbt 경고 수신자 = 이 변수가 정본(선언형 · 목록에 없으면 N 으로 내려간다)
SET DBT_ALERT_RECIPIENTS = '<USER1>,<USER2>';
-- 이후 07_OPS_알림 §3-1 블록(UPDATE · 누락 검증 · 확인 SELECT)을 그대로 실행한다

-- 장애 알림 수신자
UPDATE GN_DW.OPS.ALERT_RECIPIENT_CONFIG
SET IS_PIPELINE_ADMIN_YN = 'Y', UPDATED_AT = CURRENT_TIMESTAMP(), UPDATED_BY = CURRENT_USER()
WHERE USER_NAME IN ('<USER1>');
```

- 🔴 07_OPS_알림 §3 의 `WHERE USER_NAME = 'CHOIH'` 예시는 다른 계정 사용자다. 그대로 실행하지 않는다.
- 🟢 2026-10-20 결정: ANALYST 의 이 표 SELECT·OPS USAGE 를 회수한다(A2 §7 · `A2_권한조정_적용완료.sql` [2]). ANALYST 알림 **수신**은 `IS_ANALYST_YN` 플래그로 계속된다(표 조회 권한과 무관).
