# 데이터 웨어하우스 역할(권한) 설계서 — 이번에 추가된 역할 9개

> **이 문서를 읽는 분** = Snowflake 를 처음 맡는 IT 담당자.
> **무엇을 알게 되나** = ① Snowflake 권한이 어떻게 움직이는지 ② 이번에 왜 역할을 새로 만들었는지
> ③ 9개 역할이 각각 무엇인지 ④ 사람을 추가·변경할 때 무엇을 하고 무엇을 하면 안 되는지.
> 앞으로 할 작업 순서는 별도 문서 `12_agent개선과제/O273_롤전환_작업순서.md` 에 있습니다.

---

## 1. 먼저 알아 둘 개념 5가지

### 1-1. 역할(Role) = 「열쇠 꾸러미」

Snowflake 는 **사람에게 직접 권한을 주지 않습니다.** 권한은 「역할」에 담고, 사람에게는 역할을 줍니다.

```
  [권한]  "이 표를 읽을 수 있다"  "이 Agent 를 쓸 수 있다"
     │  담는다
     ▼
  [역할]  🔑 열쇠 꾸러미
     │  준다
     ▼
  [사람]  로그인한 사용자
```

- 사람이 바뀌어도 역할은 그대로 둡니다 → **사람에게 역할만 줬다 뺏으면** 됩니다.
- 역할 안에 **다른 역할을 넣을 수 있습니다**(상속). 아래 1-3 의 2단 구조가 이것을 씁니다.

### 1-2. 데이터가 들어 있는 곳 — 데이터베이스 · 스키마 · 객체

```
  GN_DW (데이터베이스 = 건물)
   ├─ BRONZE  (스키마 = 층) 원천 그대로 · 사람은 못 들어감
   ├─ SILVER                정제 중간 단계 · 사람은 못 들어감
   ├─ GOLD                  분석용 표(테이블·뷰)         ◄─ 이번 역할이 여는 곳
   ├─ SERVING               Agent 가 쓰는 의미 모델(SV)·뷰 ◄─ 이번 역할이 여는 곳
   └─ OPS                   운영 도구 · 관리자만
```

- 사람에게 열어 주는 층은 **GOLD · SERVING 두 층뿐**입니다.
- **SV(시맨틱 뷰)** = 표 위에 「한글 이름 · 계산식 · 설명」을 붙인 의미 모델입니다. Agent(채팅 분석)는 이 SV 를 보고 SQL 을 만듭니다.
- **Agent** = 현업이 채팅으로 질문하는 분석 도우미입니다(마케팅 분석 · 회원 분석 · 경영·전사 분석).
- **웨어하우스** = 질문을 계산하는 **컴퓨터(과금 단위)**입니다. 쓸 권한이 없으면 아무 조회도 못 합니다.

### 1-3. 이번 설계의 핵심 — 2단 역할 구조

```
     사람 ──► 기능 역할(FR)  "어떤 업무를 하는 사람인가"   ← 사람에게 주는 것은 이것 하나뿐
                  │ 상속
                  ▼
              접근 역할(AR)  "어떤 원천의 데이터를 읽는가"  ← 사람에게 직접 주지 않음
                  │ SELECT
                  ▼
              GOLD · SERVING 의 표 · 뷰 · SV
```

- **접근 역할(AR · Access Role)** = 「데이터 묶음」. 원천(데이터를 준 곳)별로 묶었습니다.
- **기능 역할(FR · Functional Role)** = 「업무 묶음」. 업무에 필요한 접근 역할 몇 개를 담습니다.
- 장점 = 새 표가 생기면 **접근 역할 1곳**에만 넣으면 그 원천을 쓰는 모든 업무에 자동으로 퍼집니다.

### 1-4. 왜 원천별로 나눴나 — 「원천별 접근통제」

데이터를 준 곳마다 **볼 수 있는 사람이 다릅니다.** 2026-10 사용자 결정으로 아래처럼 나눴습니다.

| 원천 | 예 | 볼 수 있는 업무 |
|---|---|---|
| 공통(CRM · GA4 · 머신러닝 예측 등) | 회원 · 회비 · 캠페인 · 홈페이지 방문 | 마케팅 · 회원 · 기획실 |
| 대행사(AGENCY) | 광고비 · 매체 성과 · 광고비 시뮬레이션 | **마케팅만** |
| ERP | 예산 · 지출결의 | 마케팅 · 기획실 |
| 대행사 + ERP 결합 | 캠페인별 광고비·제작비·개발단가 | **마케팅만** |

### 1-5. 꼭 지켜야 하는 두 가지 설정

| 설정 | 값 | 왜 |
|---|---|---|
| 사람 1명 = 기능 역할 **1개** | 예: 마케팅 분석가는 `GN_DW_FR_MARKETING` 하나만 | 두 개를 주면 두 업무의 데이터가 합쳐져 통제가 무너집니다 |
| `DEFAULT_SECONDARY_ROLES = ()` | 빈 값 | Snowflake 는 기본으로 **그 사람이 가진 모든 역할을 동시에 켭니다**(보조 역할). 이걸 끄지 않으면 1인 1역할이 무의미해집니다 |

## 3. 역할 9개 상세

### 3-1. 기능 역할(FR) 4개 — 사람에게 주는 역할

| 역할 이름 | 누구에게 | 담긴 접근 역할 | 쓸 수 있는 Agent(화면 이름) | 컴퓨터 |
|---|---|---|---|---|
| `GN_DW_FR_MARKETING` | 마케팅 분석가 | COMMON · AGENCY · ERP · AGENCY_ERP (4개 전부) | 마케팅 분석 | `GN_DW_ANALYTICS_WH` |
| `GN_DW_FR_MEMBER` | 회원 분석가 | COMMON | 회원 분석 | `GN_DW_ANALYTICS_WH` |
| `GN_DW_FR_EXEC` | 기획실(경영·전사) 분석가 | COMMON · ERP | 경영·전사 분석 | `GN_DW_ANALYTICS_WH` |
| `GN_DW_FR_LEAD` | 팀장급 | 없음 | 없음 | 없음 |

- `GN_DW_FR_LEAD` 는 **지금 권한이 0개**입니다(개발계 실측). 지정된 Streamlit 앱 화면만 보게 할 예정이고, 어떤 앱을 열지는 아직 결정 전입니다(작업순서 문서 ⑧).

### 3-2. 접근 역할(AR) 4개 — 데이터 묶음

| 역할 이름 | 원천 | 표 | 뷰 | SV | 합계 | 대표 객체 |
|---|---|---|---|---|---|---|
| `GN_DW_AR_SRC_COMMON` | 공통 | 58 | 33 | 38 | **129** | 회원·회비·캠페인·GA4·ML 예측 · 지표사전 검색 |
| `GN_DW_AR_SRC_AGENCY` | 대행사 | 6 | 6 | 3 | **15** | `SV_AD` · `SV_AD_INFLOW_ALLOC` · `SV_ML_REALTIME_SIMULATOR` · `WIDE_AD_*` |
| `GN_DW_AR_SRC_ERP` | ERP | 4 | 1 | 3 | **8** | `SV_BUDGET` · `SV_BUDGET_YEARLY` · `SV_EXPENSE_RESOLUTION` · `WIDE_BUDGET` |
| `GN_DW_AR_SRC_AGENCY_ERP` | 대행사+ERP | 1 | 0 | 1 | **2** | `SV_MKTG_CAMPAIGN_COST` · `FACT_MKTG_CAMPAIGN_MONTHLY_COST` |
| | | | | | **154** | 운영계 게이트 보고값과 같음 |

- 모든 AR 은 `GN_DW` 데이터베이스와 `GOLD`·`SERVING` 스키마의 **USAGE(들어갈 권한)** 를 함께 가집니다.
- 개수는 개발계 2026-10-30 실측입니다. 표가 추가되면 늘어납니다.
- 어느 객체가 어느 원천인지는 **`12_agent개선과제/output/O270_source_class.csv` 가 정본**입니다. 이름(AD_·BUDGET 등)으로 추측하지 마세요.

### 3-3. 앱 소유 역할 1개

| 역할 이름 | 용도 | 현재 |
|---|---|---|
| `GN_DW_APP_OWNER` | Streamlit 앱(화면)의 **주인** 역할. 앱은 주인의 권한으로 데이터를 읽습니다. | 권한 0 · 앱 이전 전 |

- **왜 필요한가** — 지금 운영계 앱 10개의 주인이 구 역할 `GN_DW_ANALYST` 입니다. 구 역할을 없애면 앱이 바로 깨집니다. 그래서 앱 전용 주인을 먼저 만들고, 앱을 옮긴 다음에 구 역할을 정리합니다.
- 🔴 **사람에게 주지 마세요.** 이 역할을 가진 사람은 앱이 읽는 모든 데이터를 직접 읽게 됩니다.

## 4. 기존 역할과의 관계

| 기존 역할 | 지금 | 앞으로 |
|---|---|---|
| `GN_DW_ADMIN` | DB·SV·Agent 주인(관리자) | 유지 |
| `GN_DW_DBT` · `GN_DW_ENGINEER` · `GN_DW_LOADER` | 적재·개발 | 유지 |
| `GN_DW_ANALYST` | 분석가(BRONZE~SERVING 전부 읽기) · 앱 10개 주인 | 🔴 **회수 대상** — 앱 이전·사람 배정이 끝난 뒤 맨 마지막 |
| `GN_DW_VIEWER` | 읽기 전용 소비자 | 🔴 회수 대상(위와 같은 조건) |
| `GN_DW_SERVICE` | 서비스 계정(API·Streamlit) | 회수 여부 결정 전 |

> 구 역할은 원천을 가리지 않고 다 읽을 수 있습니다. 그래서 **새 역할을 줘도 구 역할이 남아 있으면 통제 효과가 없습니다.** 정리는 작업순서 문서 ⑪ 에서 합니다.

## 5. 권한이 사라지지 않게 하는 장치(자동 유지)

표·뷰·SV 는 매일 다시 만들어지기도 합니다. 다시 만들 때 권한이 날아가지 않게 아래 3가지를 걸어 두었습니다.

| 만드는 방법 | 대상 | 권한 유지 장치 |
|---|---|---|
| dbt(매일 자동 적재) | GOLD 의 `WIDE_*` 뷰 | `dbt_project.yml` 의 `+grants` + `copy grants` · **회수 안 함**(`should_revoke=False`) |
| SQL 파일(사람이 배포) | SV · SERVING 뷰 | 각 DDL 파일 끝의 `GRANT … TO ROLE GN_DW_AR_SRC_*` 줄(40파일 76줄) |
| 확인 | 전체 | `python3 scripts/rbac_source_gate.py --live` → 마지막 줄 `🟢 PASS` |

- 🔴 SERVING 에는 「앞으로 생길 객체 자동 권한(FUTURE GRANT)」을 **쓰지 않습니다.** 한 스키마에 여러 원천이 섞여 있어서 스키마 단위로 열면 원천 구분이 깨집니다.
- 새 SV 를 만들면 **DDL 파일에 GRANT 줄을 반드시 넣고** 게이트를 돌리세요.

## 6. 자주 하는 작업(IT 담당)

### 6-1. 새 분석가 추가 — 3줄

```sql
GRANT ROLE GN_DW_FR_MARKETING TO USER <사용자>;          -- 업무에 맞는 기능 역할 1개
ALTER USER <사용자> SET DEFAULT_ROLE = 'GN_DW_FR_MARKETING';
ALTER USER <사용자> SET DEFAULT_SECONDARY_ROLES = ();     -- 🔴 빼지 마세요
```

### 6-2. 업무가 바뀐 분석가 — 옛 역할 회수 후 새 역할

```sql
REVOKE ROLE GN_DW_FR_MEMBER FROM USER <사용자>;
GRANT  ROLE GN_DW_FR_MARKETING TO USER <사용자>;
ALTER USER <사용자> SET DEFAULT_ROLE = 'GN_DW_FR_MARKETING';
```

### 6-3. 확인 — 이 사람이 무엇을 가졌나

```sql
SHOW GRANTS TO USER <사용자>;                 -- 기능 역할이 1개뿐인가
SHOW GRANTS TO ROLE GN_DW_FR_MARKETING;       -- 그 역할이 무엇을 담았나
```

### 6-4. 하면 안 되는 것

| 🔴 하지 마세요 | 이유 |
|---|---|
| 사람에게 `GN_DW_AR_SRC_*` 를 직접 주기 | 업무 단위 통제가 깨집니다 |
| 사람에게 기능 역할 2개 주기 · 보조 역할 켜기 | 두 업무 데이터가 합쳐집니다 |
| 사람에게 `GN_DW_APP_OWNER` 주기 | 앱이 읽는 데이터를 직접 다 읽게 됩니다 |
| 앱 이전 전에 `GN_DW_ANALYST` 회수 | 앱 10개가 바로 깨집니다 |
| 객체 이름만 보고 원천 판단 | 정본은 `O270_source_class.csv` 입니다 |

## 7. 용어 사전

| 용어 | 뜻 |
|---|---|
| 역할(Role) | 권한을 담는 열쇠 꾸러미 |
| 기능 역할(FR) | 업무 단위 역할 · 사람에게 주는 것 |
| 접근 역할(AR) | 원천 단위 데이터 묶음 · 사람에게 직접 주지 않음 |
| 상속 | 역할 안에 역할을 넣어 권한을 물려주는 것 |
| 보조 역할(Secondary Roles) | 로그인 시 가진 역할을 동시에 켜는 기능 · 이 설계에서는 끔 |
| USAGE | 「들어갈/쓸 수 있다」(데이터베이스·스키마·웨어하우스·Agent) |
| SELECT | 「읽을 수 있다」(표·뷰·SV) |
| 웨어하우스 | 계산하는 컴퓨터 · 과금 단위 |
| SV(시맨틱 뷰) | 표에 한글 이름·계산식을 붙인 의미 모델 · Agent 가 사용 |
| Agent | 채팅으로 질문하는 분석 도우미 |
| Streamlit 앱 | 사내 웹 화면(대시보드) · 주인 역할의 권한으로 데이터를 읽음 |
| FUTURE GRANT | 앞으로 생길 객체에 자동으로 권한 주는 설정 · SERVING 에는 쓰지 않음 |
