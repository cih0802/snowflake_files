# 11_일적재pipeline 구성 — BRONZE_CRM_2 일배치 테스트 파이프라인

Co-authored with CoCo

## 배경

BRONZE_CRM 적재 담당자가 `BRONZE_CRM_2`를 만들어 **일배치 적재를 테스트**하려 한다. 이에 맞춰
`SILVER_2` / `GOLD_2`를 신설하고, `BRONZE_CRM_2` + 기존 `BRONZE_ERP`/`BRONZE_AGENCY`/`SILVER.BIGQUERY_REFINED_DATA`를
그대로 끌어오는 파이프라인을 구성한다. 구성은 기존 `10_dbt_pipeline`과 동일하며, **오직 `bronze_crm` 원천만
`bronze_crm_2`로 교체**된다.

## 확정된 설계 결정 (이번 세션)

| 항목 | 결정 |
|---|---|
| dbt 반영 방식 | 프로젝트 복제 없음. `profiles.yml`에 `dev2` target 추가 + `generate_schema_name` 매크로가 `target.name=='dev2'`일 때 `_2` 접미를 붙임. `_sources.yml`의 `bronze_crm`만 `target.name` 분기. |
| 권한 재사용 | 신규 role 생성 없음. 기존 `GN_DW_LOADER` / `GN_DW_ENGINEER` / `GN_DW_ADMIN` 세 개만 사용. `ANALYST/VIEWER/SERVICE`는 `_2` 스키마에 권한 없음(테스트 격리). |
| SILVER_2/GOLD_2 구조 | 원안 준수 — DDL이 구조를 소유한다. 단, `04_silver_design/08_SILVER_테이블DDL_*.sql`·`03_top-down_gold/06_DDL.sql`을 손으로 재작성하지 않고, **라이브 SILVER/GOLD 테이블을 `CLONE`** 해 SILVER_2/GOLD_2를 만든 뒤 `TRUNCATE`한다(컬럼·타입·제약·COMMENT 그대로, 데이터 0행). DDL 파일과 라이브 구조 사이 드리프트 걱정 없이 "지금 라이브"와 100% 동일한 구조를 보장한다. |

## 역할 계층 관련 중요 정정

요청하신 "상위 role은 상속하니 LOADER만 부여해도 되면 그렇게" 전제를 실제 계층으로 검증했다.

```
SYSADMIN
  └ GN_DW_ADMIN
       ├ GN_DW_ENGINEER   (형제 — LOADER 를 상속하지 않음)
       ├ GN_DW_ANALYST ─ GN_DW_VIEWER
       ├ GN_DW_LOADER     (형제 — ENGINEER 를 상속하지 않음)
       └ GN_DW_SERVICE
```

`GN_DW_LOADER`와 `GN_DW_ENGINEER`는 **부모-자식이 아니라 형제**다(둘 다 `GN_DW_ADMIN`의 직속 자식). 따라서:

- `GN_DW_ADMIN`은 이미 전 role을 상속하므로 **추가 grant 불필요**(스키마 생성자 = ADMIN, 소유자 권한으로 이미 전체 권한 보유).
- `GN_DW_LOADER`에만 부여하면 **`GN_DW_ENGINEER`는 상속받지 못한다** — dbt가 `GN_DW_ENGINEER`로 실행되므로(`profiles.yml`), `BRONZE_CRM_2` 읽기·`SILVER_2`/`GOLD_2` 적재 권한은 **LOADER 부여와 별개로 ENGINEER에 명시 부여해야 한다.**

⇒ "LOADER만 부여해도 충분"은 이 계층에서는 성립하지 않는다. 대신 각 role의 실제 역할에 맞게 **최소권한으로 3개 role 각각에 필요한 만큼만** 부여했다 (`02_권한부여_LOADER_ENGINEER_ADMIN.sql` 참조). `GN_DW_ADMIN`은 소유자이므로 실행문은 형식상 포함하되 실질적으로는 no-op이다.

## 이번 세션에 실제로 수정한 파일 (10_dbt_pipeline, 라이브)

1. `10_dbt_pipeline/profiles.yml` — `dev2` target 추가(role/warehouse는 `dev`와 동일, `기존 role 재사용`).
2. `10_dbt_pipeline/macros/generate_schema_name.sql` — `target.name=='dev2'`일 때 `_2` 접미 부여.
3. `10_dbt_pipeline/models/silver/_sources.yml` — `bronze_crm` source의 `schema`를 `target.name` 분기(`BRONZE_CRM_2` ↔ `BRONZE_CRM`). 다른 bronze_* source는 변경 없음.

## 실행 순서 및 진행 상태

1. ✅ **실행 완료(이번 세션)** — `01_스키마생성_및_구조복제.sql`: `BRONZE_CRM_2` 신규 생성 · `SILVER_2`/`GOLD_2`는 기존재 확인.
   SILVER 43개 → SILVER_2 43개, GOLD 37개 → GOLD_2 37개 CLONE + TRUNCATE(0행) 실측 확인 완료.
2. ✅ **실행 완료(이번 세션)** — `02_권한부여_LOADER_ENGINEER_ADMIN.sql`: LOADER/ENGINEER/ADMIN 3역할 grant 적용.
   `SHOW FUTURE GRANTS IN SCHEMA GN_DW.BRONZE_CRM_2` 로 ADMIN 전체·ENGINEER SELECT·LOADER INSERT/UPDATE 확인 완료.
3. ⬜ **별도 팀 작업(이 세션 범위 밖)** — BRONZE_CRM_2 적재 담당자가 실제 데이터를 `BRONZE_CRM_2`에 적재.
4. ⬜ **사용자 실행 필요** — `dbt build --target dev2` (워크스페이스 개발 실행) 또는
   `EXECUTE DBT PROJECT GN_DW.OPS.DW_PIPELINE ARGS = 'build --target dev2'` (배포된 프로젝트 실행)로 1회 수동 테스트.
   ⚠️ 3번(BRONZE_CRM_2 실데이터 적재)이 끝나기 전에는 SILVER_2/GOLD_2가 빈 결과로 채워질 뿐 에러는 아니다.
5. ⬜ **사용자 결정 필요** — 검증 후 `03_일배치_TASK_스케줄.sql`로 일배치 TASK 등록.
   `CREATE TASK` 문법은 컴파일 확인 완료. 단, `ACCOUNTADMIN` 권한 부여(EXECUTE TASK ON ACCOUNT)와
   실제 스케줄 활성화(`RESUME`)는 **이번 세션에서 실행하지 않았다** — 매일 자동 실행을 시작하는
   행위라 명시적 승인 없이 활성화하지 않았다.

## 이번 세션에서 실제로 적용된 것 (라이브 반영 완료)

- Snowflake: `BRONZE_CRM_2`/`SILVER_2`/`GOLD_2` 스키마 + SILVER_2(43)/GOLD_2(37) 테이블 구조 복제 + 3역할 grant.
- dbt: `10_dbt_pipeline/profiles.yml`(`dev2` target) · `macros/generate_schema_name.sql`(스키마 접미 분기) ·
  `models/silver/_sources.yml`(`bronze_crm` source 분기) 3개 파일 수정.
- 아직 실행하지 않은 것: `dbt build --target dev2` 자체(원천 데이터 적재 전이라 의미 있는 실행 시점이 아님),
  일배치 TASK 활성화(사용자 승인 필요).

## dbt 운영 제안

- **1회성 테스트 단계**: 위 4번처럼 수동 `--target dev2` 실행으로 충분하다. `SILVER_2`/`GOLD_2` 결과를 원본과 대조(`row count`, PK 유니크, `warn_*` 테스트 재사용)해 신뢰도를 확인한다.
- **반복 일배치로 굳히는 경우**: `03_일적재_TASK_스케줄.sql`의 TASK를 그대로 스케줄에 올리되, `SUSPEND_TASK_AFTER_NUM_FAILURES`를 낮게(예: 1~2) 잡아 실패를 조기에 드러낸다. 운영 전환 여부는 이 테스트 결과에 따라 별도 결정.
- **원본 파이프라인과의 관계**: `dev`/`prod` target(원본 SILVER/GOLD)은 이번 변경으로 전혀 영향받지 않는다(분기가 `dev2`일 때만 발동). 기존 매일 배치와 동시에 안전하게 병행 가능.
- **정리(clean-up) 시점**: 테스트 종료 후 `SILVER_2`/`GOLD_2`/`BRONZE_CRM_2`를 유지할지 DROP할지는 결정 후 별도 SQL로 처리(이 세션 산출물에는 DROP 스크립트를 포함하지 않았다 — 실수 방지를 위해 파괴적 작업은 명시 요청 시에만 작성한다).
